# spectroscope 0.15.2

This release lets sessions on the same Mac send each other messages. They
find each other, the model gets two tools to list and message them, and every
message shows in the chat. A helper agent can run in the background and report
to the main agent, a session can hold a goal that its check command decides,
and `/loop` repeats a prompt on a timer. The playbook pane gets a tab for each
kind of content, a file editor, imports from your installed skills, hooks and
Claude Code plugins, and export and import as a ZIP. A playbook can now run a
workflow, and the spectro playbook ships two. Local speech shows text every two
seconds while you talk, Enter sends while you record, and a resident
whisper-server keeps the speech model loaded. A new Local Setup page on
spectroscope.ai lists what a full local installation needs. A click on a stored
session makes its Files and Terminal panels work, and the context ring uses the
window of the model the session ran on.

***

## Agent messaging

**Sessions on one Mac find each other.** The app's server, the terminal REPL,
`spectro run`, the scheduler (`spectro cron`) and a fleet node announce themselves to the other
spectroscope processes of the same user on the same Mac. The sidebar lists them
under "Other sessions on this machine" with their name, kind, folder name and
last status line. A process that has ended drops out of the list the next time
it is read.

**Two tools for the model.** `list_agents` shows the session's own name, the
other sessions and the session's helpers, without a model call. `send_message`
sends a message to one of them by name. A running agent reads the message at its
next step. An idle session starts a run with it if the permission rule below
allows that.

**Messages in the chat.** Every message sent or received is a block of its own
in the chat, with the name of the other side, the time, the status and the
text. Reply on a received message opens the composer with the recipient set,
and your answer goes out as a message from you. A stored session shows its
messages again when you open it, in every mode.

**Held when permissions differ.** An idle session starts a run with a message at
once only when the sender's permission mode is in the same class: ask; auto and
extended; or readonly. Otherwise the message waits, marked "held for you", with
Deliver and Decline. A held message expires after 10 minutes. `spectro run`,
the scheduler and fleet nodes refuse messages from other sessions. The terminal
REPL holds every message while it waits at its prompt, and `/peer deliver` or
`/peer decline` answers it.

**Limits per sender.** A session takes up to 30 messages in a row from one
sender, then one every two seconds. It ignores a repeat of the previous message
within 30 seconds and queues at most 64 undelivered messages. The sender's model
is told when a message is held, declined, expired, refused or dropped.

**Helpers talk only to the main agent.** A helper agent sends messages only to
the agent that started it. Helpers never message each other, and a helper
cannot reach another session. No other session can send a message to a helper.
What a helper sends to the main agent appears in the chat. The main agent can
ask a helper for its status, and the helper reads the question at its next
step.

**Messages and denied actions.** In the app, in auto and extended mode, a tool
call that needs permission is refused when a message the run has read says that
this action was denied and names the command or the file. In ask mode you
decide in the permission dialog, as before.

**On by default, with a switch.** "Messages between agents" in the composer's
settings menu turns messaging off. The messaging tools leave the next run, and
the app takes no messages from other sessions. The settings key is
`agentMessaging`. With messaging on, `send_message` and `list_agents` add 1,073
characters to a request to Anthropic and 1,131 to an OpenAI compatible server.
With `wait_agents` and the `background` option of `spawn_agents`, the tool list
grows by 2,254 and 2,341 characters (measured on the tool list of the request
body). With messaging off, no request carries them.

## Background helpers

**Helpers that run in the background.** `spawn_agents` takes `background: true`.
The call returns at once with the helpers' names, and the main agent keeps
working. The helpers share the chat's session slots, as before. Their status
lines and their results reach the main agent as messages at its next step.
`wait_agents` collects the results of the helpers it names, or of all, and lists
the status lines of those still running. Background helpers need messaging on.

**No helper is left running.** When the main agent ends its turn while helpers
still run, the run waits for them and hands their results to the agent. With a
goal set, it waits until the next check-in instead. A run that ends at the turn
limit cancels the helpers that still run, and Stop cancels every background
helper. A helper cannot start helpers of its own. The chat and the Lab show the
messages between the main agent and its helpers, also when you open the stored
session later.

## Workflows

**Run a workflow from the playbook.** The Playbook tab has a Workflows section.
It lists the workflows of the loaded playbook, each with a field for a question
or a note and a Run button. A workflow is a JSON file with a list of steps: a
prompt to the chat, a fan-out to several helpers with one summary, and an end.
A step that repeats needs a round limit. The run takes place in the chat of the
session, where the helpers' status lines and the summary appear.

**Two fan-outs ship.** The spectro playbook now carries `fanout-review`, three
reviewers over the diff of the working folder and one summary, and
`fanout-research`, three helpers that explore a question and one summary. When
you pick the spectro playbook add-on, Spectrolyzr copies both into the playbook
it generates.

## Goal and loop

**A goal per session.** The composer's settings menu has a Goal section with two
fields: what should be true, and a check command such as `npm test`. The goal
holds for every run of the session until you clear it. A line under the composer
shows it with its last verdict. When the agent wants to end its turn and the
check fails, the run goes on. It stops when the check passes, when the check
fails twice in a row with the same output and no tool call succeeded in
between, or at the turn limit.

**Goals and background helpers.** While helpers run, the check waits. The agent
gets a note that lists the helpers with their last status line after 30
minutes, then 60 minutes later, then every 120 minutes. When the last helper
ends, the check runs at the next end of turn.

**Errors that clear a goal.** A full context window, a failed sign-in, a billing
error or a model that is not available clears the goal. The chat says "Goal
cleared after an unrecoverable error" and names the kind of error. A network
error that passes, a steering message or the turn limit leave the goal in
place. Helpers and unattended runs hold no goal.

**Repeat a prompt with /loop.** `/loop 10m <prompt>` in the web chat or the
terminal runs the prompt now and again every ten minutes. The interval takes s,
m, h or d, and a value below one minute or above one hour is moved to that
limit. Without an interval, the model sets the pace: it ends each round by
calling `schedule_wakeup` with the next delay and a reason. In ask mode you
approve each wakeup. A wakeup starts a run only when the session is idle. A
chip under the composer shows the turn, the time of the next wakeup, its reason
and Stop.

**When a loop ends.** A loop ends when you press Stop or after seven days. A
loop without an interval also ends when the model sets no next wakeup twice in
a row. After the first miss it waits 20 minutes before it asks again. If no
window has the session open when a wakeup is due, the wakeup waits until a
window opens the session again.

## Playbook bundles

**A tab per kind.** The playbook pane has the tabs Playbook, Skills, Agents,
Hooks, Commands, Workflows, Plugin, Files and New. Each kind tab lists the
entries of that kind in `playbook.json`, each marked as listed, only on disk, or
listed but missing, and shows a file browser of its folder. Files shows the
whole folder. The tabs from Skills to Workflows and the Plugin tab stay
disabled until a playbook is loaded. Files needs only a folder.

**Edit any text file.** Select a file to edit it on the right. Save checks that
the file did not change on disk after you opened it, and offers a reload when it
did. Markdown and JSON files show a preview beside the text. `playbook.json`
opens the graph editor. With unsaved changes, a switch to another tab is
blocked, as in the graph editor. The app reads a playbook folder to six levels
and 200 files. Saving a file, Export, Import ZIP and Install stop at 24 MB.

**Import what you already have.** On the Skills tab, Import lists the skills
installed on this Mac and the skills of the catalogue, with a checkbox each. An
imported skill keeps its licence, and `PROVENANCE.md` gets a line naming its
source. On the Hooks tab, Import hooks copies the hooks of your user settings
and the scripts in your home that they call. Agents and Commands have New with a
name field. Every entry has Remove, with a confirmation.

**Project and private paths in hooks.** An imported hook that names your project
folder is written with `{project}`, and install fills in the working folder. A
hook that names a file in a hidden folder of your home, such as `~/.ssh`, or a
path that climbs out of the project folder, is left out. The Import hooks list
marks such a hook before you import. Other paths in your home are written with
`~` where they start a word of the command.

**Import a Claude Code plugin.** The Plugin tab lists the Claude Code plugins
installed in this home, with what each one carries. Import copies the kinds you
tick: skills as one pack, agents, commands, and hooks that run before or after a
tool call. Hook events and agent fields that the playbook format does not know
are dropped and listed. MCP server definitions are never copied. A plugin
without a licence file is not imported.

**Share a playbook as a ZIP.** Export saves the folder as `<id>.playbook.zip`,
and the same folder gives the same file. Import ZIP reads the file in the
browser, shows its entries and writes them into an empty folder you choose. The
server checks every path and the playbook before anything lands, and a refusal
leaves the folder empty. A bundle with more than 200 entries, more than 24 MB or
an entry deeper than six levels is refused.

**Credential check on hooks.** Export, Import ZIP and Install refuse a hooks
file in which a value matches one of the credential patterns the recordings
already redact, and name the line and the pattern.

**After Generate and Import ZIP.** After Generate on the New tab with Playbook
chosen, the pane opens the Skills tab of the new folder, so you see what the
copy carries. Import on the Plugin tab also opens the Skills tab. After Import
ZIP, the pane opens the Playbook tab of the imported folder.

## Speech

**Live text with local whisper.** With local speech and live text on, the
composer shows what you said every two seconds while you talk. In our
measurement, a spoken word appeared a median of 1.0 seconds after it was spoken
with whisper-server and 1.6 seconds with whisper-cli (Apple M4 Pro, the small
whisper model, a synthetic 20 second clip played through Chrome's test
microphone, no model answering at the same time).

**Enter sends while you record.** As soon as any text is recognised, Send is
enabled and takes the focus. Enter or Send stops the recording, waits a moment
for the last text and sends the message in one step. If you type during the
recording, the focus stays in the text box. Hosted speech works the same way.
With live text off, Enter stops the recording, waits for the transcription and
sends.

**The model loads before you speak.** When the speech model has to load, a card
over the composer says so. The microphone opens only when the model is ready, so
nothing you say comes before the model can transcribe it.

**whisper-server keeps the model loaded.** On the first press, the app starts
whisper-server from the same Homebrew package on 127.0.0.1 and keeps it running
until 30 minutes pass without use. Later presses were ready in 131 to 264 ms,
without the loading card, and each chunk took a median of 275 ms against 762 ms
with whisper-cli (same measurement as above). The setting "Live text runs on"
offers automatic, whisper-cli and whisper-server. Automatic picks whisper-server
when it is installed. The settings key is `sttRunner`. `spectro doctor` names
the runner and where it found whisper-server; whether the server is up shows in
the speech settings of the running app.

**A filled microphone.** While you record, the microphone button shows the
microphone filled in, instead of a square.

## Local Setup

**One page for a full local installation.** spectroscope.ai/local-setup/ lists
what spectroscope can use on your machine in seven levels: run the app, a local
model, speech, web search, code graph, playbooks and the developer path. Level 1
is all the app needs, and the other levels are optional. A switch shows macOS or
Linux. Each step has a check. Commands have a copy button, a step with a
script offers it for download, and a step that downloads something shows the
size with the date and method of the measurement. "I have this" marks a
step and adds to the ring of its level; the marks stay in your browser. The
page runs nothing: scripts are files you download, read and run yourself. The
website links the page under the download block.

**SearXNG without git.** When Docker and its compose plugin are ready, the web
search settings now offer `install-searxng.sh` from the running app instead of
a clone of the repository. The first copy block makes `~/spectro-searxng` and
downloads the script, the second runs it. Download script saves the file
through your browser; move it into `~/spectro-searxng` before you run it. The
script writes its compose file beside itself, keeps one it wrote before, and
stops when it finds the compose file of another stack. SearXNG then answers on
port 8888 of this machine by default, and web search switches to it without a
restart.

## Sessions

**A click wakes a stored session.** Selecting a stored session in the list makes
its folder available in the dock: Files shows its tree and Terminal opens a
shell in that folder, with no message and no model call. A folder that no longer
exists is shown as gone, the terminal stays closed, and nothing is created.
Quick clicks through the list wake only the session you stop at. A session that
runs in another window stays read only.

**The context ring keeps the model's window.** Each run now records the context
window of its model when it knows one. A stored session shows the ring against
that window as soon as you select it. A session on a model with a one million
token window shows 300,000 tokens as 30 percent, not 300 percent. Sessions
recorded before 0.15.2 take the window from their last context report. When no
window is known, the ring divides by the fallback of 100,000 tokens, and its
popover says "window unknown". A helper's window no longer moves the main
agent's ring. Switching the model before the first run moves the ring to the
new model's window when the provider publishes one.

## First start

**The dock opens as tabs.** A fresh installation opens the side panel dock in
tabs mode, one panel at a time. A browser that already stored a dock layout
keeps it.

**The mode screen returns once.** After the update, the first start screen with
learn, light and developer shows one more time. It now explains developer in
five short sentences: everything learn shows, the project folder as the
workspace, a playbook with phases and a check between them, a model per phase,
and Spectrolyzr. The mode you use stays until you choose, and after the choice
the screen does not come back.

## Chat

**Insight and Wire under each answer.** The LLM exchange under an answer now
offers Structured, Insight and Wire, as the trace does. Insight shows the
request and the response as foldable JSON with highlighting, and Expand all and
Default work on it. Wire shows the bytes. A session imported from Claude Code or
VS Code offers Structured only. The exchange opens on Structured each time.

## Code graph

**Show a graph that is already there.** When the session folder holds
`graphify-out/graph.html`, the ⋮ menu and the folder chip offer "Show code
graph" and "Update code graph". Show opens the graph in the internal browser,
the same way the "Graph ready" chip does. Update opens the build sheet with
Update selected. A folder without a graph keeps the single row "Build code
graph", which now opens the sheet on a full build. When a build ends, Build
turns into Show without a reload. If graphify is not installed, Show still
opens an existing graph, and Update shows the install command and cannot
start.

**The model can ask the graph.** A new tool, `code_graph`, asks graphify about
the graph of the session folder: a question in words (`query`), the path
between two nodes (`path`), one node and its neighbours (`explain`), what
depends on a node (`affected`) and the most connected nodes (`god_nodes`). It
only reads and asks for no permission. The app offers it to the main agent and
to explore and worker helpers when graphify is installed and the folder holds
`graphify-out/graph.json`. The system prompt then tells the model to ask the
graph before it reads many files to answer a question about structure. A call
stops after 30 seconds, and the tool cuts an answer at 16,000 characters.

## Known limits

- Local Setup is a page on the website for now. The app does not ship a copy,
  has no menu entry for it and does not tick the steps it can detect. Three
  steps show a placeholder instead of a screenshot. The Linux lines come from
  the vendors' documentation and the product README and have not yet been run
  on a clean machine. Levels 6 and 7 show two steps each, with a check and no
  commands.
- The mode screen puts developer alone in a second row, and on a short window
  you scroll to see it.
- With whisper-cli as the runner, the loading card shows on every press, for
  0.5 to 2.1 seconds in our checks, and once for 9 seconds while a model was
  answering. With live text off, every recording still runs whisper-cli.
- A recording that stays silent does not count as use, so whisper-server can
  stop after 30 quiet minutes. If the app is killed with `kill -9`,
  whisper-server keeps running until you stop it.
- The check against denied actions runs in the app only, and it matches words,
  not intent. A message that describes a denied action in other words passes
  in auto mode.
- Messages between sessions are protected by a token file that any process of
  your user account can read.
- Background helpers change the tool list inside a run, so a provider's prompt
  cache starts again from that request.
- A workflow that starts a worker helper, which can write files, does not run
  from the Playbook tab. A diff the chat prints during `fanout-review` renders
  as Markdown, so its list markers and headings look garbled.
- Hook scripts lose their execute bit after Import hooks or a ZIP round trip.
- Import ZIP accepts a hooks file that names a hidden folder of your home or a
  folder above the project; Install refuses it later.
- The credential check covers the hooks file only, and it does not yet catch a
  password after a command option or a `name=value` secret. A key inside a
  `SKILL.md` travels in a ZIP unchanged.
- The Files tab cannot create a new file, a single binary file cannot be
  deleted there, and a file whose name starts with a dot cannot be written.
- Some refusals of the skill import and of Import ZIP show an English sentence
  in the German interface.
- `code_graph` is offered in the app only. The terminal REPL, `spectro run` and
  the scheduler do not carry it yet.
- The Files panel of a woken session says "pinned workspace". The ring of an open
  session does not read the window again when a model loads later; the next run
  records it.
