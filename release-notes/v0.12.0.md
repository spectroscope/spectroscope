# spectroscope 0.12.0

Released 2026-09-02, 16 merges after 0.11.0.

This release is mostly about the numbers that govern a run, and it changes
behaviour you will see on the first run after upgrading. Four of those numbers
moved. A settings file that used to be refused whole is now read key by key. And
settings that only ever reached the browser session now reach `spectro run`,
scheduled fires, fleet nodes and every child agent, where the number you set
resolved perfectly and then reached nothing.

---

## What changes on your first run after upgrading

**A project settings file that was refused whole is now applied in part.**

Nine settings are process-global, and a project folder may not set them:
`workspace`, `logLevel`, `allowLocalhost`, `chromeBinary`, `searxngUrl`,
`headlessMcp`, `progressGuardWrites`, `progressGuardFailures` and
`progressGuardPlanTurns`. Until now a project settings file that named even one
of them was dropped entirely, every key in it, forbidden or not. It is read per
key now: the forbidden key is skipped, the rest of the file applies, and the
notice names both halves instead of saying the whole file went.

That correction has a consequence in the direction that matters. If your
project's `.spectro/settings.json` names any of those nine keys, everything else
in that file was inert and is now in force. That includes `permissionMode` and
`autoApprove`, the two settings that decide whether a tool asks you before it
runs. A file carrying `permissionMode: "auto"` next to a forbidden key used to
be dropped whole, so your gate stayed at whatever your user settings said —
`ask`, unless you had changed it. It does not any more.

This is not a corner case. It is the documented setup path: the browser and
launch pages shipped in 0.11.0 told you to put `allowLocalhost` in "the
project's own settings file", and `allowLocalhost` is one of the nine. **Open
your project's `.spectro/settings.json` before your next unattended run and read
what else is in it.** The documentation now says to put that key in
`~/.spectro/settings.json`, where it belongs, and says why: a workspace is a
folder the agent writes into, so the network fence's only switch must not live
inside the sandbox it guards.

**A run now goes up to 150 turns before the harness stops it, instead of 15.**

The old ceiling was a guess. The new one comes from a census of 7,139 real agent
sessions recorded on one developer's machine — transcripts of a comparable
coding harness, not of spectroscope, because spectroscope has no fleet of runs
to measure yet. In that sample 48.0% ran past 15 turns; the median session took
14 turns, the 90th percentile 88 and the 95th 129, and the median session took
one human input, which is exactly the shape a low ceiling kills. A run that used
to stop and hand control back will now keep going. That is the intended
behaviour and not a hang.

Two things make this bigger than a default change. First, `spectro run`, every
scheduled fire, every fleet node, the terminal REPL and every child agent used
to run on the built-in ceiling no matter what you had configured: `maxTurns` had
a settings entry, a documentation row and exactly one call site, the browser
session. All of those faces read the setting now. Second, `maxTokens` had a
builder method with no callers at all — a public method nothing in the shipped
code could reach — so every run spent the built-in budget. It is read now too,
along with the compaction threshold. Its default did not move: 32,000 output
tokens per provider call, the same figure 0.11.0 spent.

**What this costs you.** If you drive spectroscope unattended against a metered
API, one run can now cost up to ten times what it did, and the ceiling is per
agent rather than per run — a child gets the same 150 its parent has. If you had
set `maxTurns` in a settings file expecting it to hold, it was doing nothing
before and is doing something now. `--max-turns` still works as an outer brake
and still cuts a run shorter than the setting, never longer.

**Compaction follows the window the model really has, in both directions.**

A conversation used to be summarised at a flat 100,000 input tokens whenever the
backend would not say how much it could hold. The harness now falls back to the
window the model's vendor publishes before it falls back to that constant, and
takes 70% of it. On a model that publishes a 1,000,000-token window the trigger
moves from 100,000 to 700,000, with no setting touched.

The other half of the same change moves the other way. The conversation's share
of whatever window is in play went from three quarters to 70%, so a backend that
states its own window — every local server that answers the question — compacts
a little earlier than it did: a 250,000-token instance trips near 175,000 where
it used to reach near 188,000. Hosted models with a published window go up an
order of magnitude; a measured local instance goes down about 7%.

The order of preference is: a threshold you set explicitly, else the window the
backend says the loaded instance actually serves, else the window the vendor
publishes for that model, else the constant. You do not have to work out which
one applied — the context gauge names the divisor it is dividing by and where
that number came from.

**A run may ask you up to 9 questions instead of 3.** Only 1.8% of the census
sessions used the ask tool at all, but of those, 16.5% asked more than three:
one asking session in six would have hit the old budget.

**A symlink out of the workspace no longer resolves.** The sandbox rule compared
paths as spelled and now compares real ones, on every tool that takes a path —
the file tools and the directory tools alike. A link that stays inside the
workspace still works, because the rule is about leaving and not about links. A
link that points outside it is refused now, for reading as well as writing,
however deliberate it was. If your workspace reaches a sibling checkout, a data
directory or a cache through a link, move the workspace or copy in what it needs
before the next run.

**You can write a launch configuration from inside the product, and the model
cannot.** The browser's start page grew an `Add a configuration` form: a name,
and either a command with a port spectroscope starts or an address it attaches
to. It always writes `.spectro/launch.json`, and the page tells you where it
went. `write_file` and `edit_file` refuse that one file. Everything else a write
tool touches is data; a launch configuration is a program, and the next press of
play runs its command as you, on your machine. If you have an agent workflow
that generated `.spectro/launch.json` or `.claude/launch.json`, it will stop
working. That is the change rather than a side effect of it.

**To keep 0.11.0's numbers while you upgrade**, set `maxTurns: 15`,
`questionsPerRun: 3` and `compactionThreshold: 100000` in
`~/.spectro/settings.json` before the first run. All three are read on every
face now, which is the other half of this release.

## Two published pieces of spectro-core changed shape

Both are in one class. `grep -rn CompactionThreshold` over your source answers
whether this section is about you; if it finds nothing, recompile against 0.12.0
and there is nothing else here to do. Maven Central is append-only, so neither
break can be taken back once the artifacts are up.

`CompactionThreshold.Derived` carried two components and now carries three: the
window that produced the threshold sits beside the number and its provenance.
There is **no two-argument compatibility constructor**. Source that calls
`new Derived(tokens, source)` stops compiling, and a jar compiled against
0.11.0 throws `NoSuchMethodError` at the call.

`CompactionThreshold.Source` gained `MODEL`, inserted in the middle, between
`WINDOW` and `FALLBACK`. `FALLBACK.ordinal()` therefore moves from 2 to 3, and
any exhaustive `switch` over that enum stops compiling until the new constant is
handled. If you have persisted an ordinal rather than a name, it now means
something else.

Two constants also changed value: `DEFAULT_MAX_TURNS` (15 to 150) and
`QUESTIONS_PER_RUN` (3 to 9). Both are `public static final int`, which `javac`
copies into whatever compiles against them, so a jar built against 0.11.0 keeps
15 and 3 baked into its bytecode while linking against a library that uses 150
and 9. Nothing errors and nothing warns; the two halves simply disagree.
Recompile against 0.12.0 rather than dropping the new jar under an old build.

Everything else held. `SpectroConfig` grew seven components and kept a
constructor with the exact 0.11.0 shape, and the settings, tool-context,
subagent and context-info types all kept theirs. No public class, method or
settings key was removed or renamed, and no command-line flag or subcommand went
away.

## A launch that failed reaches the record

Pressing play used to put its result — `it exited with code 143` and all — in a
status line inside the browser panel that the next click erased. Success and
failure are both events in the session now, under a new frame kind,
`launch_outcome`, and both reach the recording.

Two existing frames grew a field. `context_info` gained `contextWindow`, the
window the threshold was measured against, and its `thresholdSource` gained a
fourth value, `model`, beside `override`, `window` and `fallback`.
`settings_ignored` gained `kept`, the list of keys in that file that still
applied — the record of the per-key read described above.

The reader ignores unknown *fields*, so a 0.12.0 recording keeps its shape for
older tools in that respect. A new frame *kind* is a different matter: the
format declares no fallback for a type it does not know, so expect the line to
fail rather than be skipped politely. That is a reading of the format and not a
measurement against your reader — push one `launch_outcome` line through yours
first.

## The numbers that govern a run are a page you can read

Settings grew an eighteenth section, `Governing numbers`. It lists every fixed
number in this build that decides what a run may do, how long it may take and
how much it may produce, with what each one governs and whether you can change
it. 116 numbers govern a run here; 133 are classified in all, and 19 of those
are yours, with the settings key standing beside each one. The other 17 are
aliases and plumbing, and the page says which they are and why they do not
count.

The explanation under each number is the comment from the source itself. None of
it was written for that page, which is the point: a second description is a
second thing to go stale. The page is candid about the numbers it cannot hand
you, and says which kind each one is — fixed here, fixed from outside, chosen by
the model, looks settable and is not, or an open question nobody has argued for
yet. Seven constants carry that last kind, and the page calls it the backlog,
rendered.

`GET /api/governing-numbers` serves the same list, and a server without the
endpoint says so instead of drawing an empty page. It reports the value this
build ships and the settings key that overrides it, never the value your own
settings resolved to. A drift check goes red when a new governing constant
appears without a stated reason. The page cannot fall behind the code quietly.

## Seven settings that did not exist

`maxTokens`, `questionsPerRun`, `maxQuestionOptions`, `maxQuestionChars`,
`commandTimeoutSeconds`, `chatReserveWidth` and `dockMaxWidth`. `maxTurns` was
already a key; only its default moved.

`maxTokens` is the reply budget for one provider call, and it is the one default
the census left alone: of 33,810 measured responses the median was 355 output
tokens and only 0.21% went past 32,000. What changed is that a setting can reach
it at all.

One of the seven does not reach a run yet. See the limits below.

## A skill tells the model where it lives

A skill used to arrive as text with no address. If it referred to a file sitting
beside it, the model had to go hunting: one watched run spent its whole turn on
a filesystem-wide `find` and died on the ten-second command timeout, with the
file it wanted never opened.

A run that opens a skill is told the directory it was loaded from now, and gets
`read_skill_file` to open what sits there. It is registered at the read tier, so
it asks for no gate. The address is honest about the sandbox too. It used to end
`read_file cannot: the directory is outside the working directory`, which is
false whenever the skill sits under the workspace you pointed the run at — what
pointing it at a project gives you. Whether the ordinary read tool reaches that
directory is computed now, by the rule that tool applies. The skill says where
it is.

## Ten smaller things in the workspace and the lab

- **The dock goes as wide as you tell it.** Three caps ran in series — the drag,
  the store and the stylesheet — and which one stopped you depended on your
  monitor. One function owns the row's widths now, and both numbers are
  settings.
- **Opening the gallery no longer squeezes the chat past zero.** Two allocators
  each reserved the same room with no knowledge of the other. On a 1030px row
  with the gallery open, the chat computed to −318px. Nobody had reported it.
- **A panel that fills gets its own column.** Open Files and it takes the
  column's full height instead of splitting it with a neighbour you did not ask
  to keep.
- **A tool card grows with what is in it.** A long output sat in a 260px window
  while the JSON view ran to the bottom of the page. The other faces get 70% of
  the viewport now, and a script well 88%.
- **The queue stands above the main agent.** Commands you sent faster than the
  run could take them are drawn as a backlog on the map, with a depth that steps
  with the scrubber.
- **The browser wears a tab strip.** One tab, with an × that closes the page and
  takes you back to the launch configurations. There is deliberately no `+`.
- **The terminal keeps its tabs.** Closing the panel used to throw every one of
  them away. They come back with your layout now, and the panel says what came
  back and what did not: the shells are new, so the scrollback from before is
  gone.
- **The context gauge names its divisor.** A local backend used to show no
  window line at all, because the number came from a hand-typed table of vendor
  prefixes that no local model name matches. It says what it is dividing by now,
  and where that came from: a measured instance, a published model window, your
  own setting, or nothing.
- **The LLM card stops calling a loopback address remote.**
- **The work panel's empty state stops promising what it cannot deliver.** It
  listed three kinds of work; a live session can only ever produce one of them.
  It names what it actually folds now, and says plainly that starting a launch
  configuration is not one of those things.

## Fixed

- **A symlink no longer walks out of the sandbox.** The containment check
  compared paths before resolving them, so a link inside the workspace pointing
  outside it was measured as inside. Both sides are resolved to real paths
  before the comparison now, and the published tool reference says so. It is a
  fix and an upgrade hazard at once; the first section has the hazard.
- **A refused settings key no longer costs the whole file** — described above.
- **The documentation stopped creating the condition it warned about.** The
  browser and launch pages both told you to put a process-global key in a
  project settings file, which is the one place it is refused.

## Known limits

- Reading a project settings file is per key; writing one is still
  all-or-nothing. A patch that names a forbidden key is refused entire, because
  a patch has not landed yet and one correction is cheaper than a file that will
  be read in halves forever after. The refusal message says what a read would do
  differently.
- `commandTimeoutSeconds` is a key you can set, and no shipped tool belt reads
  it yet. A shell command is still killed after ten seconds whatever your
  settings file says. What did land is that the number is declared in one place
  and the sentence the model reads derives from it, so raising it will not leave
  the model quoting the old figure.
- The published-window table is a hand-kept list of ten model prefixes. A model
  it does not recognise still falls back to the constant, and a backend that
  states its own window is still believed ahead of the table.
- The turn ceiling counts turns and nothing else. It knows about neither tokens
  nor money, and 150 turns against a metered API is not a small number.
- The browser still holds one page per session. The strip has one tab and no `+`
  on purpose: a `+` would be a promise.
- The terminal's tabs come back; their shells do not. A restored tab is a new
  shell, and the scrollback from before is gone.
- The queue node shows a depth and the texts it can honestly show, never a
  matched list. Over 342 measured transcripts, 34.2% of 15,477 queue operations
  carry no text at all, and the frame has no id to join on.
- A recording written by this release names a frame kind that older readers do
  not know.

## Getting it

The channels are the ones 0.5.0 shipped. Nothing new this cut.

**Homebrew, on macOS.** `brew install --cask spectroscope/tap/spectroscope`
installs the signed and notarized desktop kit.

**The macOS disk image.** `spectroscope-0.12.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**apt, on Debian and Ubuntu.** The signed repository at
`https://apt.spectroscope.dev` serves the deb once this version enters the pool.
0.11.0 did enter it, after three cuts that never did, so check
`apt policy spectroscope` before assuming `apt upgrade` carries you here.
x86_64 only.

If nobody is at the keyboard, use
`sudo DEBIAN_FRONTEND=noninteractive apt install -y spectroscope` instead of the
documented line. The plain line waits for you twice, and in a container neither
question is answered: apt asks you to confirm the download, and on an image
where `tzdata` has never been configured a package further down the chain asks
which timezone you live in. Neither one times out.

**The Linux kit.** `spectroscope-0.12.0-x86_64.AppImage` and
`spectroscope_0.12.0_amd64.deb` on the release page, built and smoke-tested on
Linux by this project's own CI. Both bundle their own Java runtime and
`llama-server`. x86_64 only, not signed.

**The jar and the CLI.** `spectro-server-0.12.0.jar` and `spectro-0.12.0.zip`
run on any machine with Java 21. They are the smallest way in, and the only way
onto a platform that has no kit.

**In your own code.**

```
dev.spectroscope:spectro-core:0.12.0
dev.spectroscope:spectro-orchestrator:0.12.0
```

Read the library section above before you upgrade a build that compiles against
0.11.0. Maven Central is append-only, and 0.9.0's libraries were never published
there, so on Central this release follows 0.11.0 and the gap where 0.9.0 would
sit stays visible. If the coordinates above answer 404 for you, the publish has
not propagated yet.
