# spectroscope 0.15.0
DRAFT, the cut is not made

This release adds a third mode, developer, and with it the playbook: a folder
that describes how a team builds, drawn as a graph with a model per step. The
app ships one playbook, spectro, and copies it into a folder with one button. A
run follows the playbook on the app's own state graph engine, runs each step on
the model it names and checks the handover before the next step starts. You can
edit a playbook with the mouse, and Spectrolyzr generates a new project with a
playbook pinned to it. The skills, commands and hooks a playbook carries
install from one list. The settings page shows every provider with its state,
and the model picker greys out providers that need a key or did not answer.

---

## Developer mode and playbooks

**A third mode.** developer sits next to learn and light. It opens everything
learn opens, without the tutorial, and adds a Playbook segment to the sidebar.
The first question of a new window offers it, and the mode switch changes it
later. In learn and light the segment does not exist and its code is never
loaded.

**A playbook is a folder.** Its central file, `playbook.json`, describes a graph
of steps, decisions and ends. A step names who performs it (the chat or a child
agent), its skills, its model choice, whether it stays private, the documents
it takes in and hands on, and whether it waits for your nod. A decision runs a
check and has named outcomes, each with exactly one arrow. Every loop passes a
decision with a round limit, and when the rounds run out the decision takes the
outcome `exhausted`. The file names models through a small set of model
choices, such as `fast` and `strong`, and never by address. A key or an
address in the file is refused with its path, and no step may ask for the
extended permission mode.

**The Playbook segment.** It lists your registered folders and pins one to the
working folder. It draws the graph with outcome labels and loops, and shows one
row per step: each skill marked installed or not, and the state of the provider
behind each model choice. Problems in the file show as findings, one line each.

**The spectro playbook ships with the app.** A first decision sorts the work
into a spike, a bounded change or an architectural change. The architectural
path brainstorms, checks the spec, plans, sets up a worktree and runs a build
loop of implement, review and fix, at most five rounds per task, before a final
review. Its skills are spectropowers, a copy of the superpowers skills with
house rules worked into the text. The folder carries the MIT licence of the
source and a provenance file that lists every edited file.

**Copy with one button.** "Copy the spectro playbook into a folder" writes the
bundled files into a folder you name and registers it. It never overwrites. If
any target file exists, nothing is written and the window lists the files in
the way.

## Running a playbook

**Build by this.** With a playbook pinned to the working folder, "Build by
this" opens a confirmation first. It shows the drawing and one row per step
with the provider and model it resolves to on this machine. It lists every
skill with its source and every command a check may run, word for word, and a
hash over the playbook, its templates and its skills. Start stays disabled
while the sheet names a reason, for example a missing skill or a private step
on a cloud model. If a file changed after the sheet opened, the run does not
start. No tool of the chat agent can start a run.

**A model per step.** A chat step runs as a turn of the main agent. When its
model differs from the chat's, the chat switches to it with the conversation
and switches back when the run ends. A child step runs as a child agent on the
provider of its own model choice, whatever the chat uses. A private step uses
only its primary model and stops to ask when that model does not answer,
naming the provider, model, address and reason. A cheap step tries its
primary model and then its fallbacks in order, and records the walk. A chat step that would switch to a
cloud model after a private step asks first.

**Handover checks.** The next step starts only after the previous handover
passed its check. There are five kinds: `sections` (the documents carry their
required sections), `open_items` (no unchecked task is left), `command` (exit
code 0, through the same permission gate as any agent command), `review` (a
read only child on the named model answers with an outcome) and `human` (you
answer). A step's permission is the stricter of the session's and the step's,
so a playbook cannot widen it.

**The lit graph.** The plan tab shows one line per node on the forward path.
Under the drawing, the segment lights the node that is running. When the run
ends, a line names the end it reached and the stop reason. Stop cancels the
running step.

**The sidecar.** Every session that runs a playbook gets a sidecar file under
`~/.spectro/playbook-runs/`. Per step it records the model choice, the
provider, the model and its address, the probe result, the fallback walk, the
check outcomes and your nods, together with the hash of the playbook. It
answers which model served which step. Its strings pass the same redaction as
the other recordings, and the session file itself is unchanged.

A run does not resume after a restart, and it starts only from the window.

## Editing a playbook

**Edit with the mouse.** "Edit" opens an editor on the graph. Add a step, a
decision or an end after the selection, drag from a handle to a box to
connect them, delete with the button or Backspace, and step through the
last 50 changes with Undo and Redo. The layout runs again after every change,
so a box cannot be dragged to a place of its own. The left button selects and
connects; the right and middle buttons pan. A panel edits the selected node,
the document types and the checks. An arrow to a node nobody defined is drawn
as a dashed box marked missing.

**Structure only.** Save writes `playbook.json` with structure only,
without coordinates and with the keys in one fixed order, so a diff shows your
change and nothing else. A file written by hand in another layout is rewritten
in that form on its first save, and the editor says so before you save. A file
with fields the reader does not know stays read only.

**Two refusals.** The server checks the draft a moment after each change. While
any finding exists, Save is refused with 400 and the list of findings, and the
file on disk stays as it was. When the file changed on disk after you opened
it, Save is refused with 409. Your draft stays on screen, and Revert reads the
file again.

## Spectrolyzr

**A new project with its playbook.** Spectrolyzr is a wizard behind the "New
project" tab of the Playbook segment. Pick an archetype: a service with one
`/health` route, a library with one public function, or a command line tool.
Pick TypeScript, Python or Java and a name. Add any of three add-ons: a quality
gate command, a GitHub Actions workflow for CI, and the spectro playbook.

**Why each file is there.** The last step shows the file tree. Select a file to
read its content and one sentence under "Why this file". Generate writes into a
folder you pick and never overwrites. A conflict lists the files in the way,
per folder.

**The same choices give the same files.** Generate is deterministic, byte for
byte. The files come from templates inside the app, nothing is fetched from the
network, and no generated project depends on a spectroscope package.

**The playbook is pinned.** With the spectro playbook add-on, the playbook goes
into a folder of its own, by default a sibling named after the project with
`-playbook` at the end.
Generate sets the playbook's test command to the project's check command,
registers the folder and pins it to the new project.

**No Gradle wrapper yet.** A generated Java project has no Gradle wrapper, so
`gradle test` needs Gradle and Java 21 on your machine.

## Installing what a playbook brings

**One list before anything is written.** The Contents row of the Playbook
segment counts what a folder carries and offers Install and Remove. Install
opens a list with every item, its source path in the folder, its SHA-256 hash,
its state and its reach. Nothing is written before you press Install in that
list. If the folder changed in the meantime, nothing is written and the list
reloads. The list also says how many characters the installed skills and
commands add to the system prompt of every new session.

**Skills and commands.** Skills are copied into `~/.spectro/skills/` as a pack,
each with the playbook's licence and provenance. A command becomes a one file
skill, invoked as `/<playbook id>:<name>`. Every new session sees them. A skill
that a step names and your installation lacks gets an "Install from this
playbook" link in the step table.

**Hooks only when ticked.** Hooks have their own tick, off by default. The list
shows every hook command and the full text of every script. Ticked hooks are
added to your user settings and apply to every new session.

**Agents and workflows are listed.** Agent files are listed with their hash and
checked, and nothing is copied. Workflow files are listed with their hash and
never run, because the app has no workflow runner.

**Clean installs and removals.** Each skill is built in a staging folder and
moved into place in one step. A second install of the same playbook is refused
with the folder and date of the first. Remove takes out what the install
recorded and keeps any installed copy you edited since, naming it.

## Providers

**Every provider in one table.** The settings page shows one row per provider:
the state in words (needs a key, model not downloaded, configured, answers, not
answering), whether a key is present, the address of a local server, the
number of models and whether that list is live or curated, and the age of the
last check. Check tests one provider and Check all tests every one. A check
asks for the model list, never for a completion, and returns within five
seconds, also when a server accepts the connection and never answers. Local
servers are checked when the page opens, and a provider is checked once after
you save its key. Nothing checks on a timer.

**A greyed picker.** The model picker under the message box keeps all eight
providers. A provider that needs a key or did not answer its last check is
greyed out with the reason in the tooltip, and Switch stays disabled while it is
selected. The provider the chat uses now stays selectable.

**Private addresses count as local.** An OpenAI compatible server at a private
address needs no key. It counts as local in settings, in the picker and in
`spectro doctor`.

**For scripts.** `GET /api/providers` returns the same rows and sends nothing
to any provider. `POST /api/providers/check` starts a check and answers local
callers only.
