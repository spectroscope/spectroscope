# spectroscope 0.15.0

This release adds a third mode, developer, and with it the playbook: a folder
that describes how a team builds, drawn as a graph with a model per step. The
app ships one playbook, spectro, and copies it into a folder with one button. A
run follows the playbook on the app's own state graph engine, runs each step on
the model it names and checks the handover before the next step starts. You can
edit a playbook with the mouse, and Spectrolyzr generates a new project with a
playbook pinned to it. The skills, commands and hooks a playbook carries install
from one list. The settings page shows every provider with its state, and the
model picker greys out providers that need a key or did not answer. A chat on a
local model gets a Local mode switch with its own session count, and the
completion budget and the clamp on tool output follow the model's window. GitHub
Copilot joins as a provider on macOS. A stored session shows its folder as soon
as you select it.

***

## Developer mode and playbooks

**A third mode.** developer sits next to learn and light. It opens everything
learn opens, without the tutorial, and adds a Playbook segment to the sidebar.
The first question of a new window offers it, and the mode switch changes it
later. In learn and light the segment does not exist and its code is never
loaded.

**A playbook is a folder.** Its central file, `playbook.json`, describes a graph
of steps, decisions and ends. A step names who performs it (the chat or a child
agent), its skills, its model choice, whether it stays private, the documents it
takes in and hands on, and whether it waits for your nod. A decision runs a
check and has named outcomes, each with exactly one arrow. Every loop passes a
decision with a round limit, and when the rounds run out the decision takes the
outcome `exhausted`. The file names models through a small set of model choices,
such as `fast` and `strong`, and never by address. A key or an address in the
file is refused with its path, and no step may ask for the extended permission
mode.

**The Playbook segment.** It lists your registered folders and pins one to the
working folder. It draws the graph with outcome labels and loops, and shows one
row per step: each skill marked installed or not, and the state of the provider
behind each model choice. Problems in the file show as findings, one line each.

**The spectro playbook ships with the app.** A first decision sorts the work
into a spike, a bounded change or an architectural change. The architectural
path brainstorms, checks the spec, plans, sets up a worktree and runs a build
loop of implement, review and fix, at most five rounds per task, before a final
review. Its skills are spectropowers, a copy of the superpowers skills with
house rules worked into the text. The folder carries the MIT licence of the
source and a provenance file that lists every edited file.

**Copy with one button.** "Copy the spectro playbook into a folder" writes the
bundled files into a folder you name and registers it. It never overwrites. If
any target file exists, nothing is written and the window lists the files in the
way.

## Running a playbook

**Build by this.** With a playbook pinned to the working folder, "Build by this"
opens a confirmation first. It shows the drawing and one row per step with the
primary model of the step's model choice and the state of its provider.
Fallbacks apply only during the run. The sheet lists every skill with its
source, every command a check may run, word for word with its variables filled
in, and a hash over the playbook, its templates and its skills. Start stays
disabled while the sheet names a reason, for example a missing skill or a
private step on a cloud model. If a file changed after the sheet opened, the run
does not start. No tool of the chat agent can start a run.

**What the playbook brings.** The confirmation also lists the skills, commands,
hooks, agents and workflows the playbook carries, with a hash over them. It
names every item that changed since the install and counts the items that are
not installed.

**A model per step.** A chat step runs as a turn of the main agent. When its
model differs from the chat's, the chat switches to it with the conversation and
switches back when the run ends. A child step runs as a child agent on the
provider of its own model choice, whatever the chat uses. A private step uses
only its primary model and stops to ask when that model does not answer, naming
the provider, model, address and reason. A cheap step tries its primary model
and then its fallbacks in order, and records the walk. A chat step that would
switch to a cloud model after a private step asks first.

**Agent files.** A child step with the role `agent:<name>` runs on the agent
file `agents/<name>.md` of the playbook. Install records that file with its
hash, and that record lets the step run. Without it, or when the file changed
since the install, Start refuses the run.

**Handover checks.** The next step starts only after the previous handover
passed its check. There are five kinds: `sections` (the documents carry their
required sections), `open_items` (no unchecked task is left), `command` (exit
code 0, through the same permission gate as any agent command), `review` (a read
only child on the named model answers with an outcome) and `human` (you answer).
A step's permission is the stricter of the session's and the step's, so a
playbook cannot widen it.

**The lit graph.** The plan tab shows one line per node on the forward path.
Under the drawing, the segment lights the node that is running. When the run
ends, a line names the end it reached as the result, beside the stop reason in
words. A stored session opened from the list shows its latest run the same way,
also after a reload. Stop cancels the running step.

**The sidecar.** Every session that runs a playbook gets a sidecar file under
`~/.spectro/playbook-runs/`. Per step it records the model choice, the provider,
the model and its address, the probe result, the fallback walk, the check
outcomes and your nods, together with the hash of the playbook. It answers which
model served which step. Its strings pass the same redaction as the other
recordings, and the session file itself is unchanged.

A run does not resume after a restart, and it starts only from the window.

## Editing a playbook

**Edit with the mouse.** "Edit" opens an editor on the graph. Add a step, a
decision or an end after the selection, drag from a handle to a box to connect
them, delete with the button or Backspace, and step through the last 50 changes
with Undo and Redo. The layout runs again after every change, so a box cannot be
dragged to a place of its own. The left button selects and connects; the right
and middle buttons pan. A panel edits the selected node, the document types and
the checks. An arrow to a node nobody defined is drawn as a dashed box marked
missing.

**Structure only.** Save writes `playbook.json` with structure only, without
coordinates and with the keys in one fixed order, so a diff shows your change
and nothing else. A file written by hand in another layout is rewritten in that
form on its first save, and the editor says so before you save. A file with
fields the reader does not know stays read only.

**Two refusals.** The server checks the draft a moment after each change. While
any finding exists, the server refuses the save and lists the findings, and the
file on disk stays as it was. The server also refuses the save when the file
changed on disk after you opened it. Your draft stays on screen, and Revert
reads the file again.

## Spectrolyzr

**A new project with its playbook.** Spectrolyzr is a wizard behind the "New
project" tab of the Playbook segment. Pick an archetype: a service with one
`/health` route, a library with one public function, or a command line tool.
Pick TypeScript, Python or Java and a name. Add any of three add-ons: a quality
gate command, a GitHub Actions workflow for CI, and the spectro playbook.

**Why each file is there.** The last step shows the file tree. Select a file to
read its content and one sentence under "Why this file". Generate writes into a
folder you pick and never overwrites. A conflict lists the files in the way, per
folder.

**The same choices give the same files.** Generate is deterministic, byte for
byte. The files come from templates inside the app, nothing is fetched from the
network, and no generated project depends on a spectroscope package.

**The playbook is pinned.** With the spectro playbook add-on, the playbook goes
into a folder of its own, by default a sibling named after the project with
`-playbook` at the end. Generate sets the playbook's test command to the
project's check command, registers the folder and pins it to the new project.

**Tools on your machine.** A generated Java project has no Gradle wrapper yet,
so `gradle test` needs Gradle and Java 21 on your machine. A generated
TypeScript project needs Node 22 or newer.

## Installing what a playbook brings

**One list before anything is written.** The Contents row of the Playbook
segment counts what a folder carries and offers Install and Remove. Install
opens a list with every item, its source path in the folder, its SHA-256 hash,
its state and its reach. Nothing is written before you press Install in that
list. If the folder changed in the meantime, nothing is written and the list
reloads. The list also says how many characters the installed skills and
commands add to the system prompt of every new session.

**Skills and commands.** Skills are copied into `~/.spectro/skills/` as a pack,
each with the playbook's licence and provenance. A command becomes a one file
skill, invoked as `/<playbook id>:<name>`. Every new session sees them. A skill
that a step names and your installation lacks gets an "Install from this
playbook" link in the step table.

**Hooks only when ticked.** Hooks have their own tick, off by default. The list
shows every hook command and the full text of every script. Ticked hooks are
added to your user settings and apply to every new session.

**Agents and workflows are listed.** Install records each agent file with its
hash and copies nothing. Workflow files are listed with their hash and never
run, because the app has no workflow runner.

**Clean installs and removals.** Each pack is built in a staging folder and
moved into place in one step. A second install of the same playbook is refused
with the folder and date of the first. Remove takes out what the install
recorded. It keeps any skill you edited since and any hook entry you changed by
hand, and names them.

## Providers

**Every provider in one table.** The settings page shows one row per provider:
the state in words ("needs a key", "not signed in", "model not downloaded",
"configured, not checked", "answers" or "not answering"), whether a key is
present, the address of a local server, the number of models and whether that
list is live or curated, and the age of the last check. Check tests one provider
and Check all tests every one. A check asks for the model list, never for a
completion, and returns within five seconds, also when a server accepts the
connection and never answers. Local servers are checked when the page opens, and
a provider is checked once after you save its key. Nothing checks on a timer.

**A greyed picker.** The model picker under the message box keeps all nine
providers. A provider that needs a key or did not answer its last check is
greyed out with the reason in the tooltip, and Switch stays disabled while it is
selected. The provider the chat uses now stays selectable.

**Private addresses count as local.** An OpenAI compatible server at a private
address needs no key. It counts as local in settings, in the picker and in
`spectro doctor`.

**For scripts.** `GET /api/providers` returns the same rows and sends nothing to
any provider. `POST /api/providers/check` starts a check and answers local
callers only.

## Local mode

**A switch per chat for a local model.** The gear under the message box gets a
row "Local mode". Switched on, the chat gets its own settings: how many model
sessions it runs at once (the main agent plus its helpers, three by default), a
care paragraph in the system prompt that tells the model it has limited capacity
and asks it to work in small steps and read large files in parts, a preset of
tool groups, and a read share for whole-file reads of 10 percent of the window,
marked in the gear as a proposal. Switched off, the chat behaves as in 0.14.4:
the system prompt and the tool list sent to Anthropic and OpenAI are
byte-identical to 0.14.4.

**Helpers wait for a slot.** A chat whose session count is three runs the main
agent and two helpers. A third helper waits for a free slot of that chat, and
the wait is visible in the chat and the Lab. The descriptions of the spawn tools
tell the model how many helpers run at once. The key `sessionsPerChat` can also
be set in a settings file, with a floor of 2. A changed count applies to the
slots at once: the next helper that asks for one is admitted by the new count.
The tool descriptions follow at the next run.

**Two limits follow the window.** The completion budget sent to a model is at
most the reserve that compaction keeps back, 30 percent of the window by
default, and at most what the window leaves after the estimated input, with a
floor of 512 tokens. On an 8,192 window a request asks for 2,458 tokens instead
of 32,000, and on a 200,000 window nothing changes. An image counts as 4,784
tokens of that input and a PDF page as 7,784, whatever their size in bytes. An
explicit compaction threshold at or above the window gets the floor. The clamp
on tool output follows the window as well: 6,144 characters at 8,192 tokens, the
usual 10,000 from 13,336 tokens up. The reason a blocking hook gives follows the
same rule.

**Settings say when they take effect.** The reach vocabulary gains "next run":
the tool groups, the care paragraph and the read share apply from the next run
of an open session. The reference chapter names the reach of every key.

## Copilot

**GitHub Copilot as a provider, on macOS.** Pick copilot in the model menu and
sign in with GitHub in the app. The device flow shows a code and a link, and you
approve in the browser. The chat then runs through the Copilot SDK against your
own subscription, and the harness keeps its own tool loop. The runtime is the
Copilot CLI installed with Homebrew. When it is missing, the app says so and
names the install line, and `spectro doctor` shows the state. Usage is shown as
the SDK reports it.

## Sessions

**A stored session shows its folder at once.** Selecting a chat in the list
shows its folder in the header chip before any message. A click into the message
box wakes the folder on the server, so Finder, Terminal and "Build code graph"
are available without sending anything and without a model call.
