# spectroscope 0.7.0

Released 2026-08-07, 46 merges after 0.6.1. Two changes carry it. An imported
transcript's pictures are drawn as pictures again, on every surface that shows
one, and entering a fleet opens a bus: one rail, one full agent card per node,
and a fleet bar in place of the app's tabs.

## The pictures come back

The importer used to read the base64 block, count its bytes, write
`[image/png · 31.0 KB]` and drop the bytes on the floor. Every reader downstream
then showed the sentence instead of the thing. 764 of the 5,260 Claude Code
transcripts on the machine these numbers were measured on carry pictures, and
the median one of those carries 1.17 MB of base64, which after `JSON.parse` is
already in memory.

A picture lands in four places, because it means something different in each:
the chat bubble it came with, the tool card that returned it, the trace row's
own image section, and the lab's agent card. The lab's picture panel was never
broken, only unreachable. It was fed by `image_generated` alone, which no
importer emits. Attachments get their own field beside it, "pictures handed
over · n", rather than borrowing the generated slot.

The commonest case of all was the one that did not work: a picture in a
transcript's very first message, which the importer treats as the run's opening
rather than as a message to read content out of. The same hole existed in the
standalone subagent path. A picture in the first message is now read out before
the run opens, so the first message keeps it. And because that opening is also
the session's title, an imported session was being named after four file sizes.

A second pass then went back over the picture path looking for places it still
failed. Eight problems held up, six of them serious:

- A collapsed trace row printed the whole picture. It had no case for the type,
  so it fell back to a compact JSON of the payload: 19.87 MB of base64 across
  one 140-picture file, the largest single row 614,521 characters. A row's
  summary is also its search text, so searching for "deny" matched 15 of 140
  picture rows, not one of which contained the word. The longest such row now
  measures 23 characters.
- The trace's `image` chip found no imported picture at all. A picture answered
  to `other`, so the one gesture a reader makes to find pictures hid all of
  them, and pressing `other` off to clear plumbing rows took every picture with
  it.
- 66% of the pictures live not in the session's own transcript but in the
  separate file each spawned agent writes beside it, and those files are named
  after the agent rather than the session. The lab map read the literal `"main"`,
  so on two thirds of them the agent card showed nothing at all: no pictures, no
  prompt, no reasoning, no answer, no in-flight tool.
- The HTML export dropped 83% of the pictures. A user bubble had rendered its
  attachments since the exporter was written; a tool card never did, and 7,325
  of 8,782 imported pictures sit on a card. Two files among the heaviest twelve
  exported as total losses, 34 and 58 pictures, into a document that looks like
  the app and holds none of them.
- The export preview's 2 MB ceiling was enforced by slicing to 1,200 events,
  which assumed bytes per event were roughly even. One pasted screenshot puts
  275 KB on one event: a 1,742-event file handed the iframe 4.45 MB, 2.2x the
  ceiling. The slice halves until the built document fits, worst case measured
  at four builds, 100 ms, 150 events, 1.69 MB, and the note reports the count
  actually shown instead of a constant.
- A picture pasted into a message queued while a run was still in flight never
  rendered at all: 212 blocks over 177 records, every one a person's own paste.
  145 of those records have their words nowhere else in the file and 17 carry no
  words at all, so that frame was the only trace of the whole message.

Proof over 207 picture-carrying transcripts afterwards: 4,381 frames emitted,
4,381 rendered, zero stranded.

Clicking a picture opens it full size, and the arrow keys walk every picture in
the session, wrapping at both ends. Esc closes. The order is the session's
order, folded once, so a bubble's attachments and a card's pictures interleave
the way they happened. Live: a click on a tool card's picture opens the gallery
at 5 of 11, not at 1.

A picture has three faces. `picture`, `base64` (the string itself, measured and
copyable), and `file`, the `.jsonl` line it lives on with three lines either
side. No server call: the import already holds the file's lines byte for byte
and knows which line produced which event. A record carrying a screenshot is one
JSON line hundreds of thousands of characters long, so the target line is cut
into segments, readable JSON and every base64 blob as a measured absence you can
click to open. Measured live: line 5 of 646, that one record carries 4 pictures,
the marks read 42,264 / 46,112 / 128,900 / 82,756 characters, and the rendered
line contains zero raw base64 runs. The first cut marked only the first blob and
printed the second picture's raw base64 on screen, the exact noise the module
exists to remove, moved 300 characters right. Found by looking, not by a test.

The folder button asked for cannot exist as asked, and the app says so rather
than faking it: the picture is not a file, it is base64 inside the transcript.
Two honest things are offered instead. Open the transcript's folder, with a
tooltip saying which folder it means, and save the picture, after which it
really is a file. The save writes bytes already in the page; no request leaves
the machine. The import dialog also gained an `images` filter chip and an images
count, counted in the same pass as every other fact, including pictures nested
inside a tool result.

What this does not do.

- Nothing reads what is in a picture: no OCR, no caption, no description, no way
  to search a session by what a screenshot shows.
- The arrow-key gallery covers pictures a transcript carried. Generated images
  keep their own separate panel and are not in the walk, and a generated picture
  in the trace is not clickable at all, because its bytes sit behind an endpoint
  the page does not hold.
- There is no zoom and no pan.
- The `file` face exists only for a session imported from a file, so "where does
  this picture live" is an import-only answer. The folder button likewise
  appears only for a session that came from the store.
- The lab agent card shows at most six pictures and does not say how many it
  left out.
- The tool card still prints the stand-in note above the picture. That is
  deliberate and measured, 5,268 of 7,331 cards are picture-only and their
  `output` is what the text feed, the chat search index and the raw/json faces
  read, but it reads as duplication next to a thumbnail.
- All three JSONL exports still drop every picture, because the frame is
  import-only by construction. Only the HTML export holds the bytes.
- There is no endpoint for a picture, which was the right call for an import and
  also means a picture cannot be fetched, linked or shared out of the app.
- The pictures ride in memory for the whole import. Nothing is streamed or
  paged.
- Above 2 MB the export preview is still a slice of the session, honestly
  counted and still not the document you are about to save.
- The `images` chip needs a server that sends the count. An older one reads as
  "did not say" rather than as zero.

## The fleet is a bus

A fleet is a set of agents running as separate processes, watched together.
While one is entered, the six app tabs are replaced by the fleet's own bar:
`[bus] [spectrum] [trace]`, a separator, one tab per agent, and a `[+]` to dock
another node. The quickest way to see it is one of the five recorded scenarios
in the fleets segment, which need no server, no key and no hub. The bar replaces
the app nav entirely while a fleet is entered, and keeps spectrum and trace
because both read across the whole fleet rather than one agent.

The bus docks every node on one rail as a full agent card: id, role, provider, a
restart marker when the node came back with a new epoch, an offline label, the
task line, four chips for what the agent is wired to (disk, shell, mcp, llm,
with a cloud mark when the llm is remote), a gate row when a decision is parked,
its spectral band, tokens in and out, and a stop control. Spawn ancestry orders
the row and draws no tree: a spawned node docks immediately right of its spawner
and carries the parent id, but the nodes stay peers on one line. Traffic is
drawn on the rail, each `agent_message` a mark between the two agents' drops,
coloured by role, the most recent one animating from sender to receiver. Drawing
that traffic needs to know who sent each message and who received it, which the
fleet view used to discard. It keeps that now.

The card head and the card's band are doors. The head opens that agent's own
tab, the band opens the trace already filtered to that agent, and picking an
agent tab pins the trace filter with it, so a per-agent trace is one click and
arrives scoped. An agent tab shows that agent's activity as a feed, one row per
event with a relative timestamp, the type and a preview, dot-coloured across
eleven kinds, scrolled to the live edge. A parked permission gate can still be
answered from anywhere in the fleet: the gate bar sits outside the view chain.

Three things around it were plainly broken and are not now. Pressing `fleets` in
the sidebar changes the screen: the segment was a private state inside the
sidebar, so the press re-rendered one list body and the whole right-hand side
stood still. A pasted `#/fleet/{id}` moves the sidebar with it, and an install
where the tutorial has not unlocked fleets yet puts a reader back in sessions
rather than stranding them in a segment that will not open. And the fleets
segment with nothing entered lands on a lobby rather than on the last session
left standing: the five recorded scenarios, and a count of the fleets already
listed. The lobby's two machine-dependent offers say they cannot work before
they are pressed. Without a hub listening it names the variable to set instead
of printing an address as if it were runnable, and the spawn button is disabled;
with a hub it states plainly that spawning needs `SPECTRO_ALLOW_SPAWN` and that
the server does not report whether it is set. The bus also draws its rail with
no nodes docked. Before, the one surface that explains what this app is returned
a line of placeholder text in place of the rail.

What this does not do.

- You cannot message an agent. Both composers, the one on every bus card and the
  one under the agent feed, are disabled inputs that say why on hover. The wire
  is at version 3 and its control op carries `stop` and `gate` only; the fleet
  endpoints are the roster, a node's events, stop, gate and spawn. There is
  nothing to send a message to, and that server leg is still open.
- The fleet machine room shipped in 0.3.0 is now unreachable. It is still
  mounted under the lab tab, but an entered fleet never reaches the app-tab
  chain, so a view that could be opened in 0.6.1 has no way in at all in this
  release.
- The node-and-edge canvas that used to draw a fleet as a graph is no longer
  reachable either, and is carried along as dead code.
- Chat, graph and text have no fleet face at all any more: an entered fleet
  offers bus, spectrum, trace and one feed per agent.
- The level pill and the translate toggle live on the app nav and disappear
  while a fleet is entered.
- There is no way off the fleet bar itself. Leaving takes the sidebar, and
  switching the segment alone does not leave the fleet.
- A node spawned from the UI is forced to `--permissions readonly`: it can read,
  and it can never write a file or run a command.
- A fleet is still not an object anyone creates. There is no endpoint that makes
  one, and the only path to a live fleet is spawning a node into a hub that is
  already running behind two variables that both default to off, with the server
  answering a uniform 404 for every reason it refuses, so the lobby cannot say
  which one is missing.
- The trace inside a fleet gets no source face and no translation, unlike the
  trace of an own session.
- The rail draws the last 24 messages and nothing says how much was dropped.
- The surface decision is not closed. A third design, the three-column control
  room, exists on a branch and has not been judged against this one, and whether
  the canvas and the machine room should be kept or folded is still open.
- The bus was verified against the recorded review fan-out scenario, not against
  a large live hub fleet, and a card that resizes without its node count
  changing can leave a drop off-centre.

## An imported session says more of what the file holds

The reasoning lens speaks on the row a reader lands on. Measured over 5,119
transcripts, the first row of all 16,579 imported thinking blocks sits directly
under a `turn_start`, and 16,572 of them come off the same line of the file as
that `turn_start`. The panel was drawn on the lower row. Tool calls and answers
now carry a back-pointer to the thinking that was in charge: 41,346 imported
tool-call rows said nothing under the lens before, and 29,043 action rows carry
a chip that jumps to their block. On one imported transcript, 17 reasoning
panels moved onto rows carrying 10,078 characters and 25 back-pointers appeared
where there were none. On a live run the same chip flooded: 75 thinking blocks
emitted 3,213 chips, 3,150 on a streamed chunk, one session showing 747 chips
carrying 2 distinct strings. A chunk that continues an answer says nothing now:
3,213 chips down to 106, with imported counts unmoved at 29,067 either side.

- The structured face prints the thought the source face already had. 83,211 of
  275,254 assistant records carry a thinking block, running 0 to 67,984
  characters, median 296. The words of the answer are named and sized, never
  reprinted, because the chat a few centimetres below already carries them.
  Both faces share one 65,536-character ceiling and both name the two numbers
  when they cut.
- A tool card whose only content block was an image or a tool reference is no
  longer blank: 1,546 imported blank cards, 1,348 image-only and 201 dropping
  the 439 tool names they consisted of. Now 0, and those 201 name their tools.
- The importer reads `toolUseResult`, the tool's own return value, carried by
  44,208 of 496,675 records and read by nothing until now. File reads shed the
  line-number gutter on 3,150 cards, 1,566 state which page they returned, 22
  say they stopped at the token cap, 999 commands keep stdout and stderr apart,
  7,740 edits say where the change landed, and 1,289 task updates draw from and
  to. Rendered through the real importer over 5,137 transcripts: 41,435 cards,
  29,501 with a detail, 13,282 reading differently, and the 11,934 with no
  detail changed by 0 bytes.
- Compaction is visible. 21 boundaries across 17 files produced no frame at all;
  each now names how many turns went away and how long the summary was, and the
  391,308 characters of machine-written summary that rendered as the person's
  own words are out of the chat bubble.
- API failures read as failures. A seven-step backoff over 72 seconds was a
  silent gap in the clock; 150 error frames now exist where there were 0, and
  the 83 outage texts that read as the model's own answer are gone.
- Subagent tokens are counted: 230 usage frames and 842,802 output tokens
  reached the screen with their words and without their cost. On the largest
  fan-out in the store that is 331,967 of 942,677 output tokens, 35% of a
  session total that used to mean only what the main agent spent. An imported
  child names the model it actually ran on, 616 of 643, and the "launched, never
  reported back" badge fell from 393 to 28 once the later task notification was
  read as the child reporting in.
- Skill and MCP attribution were never parsed: 0 chips before, 19,294 skill and
  28,523 MCP chips after, on 136 of 167 session transcripts. Names travel
  verbatim, plugin prefix and all; spectroscope looks nothing up.
- The trace says where the run stood and when it moved. 104 of 167 session files
  stand in more than one directory, 32 on more than one branch, 12 on more than
  one client version, and the app said nothing. There are 3,933 ground rows now,
  167 openings and 3,766 moves, each move carrying only the fields that changed.
- A trace summary keeps a floor beside its chips. Two chips at 1280 px left the
  summary 0 px wide on 18,190 anchored lines; the text keeps a 10ch floor and
  each chip a 22ch ceiling, which is 135 px of summary instead of 0.

A standalone subagent transcript imports as a session. There are 4,687 of them
in this store against 167 session files, and every one imported to nothing: a
110-line file arrived as "110 lines, 1 frames, 110 lines carry no conversation".
Across those files, frames went from 4,684 to 481,515 and lines nothing was read
from fell from 314,022 to 9,976. The gate reads the file's shape, never its
name, so a renamed or copied file is still read for what it holds. The bar says
what such a file is instead of blaming it, and the old sentence stopped calling
somebody else's lines empty. Both the header's context ring and the run's token
line were wrong on these files, because the reducer spelled the run's own agent
`main` and no standalone transcript contains that word.

The import dialog is a room now: full screen, only the row list scrolling, a
two-axis filter, and a statistics line over the current selection with "n not
read yet" beside the totals, because a total that silently omits forty rows is
not a total. Facts arrive per visible row on their own endpoint, and reading
only a prefix would have reported a different session: across the 60 largest
transcripts the last previously-unseen model first speaks at a median 27% of the
way in, at 94% at the ninetieth percentile, and in one file on the final line.
The subagent count was blind to the agents that matter most, globbing 718
sidecar files while 4,013 more sat under the workflow folders, so the sessions
with the biggest fan-out answered "subagents: 0". The listing still answers in
151 ms for 300 rows; 24 rows of facts over 296.87 MiB cost 407 to 864 ms cold
and 3 to 5 ms warm. Two defects were caught on the way: the first cut of the
full-screen rule clipped its own Load button, and a path holding a NUL byte
answered 500 with Spring's default error body, telling a prober that path was
different from the ones that answer 404, and in a batch abandoning every row
queued behind it.

An imported session's agents arrive beside it. A session transcript holds only
its own start, measured over the 25 largest here as 71,329 records and zero
sidechain, so every word the agents said lives in sibling files the importer
never opened. The work panel lists them, each openable as a session in its own
right. The join is read off the disk, never guessed, and it stays a listing:
41 agents across 5 runs in 4 ms, against 10 ms to read one 231 KB agent file.
Where the task's own claim and the files disagree, both are shown and neither is
corrected. A button asks the configured model what a session was about and
writes one line per row, kept on disk keyed by each file's size and modification
time; a second press cost 12 ms and wrote nothing, a restart gave the same text,
and a transcript that had grown was asked again. The gist is bounded on purpose:
1,200 characters of the opening prompt travel, the answer is capped at 120
tokens and 12 words, requests are serial, one press covers at most 60 sessions,
and the instruction tells the model to say "unclear from the opening prompt"
rather than invent a subject. An import still writes nothing to disk and the bar
still says so; the gists are the one exception, written only on a press.

What this does not do.

- The compaction summary is now readable nowhere in the app. It was a lie about
  who spoke in the bubble, and every face of the trace hangs off a row, so
  391,308 characters that were readable in the wrong place are readable only in
  the file. Giving it a carrier is an open call, not an oversight.
- 28 trace rows still name a model called `<synthetic>`. Those records carry the
  file's own `isApiErrorMessage:false` and say "No response requested.", so the
  filter follows the file.
- The agents beside a session are a listing, not a join. Opening one replaces
  the view, and the parent's trace, spectrum and graph gain no child rows,
  because a real join would mean reading four thousand files to open one
  session.
- The listing appears only where the transcript records a run id for the agents
  a session started. The 718 agent files that sit directly beside a session are
  served by the endpoint, and no screen lists them.
- The sidecar folder is derived from the transcript's location, so one session
  split across two project directories, with 64 agent files on the other side,
  answers "none", indistinguishable from a session that spawned nothing. It sits
  below the listing cap today.
- The dialog lists the 300 newest of 5,146, and the filter, the statistics line
  and the gist buttons see only that window.
- A rejected batch of facts strands its rows: the sweep that asks again fires
  only when the filter goes from inactive to active. This is known and not fixed
  here.
- A pasted or file-picked transcript has no store path, so it gets no facts row,
  no gist and no sidecar agents.
- The facts cache dies with the server process.
- The gist needs a configured provider with a key and spends one API call per
  session.
- All of this reads Claude Code transcripts. The VS Code / Copilot importer and
  spectroscope's own format gain none of it.
- The `attributionAgent` chip is deliberately not drawn, appearing on 0 of the
  167 session transcripts.
- The reasoning lens shows the model's own recorded self-report next to what it
  then did. It is not a window into the weights.

## Back and forward, in a window with no address bar

Back and forward buttons sit at the left of the tab bar, with ⌘← and ⌘→ bound to
the same actions and listed in the keymap. A greyed-out button means there is
nowhere to go: the app stamps its own index into each history entry it writes,
because `history.length` counts entries from before the app loaded and the DOM
reports no forward availability at all. Forward never lit in the first cut,
because only pushes were stamped and the entry the app boots on is written with
a replace.

A transcript in the session store has an address now, and the tab survives in
it, so Back walks from a workflow's agent to the session that named it. Touching
any tab on an imported transcript used to overwrite the address with `#/`, and
because that write replaces the entry Back returns to, the deep link was gone
permanently. The duplicated address rule is gone with it: one writer, one place.

`SPECTRO_HUB_PORT` and `SPECTRO_ALLOW_SPAWN` are settable in a new fleet section
of settings, alongside the sections that were already there, and the screen
states that the value is not in force until a restart. Exactly two names may be
written into `~/.spectro/.env` by the settings endpoint, and only those two are
read back out of that file into the server's own property resolution. That
allowlist is the security boundary: the same file already holds the provider
keys the onboarding screen writes, and lifting whatever else it contains into
Spring would put secrets into every property resolution and obey any line an
operator had pasted. Arming spawn asks for confirmation in words, and a setting
already held by a real environment variable greys its box, because the
environment wins for the life of the process.

The right panel no longer reopens on Work at every launch. Measured against
0.6.1 with the browser's saved state cleared, the stored panel tab came back set
to Work, and a reader who chose Files had that overwritten on the next reload.
A start lands on your own last tab and open state; a first-ever start opens
closed on agents. The trace's Compact face is retired: five faces become four,
and a stored Compact opens on Wire.

What this does not do.

- The view-state grammar (a trace row, a spectrum window, a filter set) is
  parsed, formatted and test-pinned, and nothing consumes it. No surface
  publishes its state into the address or reads it back, so you cannot produce
  such a link from the app and pasting one changes nothing. Wiring a surface to
  that grammar is the next step and is not done here.
- Fleet addresses carry no tab and no view state.
- Scenarios, pasted transcript bodies and files opened from disk still have no
  address at all.
- The back and forward buttons are absent in fleet mode, where the fleet bar
  replaces the tab nav. The shortcuts still work, but nothing on screen shows
  the state.
- ⌘← and ⌘→ are suppressed while the focus is in a text field.
- The depth counter only knows entries this app wrote, so at index 0 the app's
  button and the browser's own button disagree by design.
- Both fleet settings need a server restart and nothing restarts it for you.
- A reader whose stored panel tab was written to Work by the bug lands on Work
  once more after upgrading, because the change deliberately does not rewrite a
  stored preference to guess otherwise.

## The spectrum's zoom stops behaving like a widget

The overview strip and the zoom control are drawn on any stream that has a lane.
They used to appear only once a lane could not draw half of what it carried, so
on the 123-event session that turned this up, everything fit and nothing
appeared. A one-event run gets a strip with one mark and a window over all of
it. The `−` and `+` buttons are gone; the one that puts the whole span back on
screen remains, labelled `all`, because a stepless zoom needs a way home more
than a stepped one does. The keyboard did not lose the steps: `+` and `-` zoom,
`0` fits, shift and arrows pan a quarter window, `[` and `]` page across empty
axis.

ctrl+wheel, and a trackpad pinch, now zoom while the pointer is over the
overview strip. Before, the handler lived inside the lane component, so the one
surface that draws the window was the one surface where the gesture did nothing.
Walked on the built server: ctrl+wheel over the strip took the window from the
whole span down to a 350 px window anchored where the pointer stood, and back
out. A plain vertical wheel is still left alone, so the page scrolls.

The window's two ends on the strip can be grabbed and dragged, which sets a span
directly instead of zooming around a point, and the other end stays put. Nothing
is drawn on the ends: the window box stays exactly as wide as the window it
stands for, down to a hairline at the zoom floor, and the extra room is a
6-pixel hit zone. Nothing but the cursor says an end can be grabbed. Dragging
one end past the other does not turn the window inside out, a window under 18
pixels has no ends at all and is all body, and the grip is held for the length
of a drag, so a fast drag that outruns its own grab zone keeps the end.

A collapse button also joined the sidebar's brand row, because the header's
burger is the first thing a narrow window takes away, so the one control that
gives room back was reachable only once you already had room. At 720 px, pressing
it takes the sidebar away and the strip underneath gains 322 px.

What this does not do.

- The grabbable ends are invisible by design and the only signal is the mouse
  cursor, so on a touch screen there is nothing to discover and a 6-pixel zone
  is a mouse-sized target.
- There is no keyboard way to drag an end.
- The strip is still `role="img"` labelled "drag to move the window": a screen
  reader is told nothing about the ends, and the surface is not exposed as a
  control.
- Nothing in the interface says the ends can be grabbed. The hint line was not
  updated, and the user guide's spectrum chapter does not document the zoom at
  all, so that one line is the whole documentation of the instrument.
- Zooming still needs a modifier, which is correct and is also the reason a
  reader concluded the zoom was broken.
- The ends are on the overview strip only.
- The narrow window now carries two controls that do the same thing.
- A pan that is documented to keep the window's width returns
  0.10000002384185791 where it should return 0.1. It is invisible on screen, it
  still contradicts what the code promises, and it is not fixed here.
- The three walks recorded above were done by hand against a built server.
  Nothing in the suite drives a real pointer.

## Three tool chips, and a command that reads a step per line

The trace's chip row had one `tool` chip and everything a tool did sat under it.
Over the 1,961 transcripts on the measuring machine: 71,730 tool calls, 9,367 of
them over MCP, with no way to ask for them. There are three chips now, `tool`,
`workflow` and `mcp`, and the rule is the tool's wire name. The busiest single
thing behind `mcp` is the browser, 4,572 `javascript_tool` calls and 2,547
`computer` calls, all previously indistinguishable from the 42,070 Bash calls
beside them. A tool result inherits the chip of the call it answers, because a
result keeps only the id of its call, and a result whose call is not in the
stream falls back to plain `tool` and stays on screen. The first cut knew only
the `Workflow` tool and missed `Monitor`, 53 calls against 197, roughly one
background launch in five. Neither new chip gets a colour of its own, and both
read the same word in German and English, because the words are the wire
vocabulary. The index that makes the inheritance possible is built only while
the three chips disagree or while a tool result row is open, so an unfiltered
live trace with nothing open pays nothing.

A chained shell command breaks before every top-level `&&` and `||`. Of 41,960
Bash commands in that corpus, 25,009 are chained, and until now each was one
paragraph of shell wrapped at whatever column the card happened to be. `||`
breaks too, though only `&&` was asked for: they are the same joint, and the
request's own example ended with one. This is not a `split("&&")`, and the corpus
is the reason: 430 of those chained commands contain no real operator at all,
every apparent one sitting inside quotes, a substitution or a heredoc body.
Counting partial cases, a naive split would have broken 1,220 commands in a place
the shell does not see a joint, showing a reader a command that is not the
command that ran. The breaker walks the string once, tracking quote mode,
escapes, paren depth and heredoc terminators, and 3,744 of the measured commands
carry a heredoc. It adds newlines and nothing else: strip them back out of all
41,960 outputs and you get the input back, byte for byte. The break is display
only, drawn by the two renderers that draw a command block, which reaches the
chat tool card, the trace's open row, the lab's tool-call panel and the HTML
export.

What this does not do.

- The permission gate does not get the line breaks. A pending Bash command in
  the gate bar is printed as JSON input, so it is still one long line at the
  moment you have to decide about it.
- Only the HTML export carries the breaks. Markdown, JSONL, the raw and json
  faces and the search index all read the recorded bytes.
- The rule knows `&&`, `||` and `;`, so a long pipeline is still one line and a
  backgrounding `&` never breaks.
- Three chips is not a catalogue. Two very different MCP tools share one chip
  and there is still no way to ask for Bash alone.
- The `workflow` chip matches exact names, so the next launcher added upstream
  will be missed the same way `Monitor` was.
- The chips do not reach the work a background task did, only its launch and its
  receipt.
- On a live stream past 5,000 rows the trace window can evict a call while its
  result is still on screen, so that result falls back to `tool` and disappears
  under an `mcp`-only filter. The gap is measured at 3 frames at p90, on a row
  the window is about to drop anyway, but it is a real hole.

## The folders a session left on disk, and an install with no terminal

An imported transcript carries up to three buttons for its own directories:
`folder`, the project directory the transcript sits in; `workflows`, the journals
its runs wrote; and `scratchpad`, the temp directory those runs used. The app
read all of it and could show you none of it, because the store is under a
dot-folder Finder hides and the scratchpad is under a path nobody would guess.
The buttons sit beside export and translate in the chat, and beside the Langfuse
link in the trace, as one component mounted twice. A button is drawn only for a
directory the server has just stat'd, asked per session rather than remembered,
because a scratchpad appears when a run makes one and a temp sweep takes it away.
Measured against this store: 173 session transcripts, all 173 with a project
folder, 73 with a workflows folder, 4 with a scratchpad still on disk. Hovering
shows the absolute path, which is also how you copy it out for a terminal.

The path is never the caller's. The request names a transcript and a kind, and
the server derives the directory through the same fence the read endpoints wear.
The spawn is an argument list, never a command string, and the program comes from
the operating system, never from the request. Measured before shipping: a rebound
Host gets 404, the encoded `/%61pi/` form gets 404, and both a traversal and an
unknown kind answer `missing` with nothing opened. One measurement changed the
code before it shipped: the scratchpad is under `/tmp`, not under
`java.io.tmpdir`, which on macOS is a per-process directory. The first version
would have offered a button for a directory that has never existed.

The Files tab also stops blaming the server. "no terminal available, the server
refused the connection" was true and useless: the `spectro-pty` helper rides the
signed desktop bundle and is not in the jar, so a plain `java -jar` has no
terminal by construction. The config now reports the shell as ready, off or
unavailable, and the head says `no terminal` with the reason in its title. A
server that does not report the field at all is read as ready, so an older server
behaves exactly as before.

What this does not do.

- There is no button for the directory the session actually ran in. `folder`
  opens the transcript's project directory inside the store, not the repository
  the agent worked in, and the importer already reads that path without using it
  here (104 of 167 session transcripts carry more than one).
- Only a transcript opened from the store gets buttons, so a pasted file, a file
  picked from disk, a live run and spectroscope's own archived sessions show
  nothing at all.
- The scratchpad location is a hard-coded layout with the uid read off the home
  directory, so on Windows there is never a scratchpad button, and if the
  harness moves its scratchpads the button stops appearing with nothing saying
  why.
- The folder opens on the machine running the server, which the fence keeps to
  the machine you are at, though a tunnel presenting itself as loopback would
  open a window in front of somebody else.
- A failed press says "did not open" and not which of the two failures it was.
- `xdg-open` is assumed for anything that is not macOS or Windows, so a headless
  Linux box answers unsupported.
- No automated test proves a folder was ever opened. The suite pins the five
  refusals, and the successful press was verified by hand once.
- The `folder` button in the image viewer looks the same and behaves
  differently: it does not ask first and a failure is silent.
- The terminal is still absent from the plain jar. Nothing here changed that.
- The `no terminal` label with both of its explanations is an inline
  German/English ternary rather than an i18n key, unlike the folder labels
  beside it. That debt is still open.

## The build, the samples and the published POM

Every module already compiled for Java 21, and a class file from this machine's
JDK 25 reads major 65, which is Java 21. That governs the artifact and never
governed which JVM runs the tests, and that was open: the developer machine has
only 25, CI pins Temurin 21, the build container ships 21. The five modules now
declare a toolchain with the foojay resolver, so Gradle finds a Java 21 JDK or
downloads one. Measured after: the test JVM reports 21.0.12 (Eclipse Adoptium) on
a machine whose only installed java is 25.0.2. The cost is a one-time download of
roughly 200 MB where no 21 exists.

One test pinned a macOS-only fact as a universal one, asserting both that the
scratchpad root is `/tmp` and that it is not `java.io.tmpdir`. On Linux those are
the same path, so the negative could never hold. The break reached the shared
branch and stood for about eleven minutes, and the merge that caused it was
forced through while its own run was already failing. It never reached a release.

Six of the eight sample directories are Gradle projects and none of them shipped
a wrapper, while every README opened with `gradle build`. The first documented
command of the first example failed on any machine without a system-wide Gradle,
which is exactly the machine a sample is for. Each now carries `gradlew`,
`gradlew.bat` and a 48,462-byte wrapper jar pinned to Gradle 9.6.1, 361,482 bytes
across the six. Proven the way it will be met: one sample copied into an empty
directory, `gradle` not on PATH, `./gradlew build` returns 0.

`spectro-core` declared jackson-databind 2.17.2 while its own dependency,
anthropic-java 2.34.0, brings the 2.18.2 family. Gradle resolves highest-wins, so
every build here passed and nothing in this repo ever saw it. What we publish is
the POM, and the POM contradicted the dependency beside it. Measured in the jars:
`ParserMinimalBase(StreamReadConstraints)` exists in jackson-core 2.18.2 and not
in 2.17.2, so the classpath that crashes is a 2.18 databind beside a 2.17 core.
The first fix proposed here was to pin jackson-databind, which would have widened
the gap. It was wrong, and it was corrected before anything shipped. `spectro-core`
imports the Jackson BOM now instead of naming one artifact's version, declared
`api` so the constraint travels into the published POM; `spectro-mcp-notes` does
the same. A number pins one artifact, and Jackson is a family whose halves call
each other's constructors. This reaches consumers only with this release: 0.6.1
on Maven Central still declares 2.17.2, and Central is append-only, so anyone
hitting the crash today still has to pin Jackson themselves.

The release playbook now runs `brew style` on the working copy before the push,
then updates, then audits. `brew audit` takes a name, not a path, and answers it
from Homebrew's own clone, which only moves on `brew update`: run before the push
it reads the previous release's cask and reports success. Measured hours after
0.6.0 shipped, that clone still said 0.5.0 while the audit was being quoted as
proof 0.6.0 was sound. The style pass caught a real offence on a cask published
four times over, a missing `depends_on macos:` whose autocorrection had sat
uncommitted since 2026-07-31.

Four collections of agent skills, the instruction folders an agent can load at
run time, contribute their skills directories, vendored verbatim at a named
commit: 57 skills, each pack keeping its upstream LICENSE and a provenance record
naming repo, commit and date. Only the skills directory of each repo came across,
which is the part that is a skill; the rest of each product, a CLI, a stack,
screenshots, was left behind. One pack carries 54 fonts under 27 SIL OFL notices,
which were checked rather than assumed, because a font's licence is not covered
by a repository's MIT statement. The catalogue is carried and deliberately not
seeded: the seeded skills folder is appended to every run's system prompt, and 57
foreign skills in that context, one of them colliding by name with our own, is
not a default. It is groundwork, not a feature. There is no install verb, no
endpoint and no button; outside its own folder the only reference to it anywhere
in the tree is the line that copies it into the server jar, so today the files
are reachable by unzipping the jar and by nothing else. Calling it a marketplace
would be false. It adds 391 files in 141 directories, 8,703,566 bytes, and it is
a `processResources` entry, so it rides the server jar every user downloads:
measured at the commit, 50 MB to 53 MB for something with no verb behind it yet.

The repository carries a local CI stack under `ci/`, and it had been writing into
the working copy it was mounted on. `npm ci` installed Linux binaries over
`node_modules`, so the next gate on the Mac died on a missing darwin rollup
module, and the PTY helper build put an ELF over the Mach-O, so the host gate
failed six PTY tests with no visible cause. Three container-side volumes now sit
over the paths the container writes; any new path a container job writes has to
be added by hand or the working copy is damaged the same way. That stack also
stopped reporting a pass it could not show: build #5 was green while its own log
said "None of the test reports contained any result", because a declarative
`post` block runs in the job's workspace rather than the mounted repo, and
`allowEmptyResults: true` let it pass in silence. Both flags are off and both
steps run inside the repo.

What this does not do.

- The samples still print a bare `gradle run` in three READMEs where an
  environment prefix precedes it, and four still name 0.4.1 coordinates in prose
  while every sample build file pins 0.6.1. The fleet-across-processes sample
  goes further: it instructs you to download `spectro-server-0.4.1.jar` and
  `spectro-0.4.1.zip`, release assets two versions old, in five places.
- A copied sample resolves released artifacts, so it gets the Jackson
  declaration of the version it names, not the corrected one in this tree.
- `./gradlew` still needs a JVM present to start Gradle at all. The toolchain
  removes the need for the right JVM, not for any JVM.
- No workflow runs the gate on macOS, so macOS-only breakage is still caught
  only by a human on a Mac, and the toolchain says nothing about the Node
  toolchain or the C compiler for the PTY helper, which is still built outside
  Gradle.
- The tap ordering is documentation, not enforcement.
- The build stack reaches nobody who does not clone the repository and run
  Docker. Sonar and Dependency-Track are written into it and were never started,
  because Docker Desktop had 7.7 GiB of the host's 48 on the measuring day and
  `up all` needs 16.
- Nothing in that stack can sign the DMG, because codesign and notarytool need
  the host and its keychain.
- The gate the stack runs was found to be non-portable as written, since the PTY
  helper is C and built outside Gradle, so a fresh container failed six tests
  until the pipeline built it. The pipeline builds it now. The underlying fact,
  that `./gradlew test` alone does not produce a complete gate, is unchanged.
