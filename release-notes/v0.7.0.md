# spectroscope 0.7.0

Released 2026-08-07, 47 merges after 0.6.1. Two changes carry it. An imported
transcript's pictures are drawn as pictures again, on every surface that shows
one, and entering a fleet opens a bus: one rail, one full agent card per node,
and a fleet bar in place of the app's tabs. Behind those, an imported session
gives up a great deal more of what its file already held, and the settings page
grew a skill catalogue you can install from without a network.

## The pictures come back

The importer used to read the base64 block, count its bytes, write
`[image/png · 31.0 KB]` and drop the bytes on the floor. Every reader downstream
then showed the sentence instead of the thing. On the machine these numbers come
from, 764 of 5,260 Claude Code transcripts carry pictures, and after `JSON.parse`
those bytes are already in memory, so they travel on the frame and there is no
new endpoint.

A picture lands in four places, because it means something different in each: the
chat bubble it came with, the tool card that returned it, the trace row's own
image section, and the lab's agent card. The lab's picture panel was never
broken, only unreachable: it was fed by `image_generated` alone, which no
importer emits.

The commonest case of all was the one that did not work: a picture in a
transcript's very first message, which the importer treats as the run's opening
rather than as a message to read content out of. Since that opening is also the
session's title, an imported session had been named after four file sizes.

A second pass went looking for places the picture path still failed, and eight
problems held up. A collapsed trace row printed the whole picture, because it had
no case for the type and fell back to a compact JSON of the payload, 19.87 MB of
base64 across one file, and since a row's summary is also its search text, Cmd+F
was matching base64 noise. The trace's `image` chip found no imported picture at
all. The lab map read the literal `"main"`, so on the two thirds of pictures that
live in a spawned agent's own sidecar file the card showed nothing: no picture,
no prompt, no reasoning, no answer. The HTML export dropped 83% of pictures,
every one that sat on a tool card. And a picture pasted into a message queued
while a run was in flight never rendered at all, though for 17 of those records
the picture was the only trace of the message.

Proof over 207 picture-carrying transcripts: 4,381 frames emitted, 4,381
rendered, zero stranded.

Clicking a picture opens it full size; the arrow keys walk every picture in the
session, wrapping at both ends, in the session's own order. Esc closes. A
picture also has three faces: `picture`, `base64` (the string itself, measured
and copyable) and `file`, the `.jsonl` line it lives on with three lines either
side. There is no server call: the import already holds the file's lines byte for byte
and knows which line produced which event. A record carrying a screenshot is one
JSON line hundreds of thousands of characters long, so the target line is cut
into segments: readable JSON, and every base64 blob as a measured absence you can
click to open.

The folder button asked for cannot exist as asked, and the app says so instead of
faking it: the picture is not a file, it is base64 inside the transcript. Two
honest things are offered instead. Open the transcript's folder, or save the
picture, after which it really is a file. The save writes bytes already in the
page, so no request leaves the machine.

**What this does not do.** Nothing reads what is in a picture: no OCR, no
caption, no search by what a screenshot shows, and no zoom or pan in the viewer.
Generated images keep their own panel and are not in the arrow-key walk. The
`file` face and the folder button exist only for a session opened from the store.
All three JSONL exports still drop every picture, because the frame is
import-only by construction; only the HTML export holds the bytes. And there is
still no endpoint for a picture, so one cannot be linked or shared out of the
app.

## The fleet is a bus

A fleet is a set of agents running as separate processes, watched together. While
one is entered, the six app tabs are replaced by the fleet's own bar:
`[bus] [spectrum] [trace]`, a separator, one tab per agent, and a `[+]` to dock
another node. Spectrum and trace stay because both read across the whole fleet
rather than one agent. The quickest way to see it is one of the five recorded
scenarios in the fleets segment, which need no server, no key and no hub.

The bus docks every node on one rail as a full agent card: id, role, provider, a
restart marker when the node came back with a new epoch, an offline label, the
task line, four chips for what the agent is wired to (disk, shell, mcp, llm, with
a cloud mark when the llm is remote), a gate row when a decision is parked, its
spectral band, tokens in and out, and a stop control. Spawn ancestry orders the
row and draws no tree. A spawned node docks immediately right of its spawner and
carries the parent id, but the nodes stay peers on one line. Traffic is drawn on
the rail, each `agent_message` a mark between the two agents' drops, coloured by
role, the most recent one animating from sender to receiver. Drawing that needs
to know who sent each message and who received it, which the fleet view used to
discard on the way in. It keeps that now.

The card head and the card's band are doors: the head opens that agent's own tab,
the band opens the trace already filtered to that agent, and picking an agent tab
pins the trace filter with it. An agent tab shows that agent's activity as a
feed, one row per event with a relative timestamp, the type and a preview,
dot-coloured across eleven kinds, scrolled to the live edge. A parked permission
gate can still be answered from anywhere in the fleet, because the gate bar sits
outside the view chain.

Three things around it were plainly broken and are not now. Pressing `fleets` in
the sidebar changes the screen. The segment was private state inside the
sidebar, so the press re-rendered one list body while the whole right-hand side
stood still. A pasted `#/fleet/{id}` moves the sidebar with it. And the fleets
segment with nothing entered lands on a lobby rather than on the last session
left standing, with the lobby's two machine-dependent offers saying they cannot
work before they are pressed rather than after.

**What this does not do.** You cannot message an agent: both composers are
disabled inputs that say why on hover, because the wire's control op carries
`stop` and `gate` only, and that server leg is the open one. The fleet machine
room from 0.3.0 and the node-and-edge canvas are both unreachable now. They are
still mounted, but an entered fleet never reaches the app-tab chain, so a view you
could open in 0.6.1 has no way in at all. Chat, graph and text have no fleet face
any more, and there is no way off the fleet bar itself; leaving takes the
sidebar. A node spawned from the UI is forced to `--permissions readonly`. And a
fleet is still not an object anyone creates: no endpoint makes one, the only path
is spawning into a hub already running behind two variables that both default to
off, and the server answers a uniform 404 for every reason it refuses. The
surface decision is not closed either. A third design, the three-column control
room, exists on a branch and has not been judged against this one.

## An imported session says more of what the file holds

The reasoning lens now speaks on the row a reader lands on. Measured over 5,119
transcripts, the first row of all 16,579 imported thinking blocks sits directly
under a `turn_start`, and the panel was being drawn on the lower row. Tool calls
and answers carry a back-pointer to the thinking that was in charge, which
reaches 29,043 action rows that said nothing under the lens before.

- Tool results are read. The importer reads `toolUseResult`, the tool's own
  return value, carried by 44,208 records and read by nothing until now. File
  reads shed the line-number gutter, commands keep stdout and stderr apart, edits
  say where the change landed, and task updates draw from and to. Over 5,137
  transcripts, 29,501 of 41,435 cards gained a detail and the rest changed by 0
  bytes.
- A blank tool card is no longer blank: 1,546 imported cards whose only content block
  was an image or a tool reference rendered as nothing.
- Compaction is visible, naming how many turns went away and how long the summary
  was, and the machine-written summary that rendered as the person's own words is
  out of the chat bubble. API failures read as failures too: a seven-step backoff over 72 seconds was a silent gap in the clock, and 83 outage
  texts read as the model's own answer.
- Subagent tokens are counted: 842,802 output tokens reached the screen with
  their words and without their cost; on the largest fan-out in the store that is
  35% of the session total. An imported child also names the model it ran on, and
  the "launched, never reported back" badge fell from 393 to 28 once the later
  task notification was read as the child reporting in.
- Skill and MCP attribution was never parsed: 0 chips before, 47,817 after.
  Names travel verbatim, plugin prefix and all; spectroscope looks nothing up.
- The trace says where the run stood and when it moved. 104 of 167 session
  files stand in more than one directory and 32 on more than one branch, and the
  app said nothing.

A standalone subagent transcript imports as a session. There are 4,687 of them in
this store against 167 session files, and every one imported to nothing. A
110-line file arrived as "110 lines, 1 frames, 110 lines carry no conversation".
The gate reads the file's shape, never its name, so a renamed or copied file is
still read for what it holds, and the bar says what such a file is instead of
blaming it.

The import dialog is a room now: full screen, only the row list scrolling, a
two-axis filter, and a statistics line over the current selection with "n not
read yet" beside the totals, because a total that silently omits forty rows is
not a total. Facts arrive per visible row on their own endpoint, and reading only
a prefix would have reported a different session. Across the 60 largest
transcripts the last previously-unseen model first speaks at a median 27% of the
way in, and in one file on the final line. The subagent count had been blind to
the agents that matter most, counting 718 sidecar files while 4,013 more sat
under the workflow folders, so the sessions with the biggest fan-out answered
"subagents: 0".

An imported session's agents arrive beside it. A session transcript holds only
its own start, so every word the agents said lives in sibling files the importer
never opened. The work panel lists them, each openable as a session in its own
right, joined off the disk rather than guessed, and it stays a listing: 41 agents
across 5 runs in 4 ms. Where the task's own claim and the files disagree, both
are shown and neither is corrected. A button also asks the configured model what
a session was about and writes one line per row, kept on disk keyed by each
file's size and modification time; the answer is capped at 120 tokens and 12
words, and the instruction tells the model to say "unclear from the opening
prompt" rather than invent a subject. An import still writes nothing to disk and
the bar still says so. The gists are the one exception, written only on a press.

**What this does not do.** The compaction summary is now readable nowhere in
the app: it was a lie about who spoke in the bubble, and every face of the trace
hangs off a row. Giving it a carrier is an open call, not an oversight. The
agents beside a session are a listing, not a join. Opening one replaces the
view, and the parent's trace, spectrum and graph gain no child rows, because a
real join would mean reading four thousand files to open one session. The sidecar
folder is derived from the transcript's location, so a session split across two
project directories answers "none", indistinguishable from one that spawned
nothing. The dialog lists the 300 newest of 5,146, and the filter, the statistics
line and the gist buttons see only that window. A pasted or file-picked
transcript has no store path, so it gets no facts row, no gist and no sidecar
agents, and the gist needs a configured provider with a key and spends one API
call per session. All of this reads Claude Code transcripts; the VS Code /
Copilot importer and spectroscope's own format gain none of it. And the reasoning
lens shows the model's own recorded self-report next to what it then did. It is
not a window into the weights.

## Install a skill without a terminal

Four collections of agent skills, the instruction folders an agent can load at run
time, are vendored verbatim at a named commit and ride inside the artifact:
57 skills, each pack keeping its upstream LICENSE and a provenance record naming
repo, commit and date. One pack carries 54 fonts under 27 SIL OFL notices, which
were checked rather than assumed, because a font's licence is not covered by a
repository's MIT statement.

The settings page lists them beside the skills you already have, with the pack
and its licence on the button before you press it, and one press copies a skill
into `~/.spectro/skills`. Nothing is fetched, so this works with the network
unplugged; nothing is executed, and nothing arrives with an execute bit, even
though thirteen catalogue files carry one upstream. The pack's `LICENSE` and
`PROVENANCE.json` travel with the copy, and an install whose licence cannot be
read is refused rather than made.

An installed skill is namespaced: it lands at `<root>/<pack>/<skill>` and the
agent calls it `<pack>:<skill>`, the convention Claude Code already uses for
plugin skills. That is what lets somebody else's `brainstorming` sit beside one
you wrote instead of overwriting it. Skills installed before this release sit at
the top level, keep their bare names and are untouched.

Three of the four skills this project seeded into a fresh home (`brainstorming`,
`test-driven-development` and `writing-plans`) are gone from the seed set,
because the catalogue carries versions three to five times longer and only a
skill's name and description ever enter the system prompt. `verification` stays;
it has no counterpart. An existing installation keeps whatever it already has:
nothing on disk is removed.

One parsing bug had to go first, or several of these would have installed
unusable: the frontmatter reader split at the first colon, so a `description: |`
block scalar yielded the string `|` and the skill reached the model as
`- humanizer: |`, which is unfindable.

**What this does not do.** Nothing is installed from a live git remote, and there
is no update check: the catalogue is pinned to the commit it was vendored at, and
a copy that quietly moves under a run nobody re-read is worse than one that does
not move. Re-installing is refused rather than treated as a no-op, because the
folder on disk may carry your edits and its off switch. The catalogue adds
roughly 8.7 MB to the server jar whether or not you install anything from it. And
we publish nothing of our own to it; this is a client, not a registry.

## Back and forward, in a window with no address bar

Back and forward buttons sit at the left of the tab bar, with ⌘← and ⌘→ bound to
the same actions and listed in the keymap. A greyed-out button means there is
nowhere to go: the app stamps its own index into each history entry it writes,
because `history.length` counts entries from before the app loaded and the DOM
reports no forward availability at all.

A transcript in the session store has an address now, and the tab survives in it,
so Back walks from a workflow's agent to the session that named it. Touching any
tab on an imported transcript used to overwrite the address with `#/`, and
because that write replaces the entry Back returns to, the deep link was gone
permanently. The duplicated address rule went with it: one writer, one place.

`SPECTRO_HUB_PORT` and `SPECTRO_ALLOW_SPAWN` are settable in a new fleet section
of settings, which states that the value is not in force until a restart. Exactly
two names may be written into `~/.spectro/.env` by the settings endpoint, and
only those two are read back out of it. That allowlist is the security boundary:
the same file holds the provider keys the onboarding screen writes, and lifting
whatever else it contains into Spring would put secrets into every property
resolution and obey any line an operator had pasted. Arming spawn asks for
confirmation in words, and a setting already held by a real environment variable
greys its box.

The right panel no longer reopens on Work at every launch. A start lands on your
own last tab and open state; a first-ever start opens closed on agents. The
trace's Compact face is retired. Five faces become four, and a stored Compact
opens on Wire.

**What this does not do.** The view-state grammar (a trace row, a spectrum window,
a filter set) is parsed, formatted and test-pinned, and nothing consumes
it, so you cannot produce such a link from the app and pasting one changes
nothing. Wiring a surface to it is the next step. Fleet addresses carry no tab
and no view state, and scenarios, pasted bodies and files opened from disk still
have no address at all. The buttons are absent in fleet mode, where the fleet bar
replaces the tab nav, though the shortcuts still work. Both fleet settings need a
server restart and nothing restarts it for you. And a reader whose stored panel
tab was written to Work by the bug lands on Work once more after upgrading,
because the change deliberately does not rewrite a stored preference to guess
otherwise.

## The spectrum's zoom stops behaving like a widget

The overview strip and the zoom control are drawn on any stream that has a lane.
They used to appear only once a lane could not draw half of what it carried, so
on the 123-event session that turned this up, everything fit and nothing
appeared. The `−` and `+` buttons are gone; the one that puts the whole span back
on screen remains, labelled `all`, because a stepless zoom needs a way home more
than a stepped one does. The keyboard did not lose the steps: `+` and `-` zoom,
`0` fits, shift and arrows pan a quarter window, `[` and `]` page across empty
axis.

ctrl+wheel, and a trackpad pinch, now zoom while the pointer is over the overview
strip. Before, the handler lived inside the lane component, so the one surface
that draws the window was the one surface where the gesture did nothing. A plain
vertical wheel is still left alone, so the page scrolls.

The window's two ends on the strip can be grabbed and dragged, which sets a span
directly instead of zooming around a point. Nothing is drawn on them: the window
box stays exactly as wide as the window it stands for, down to a hairline at the
zoom floor, and the extra room is a 6-pixel hit zone. Dragging one end past the
other does not turn the window inside out, and the grip is held for the length of
a drag, so a fast drag that outruns its own grab zone keeps the end.

A collapse button also joined the sidebar's brand row, because the header's
burger is the first thing a narrow window takes away, so the one control that
gives room back was reachable only once you already had room. At 720 px it gives
the strip underneath 322 px.

**What this does not do.** The grabbable ends are invisible by design and the
only signal is the mouse cursor, so on a touch screen there is nothing to
discover and there is no keyboard way to drag one. The strip is still
`role="img"`, nothing in the interface says the ends can be grabbed, and the user
guide's spectrum chapter does not document the zoom at all. Zooming still needs a
modifier, which is correct and is also why a reader concluded it was broken. The
three walks above were done by hand against a built server; nothing in the suite
drives a real pointer.

## Three tool chips, and a command that reads a step per line

The trace's chip row had one `tool` chip and everything a tool did sat under it.
Over 1,961 transcripts: 71,730 tool calls, 9,367 of them over MCP, with no way to
ask for them. There are three chips now, `tool`, `workflow` and `mcp`, and the
rule is the tool's wire name. The busiest single thing behind `mcp` is the
browser, previously indistinguishable from the 42,070 Bash calls beside it. A
tool result inherits the chip of the call it answers, because a result keeps only
the id of its call. The first cut knew only the `Workflow` tool and missed
`Monitor`, roughly one background launch in five.

A chained shell command breaks before every top-level `&&` and `||`. Of 41,960
Bash commands in that corpus, 25,009 are chained, and until now each was one
paragraph of shell wrapped at whatever column the card happened to be. This is
not a `split("&&")`, and the corpus is the reason: a naive split would have
broken 1,220 commands where the shell sees no joint at all, every apparent
operator sitting inside quotes, a substitution or a heredoc body. That shows a
reader a command that is not the command that ran. The breaker walks the string
once, tracking quote mode, escapes, paren depth and heredoc terminators, and it
adds newlines and nothing else: strip them back out of all 41,960 outputs and you
get the input back, byte for byte. The break is display only, and reaches the
chat tool card, the trace's open row, the lab's tool-call panel and the HTML
export.

**What this does not do.** The permission gate does not get the line breaks, so
a pending Bash command is still one long line at the moment you have to decide
about it, and only the HTML export carries them. Markdown, JSONL, the raw faces
and the search index all read the recorded bytes. The rule knows `&&`, `||` and
`;`, so a long pipeline is still one line. Three chips is not a catalogue: two
very different MCP tools share one, there is no way to ask for Bash alone, and
the `workflow` chip matches exact names, so the next launcher added upstream will
be missed the same way `Monitor` was.

## The folders a session left on disk

An imported transcript carries up to three buttons for its own directories:
`folder`, the project directory the transcript sits in; `workflows`, the journals
its runs wrote; and `scratchpad`, the temp directory those runs used. The app read
all of it and could show you none of it, because the store is under a dot-folder
Finder hides and the scratchpad is under a path nobody would guess. A button is
drawn only for a directory the server has just stat'd, asked per session rather
than remembered, because a scratchpad appears when a run makes one and a temp
sweep takes it away. Hovering shows the absolute path, which is also how you copy
it out for a terminal.

The path is never the caller's. The request names a transcript and a kind, and
the server derives the directory through the same fence the read endpoints wear.
The spawn is an argument list, never a command string, and the program comes from
the operating system, never from the request. Measured before shipping: a rebound
Host gets 404, the encoded `/%61pi/` form gets 404, and both a traversal and an
unknown kind answer `missing` with nothing opened.

The Files tab also stops blaming the server. "no terminal available, the server
refused the connection" was true and useless: the `spectro-pty` helper rides the
signed desktop bundle and is not in the jar, so a plain `java -jar` has no
terminal by construction. The config reports the shell as ready, off or
unavailable, and the head says `no terminal` with the reason in its title. A
server that does not report the field at all is read as ready.

**What this does not do.** There is no button for the directory the session
actually ran in. `folder` opens the transcript's project directory inside the
store, not the repository the agent worked in. Only a transcript opened from the
store gets buttons, so a pasted file, a picked file, a live run and
spectroscope's own archived sessions show nothing, and on Windows there is never
a scratchpad button. The folder opens on the machine running the server, which
the fence keeps to the machine you are at, though a tunnel presenting itself as
loopback would open a window in front of somebody else. And no automated test
proves a folder was ever opened: the suite pins the five refusals, and the
successful press was verified by hand.

## The build and the published POM

Every module already compiled for Java 21, and that governs the artifact but
never governed which JVM runs the tests. That was open, since this machine has
only 25, CI pins Temurin 21 and the build container ships 21. The five modules
declare a toolchain with the foojay resolver now, so Gradle finds a Java 21 JDK
or downloads one. Measured after: the test JVM reports 21.0.12 (Eclipse Adoptium)
on a machine whose only installed java is 25.0.2. The cost is a one-time download
of roughly 200 MB where no 21 exists.

Six of the eight sample directories are Gradle projects and none of them shipped
a wrapper, while every README opened with `gradle build`. The first documented
command of the first example failed on any machine without a system-wide Gradle,
which is exactly the machine a sample is for. Each now carries `gradlew`,
`gradlew.bat` and a wrapper jar pinned to Gradle 9.6.1. Proven the way it will be
met: one sample copied into an empty directory, `gradle` not on PATH,
`./gradlew build` returns 0.

`spectro-core` declared jackson-databind 2.17.2 while its own dependency,
anthropic-java 2.34.0, brings the 2.18.2 family. Gradle resolves highest-wins, so
every build here passed and nothing in this repo ever saw it. But what we publish
is the POM, and the POM contradicted the dependency beside it. Measured
in the jars: `ParserMinimalBase(StreamReadConstraints)` exists in jackson-core
2.18.2 and not in 2.17.2, so the classpath that crashes is a 2.18 databind beside
a 2.17 core. The first fix proposed was to pin jackson-databind, which would have
widened the gap; it was wrong and was corrected before anything shipped.
`spectro-core` imports the Jackson BOM now instead of naming one artifact's
version, declared `api` so the constraint travels into the published POM, and
`spectro-mcp-notes` does the same. A number pins one artifact; Jackson is a
family whose halves call each other's constructors. **This reaches consumers only
with this release.** 0.6.1 on Maven Central still declares 2.17.2, and Central
is append-only, so anyone hitting the crash today still has to pin Jackson
themselves.

The release playbook now runs `brew style` on the working copy before the push,
then updates, then audits. `brew audit` takes a name, not a path, and answers it
from Homebrew's own clone, which only moves on `brew update`, so run before the
push it reads the previous release's cask and reports success. Hours after 0.6.0
shipped, that clone still said 0.5.0 while its audit was being quoted as proof
0.6.0 was sound.

The repository also carries a local CI stack under `ci/`, new in this release.
It found something worth having: `./gradlew test` alone does not produce a
complete gate, because the PTY helper is C and built outside Gradle, so a fresh
container failed six tests until the pipeline learned to build it.

**What this does not do.** Four sample READMEs still name 0.4.1 coordinates in
prose while every sample build file pins the current version, and a copied sample
resolves released artifacts, so it gets the Jackson declaration of the version it
names rather than the corrected one in this tree. `./gradlew` still needs a JVM
present to start Gradle at all. The toolchain removes the need for the right JVM,
not for any JVM, and it says nothing about Node or about the C compiler for the
PTY helper. No workflow runs the gate on macOS, so macOS-only breakage is
still caught only by a human on a Mac. The tap ordering is documentation, not
enforcement. And nothing in the local CI stack can sign the DMG, because codesign
and notarytool need the host and its keychain.

## Fixed

- The terminal in the Files tab grows back with the window. Its flex rule had a
  grow factor of 0, so it gave height back and could never take it again:
  measured from 900 px to 600 and back, the pane recovered correctly while the
  terminal host stayed at 61 px and 3 rows.
- The sidebar's brand, its three actions and the sessions/fleets switch are one
  sticky block, so scrolling the session list no longer carries the segment
  switch off screen.
- A trace summary keeps a floor beside its chips. Two chips at 1280 px left the
  summary 0 px wide on 18,190 anchored lines; the text keeps a 10ch floor and
  each chip a 22ch ceiling.
- The bus renders its rail with no nodes docked. Before, the one surface that
  explains what this app is returned a line of placeholder text.
- A path holding a NUL byte answered 500 with Spring's default error body, which
  told a prober that path was different from the ones that answer 404, and in a
  batch abandoned every row queued behind it.
- The status table of the local CI stack printed one server's port as `888—`,
  because the substitution replaced the first zero anywhere in the string rather
  than a string that is zero.

## How you get it

The channels are the ones 0.5.0 shipped. Nothing new this cut, and nothing
dropped.

**Homebrew, macOS on Apple silicon.**
`brew install --cask spectroscope/tap/spectroscope` installs the signed and
notarized desktop kit.

**The macOS disk image.** `spectroscope-0.7.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**apt, on Debian and Ubuntu.** The signed repository at
`https://apt.spectroscope.dev` serves the deb; if you added it for an earlier
release, `apt upgrade` carries you here. x86_64 only.

**The Linux kit.** `spectroscope-0.7.0-x86_64.AppImage` and
`spectroscope_0.7.0_amd64.deb`, built and smoke-tested on Linux by this
project's own CI. Both bundle their own Java runtime and `llama-server`. x86_64
only, not signed.

**The jar and the CLI.** `spectro-server-0.7.0.jar` and `spectro-0.7.0.zip` run
on any machine with Java 21. They are the smallest way in, and the only way onto
a platform that has no kit.

**In your own code.**

```
dev.spectroscope:spectro-core:0.7.0
dev.spectroscope:spectro-orchestrator:0.7.0
```

Both are on Maven Central, which is append-only: 0.7.0 stands beside 0.6.1
rather than replacing it. This is the first release whose POM carries the Jackson
BOM, so a consumer no longer inherits a databind version that contradicts what
`anthropic-java` brings.

## The gate

Measured on 2026-08-07 on the release tree, with the build cache and the
up-to-date checks disabled: GATE_JUNIT Java tests across GATE_JUNIT_FILES result
files and GATE_VITEST web tests across GATE_VITEST_FILES files, no failures. One
Java test is skipped when no live API key is present. Javadoc runs over all four
published modules. Both suites run the same way in CI.

## Not in this release

## Requirements

Java 21 or newer. The macOS desktop kit is arm64, signed and notarized, and
includes its own Java runtime. The Linux kit is x86_64, includes its own Java
runtime, and is not signed. The server jar and the CLI need a `llama-server` on
the PATH (`brew install llama.cpp`) to run a local model; both desktop kits
bundle one. The terminal in the Files tab needs the `spectro-pty` helper, which
only the desktop kits carry.
