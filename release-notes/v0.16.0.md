# spectroscope 0.16.0

A session has a new tab, files. It shows which files a run's file tools read,
created or changed, and when, with every edit as a diff. Shell commands go
through a heuristic that names the files they probably touched. If you want
another reading, a model you pick reads the session's file calls; a local
model works. The Lab now counts four more of the app's own file tools.

***

## Files tab

**What the run did to files.** The tab sits after trace and is shown wherever
trace is; light mode leaves it out. It reads only what the session recorded:
the tool calls, their inputs and their results. The tab does not scan your
folder.

**Four views.** The `all` view shows an explorer, the list of calls and what
one call did. When you select a file, the list shows only that file's calls.
The `diff` view keeps the explorer and gives the detail more room. The
`created` view shows one card per file the run created, with its content when
the session holds it. The `operations` view is a table of every call with its
time, its prompt, what it did, the files it touched and its tool. When more
than one agent made file calls, the table also names the agent. The timeline
is above every view.

**Edits as a diff.** An edit shows the text it replaced and the text it put in
its place, in one column or as before and after. A write says whether it
created the file or overwrote it. Where the session does not record that, as
in an imported transcript, it says the file was written. A failed call is
listed without files.

**The timeline.** One row per file and one row for shell commands, one mark
per touch, and the prompts numbered on the axis. It draws up to 30 files; the
explorer lists the rest. A call's time counts from the start of the run and
shows its seconds: "+7.4 s", "+12:05", "+1:25:32", "+3 d 04:12:05". The axis
labels use at most two units, such as "1 h 25 min". A pause of more than two
minutes shrinks to a short break mark. Point at the mark to see how long the
pause was. This way a session that ran over several days still fits. A
recording without timestamps counts calls instead. The tab has its own
cursor: drag it, play it, or step through the calls with the arrow keys.
Everything after the cursor is dimmed. Moving it does not move the chat, the
trace or the Lab. With more than one agent, a chip per agent filters the tab.

**Recorded, probable, model.** Every file entry says where it comes from. The
tag `recorded` means a file tool named the file. The tag `probable` means the
heuristic found it in a shell command, for example `echo text > notes.md`,
`cp a b` or `sed -i`. When a command runs a script, the tab says that the
script may have changed the files its arguments name. When the session's
folder is available, a link opens the script in the Files panel beside the
chat. Probable and model entries have dashed or ringed marks, so they look
different from recorded ones.

**A model's reading, when you ask for it.** Switch to `heuristic + model`,
pick a provider and a model, and press "analyze with model". The picker starts
empty, so nothing runs on the chat's model by accident, and later offers the
pair you picked last. Local providers such as Ollama and LM Studio are
offered; the built-in model is not. Before the tab sends anything, a sheet
shows the provider, the model and the address. It says whether the text
leaves this machine and how many characters go out, and you can open the
exact text. The text names the session's folder and has one line per file
call, plus the output of each shell command cut to 2,000 characters. The tab
does not send what a file tool wrote. Only the model's entries for shell
commands count, and they carry the `model` tag. The app keeps the reading for
this session only and does not save it. `/clear` in a live chat drops it.

**Open in trace.** Every call has a link to its row in the trace.

## Lab

**More file tools count.** The Lab's map and its files list now count the
app's own `edit_file` as a write and its `grep`, `glob` and `view_file` as
reads. Before, they left these four tools out.

## Server API

Two endpoints serve the model reading, and both answer only requests from this
machine. `GET /api/files/analyze/engine?provider=&model=` says whether a pair
can run. `POST /api/files/analyze` streams the model's answer as NDJSON. The
request names its provider and model. The server never falls back to its
default model and refuses the built-in model. It accepts at most 60,000
characters of text and never logs them.

## Library API

No change.

## Known limits

- The heuristic sees the command line only; it does not see the command's
  output. A script, a build tool or code run from the command line can change
  files the tab cannot name. The tab then names the script or says that it
  cannot tell which files changed.
- The consent sheet treats a model at a local address as local unless its name
  ends in `:cloud` or `-cloud`. A local server that sends a model with another
  name on to a cloud service is shown as local.
- A session without a recorded working folder shows paths as the tools wrote
  them.
- When a helper's Claude Code transcript is imported on its own, the message
  its coordinator sent it counts as a prompt.
- The deprecated settings file in the folder the app was started from can
  still set `toolResultElision`.
- A settings file changed by hand outside the app reaches an empty chat only
  after a reload.
- The agent's file tools refuse to write under a playbook folder, but a shell
  command run with `run_command` can still write there.
- The hooks of a picked playbook do not run in the session.
- Refusals from the server, such as the reason a run may not start, show in
  English in the German interface.
- The context tab still lists the skills of the folder the app was started
  from, not the skills of the session.
- The run panel lists the files that the agent's file tools wrote. It does not
  list files written by shell commands, MCP tools or git. It counts the shell
  commands of a step; the files tab names the files those commands probably
  touched.
