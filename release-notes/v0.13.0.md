# spectroscope 0.13.0

This release gives a run room to work for hours and lets you reach it while it
works. The time limits on a shell command, a subagent and a whole run were set
for short sessions; they now ship at 15 minutes, two hours and 1,000 turns, and
each one is a setting that reaches the run. A sentence you type during a run
reaches that run at its next turn. A permission request opens a window, and
the context ring divides by the window the model actually holds. Stop shows
within seconds on a fast model, and spectroscope refuses a shell command aimed
at its own processes.

---

## First run

**A shell command may run for 15 minutes.** The agent's `run_command` used to
be killed after 10 seconds. The shipped limit is 900 seconds now. In 0.12.0,
`commandTimeoutSeconds` was a key you could set that no run read. This release
reads it in the app's sessions, in child agents, in `spectro run` (and so in
scheduled fires and fleet nodes) and in the terminal face. The `Tools` facade of
the SDK has no settings to read and uses the shipped 900. If a settings file of
yours already names `commandTimeoutSeconds`, that number applies from now on.
The exception is a value below the key's floor of 1. A 0 is one, and clearing
the field on the settings page used to leave one behind. spectroscope skips such
a value as if the key were not set, and the settings page names it beside the
field. Two things still go wrong when a command reaches the limit, and both
are under Known limits: its output is lost, and processes it started can keep
running.

**A subagent may work for two hours.** The floor of a child's time budget was
300 seconds, fixed in the code. It is now the setting `subagentBudgetSeconds`,
shipped at 7,200. A slow backend can still raise a lower setting, up to 30
minutes; nothing lowers the number you set. In return, a child that stalls after
its first token holds its parent for up to two hours, and in the worst case for
2 hours 45 minutes, counting the time allowed before that first token.

**A run may take 1,000 turns.** The ceiling was 150. On one developer's own
sessions the longest run took 118 turns in 2 hours 10 minutes; at that pace an
eight-hour unattended run needs about 440, and 1,000 sits above that. The
ceiling counts turns and nothing else, and every child agent gets the same
1,000 as its parent. If you run unattended against a metered API, one agent can
now spend almost seven times the turns it could in 0.12.0.

**What you type while a run is working goes to that run.** Enter used to put
the message in a queue that sent it after the run had ended. While a run is up
and no message is waiting, the send button reads Steer, and the run reads your
sentence at the start of its next turn. If you are used to typing your next
task while a run finishes the current one, that task now lands in the current
run. A message with an attachment, or one typed while queued messages are
already waiting, still joins the queue. The rules are under Steering.

**The line under an answer is shorter.** By default it shows input tokens,
output tokens and the duration. The cache numbers, the speed, the clock times
and the model moved to an extended reading, which you choose in the three-dot
menu at the left of the chat bar, under answer line.

**A permission request opens a window.** The thin bar under the message field
is gone. The window stays until you answer it. Deny has the focus, Escape
denies, and a click outside the window does nothing. The Lab no longer asks:
while it is on screen, a waiting request shows as a `gate open` chip on the
chat tab.

**The context ring divides by the window.** It used to divide by the
compaction point, which is 70% of the window, so a window that was half full
read 71%. It now reads, for example, `143k of 250k loaded window (57%)`, and
the compaction point is a mark on the ring. The ring turns amber and red at the
same token counts as before. A model that Ollama serves from the cloud also
compacts much later: it used to fall back to 100,000 tokens, and it now reads
its window from Ollama. For a model whose window Ollama states as 1,048,576
tokens, compaction moves from 100,000 to 734,003 tokens.

**rtk is an option, and it ships off.** A switch in the same three-dot menu can
send the agent's shell lines through rtk, a separate command-line tool that
shortens command output. Nothing changes until you install rtk and turn the
switch on.

**To keep 0.12.0's numbers while you upgrade**, set `maxTurns: 150`,
`commandTimeoutSeconds: 10` and `subagentBudgetSeconds: 300` in
`~/.spectro/settings.json` before the first run, and choose extended under
answer line. For a cloud model on Ollama, `compactionThreshold: 100000` brings
back the old compaction point and the ring's old reading, but that number then
applies to every model you run. Steering and the permission window have no
switch.

## Time limits

The three limits sit together in Settings, Permissions, under limits on one
run: Turns per run, Time per subagent and Time per shell command. A change to
either time limit reaches the next session.

A subagent cut by its budget now hands back what it had written. The parent
used to receive one error line. It now receives that line, which names the
seconds that applied and says that `subagentBudgetSeconds` raises them, and
under it the text of the turn the child was cut in, below a marker that says
the text is unfinished. Text from the child's earlier turns is not included. A
child that had written nothing gets the error line alone.

## Steering

While a run works, the send button reads Steer. Your sentence appears in the
chat at once as `Steering message, waiting for the next safe point`, and changes
to delivered or not delivered once the run has answered for it.

The model reads the sentence at the start of its next turn, introduced as a
message from the person watching the run. Several sentences sent during one
turn arrive together, in the order you sent them. A run that was about to end
goes on so it can read a waiting message, and from there it works as usual
until it ends again. A message is read once, so it cannot keep the run going a
second time. If the run ends before it reads your sentence, for example at the
turn ceiling, the chat marks it not delivered and sends it as your next
message.

A steering message has no say over permissions. It does not answer a waiting
permission request, change the permission mode or add an allowlist entry.

It carries text only, and it reaches the main agent of a session in the app.
Child agents, fleet nodes, `spectro run` and the terminal face cannot receive
one. Against a server older than this release, the first steering message falls
back to the queue and the app stops trying on that connection.

---

## Stop and quit

Stop now shows in the app within seconds, even with a fast thinking model in a
long session. In 0.12.0 the run itself stopped at once, but the app showed it
only after every event queued ahead of the stop had been written to the session
file and sent to the page, and a fast thinking stream could queue minutes of
them. Now, while the app is behind, the pieces of thinking or answer text that
one agent has waiting go out as one larger piece, so the queue stays short.
When the app keeps up, pieces go out one at a time as before. In our tests the
stop reached the app in under two seconds in two cases: 150 thinking lines a
second into a session that already held 100,000 events, and four child agents
thinking at once.

On a normal quit, the server now writes the events still in its queue to the
session file before it exits. It waits up to three seconds for that. Whatever
is still queued after that is lost, but any run that was still going is
recorded as stopped. Before, a quit during a backlog lost all of those events,
and a session resumed later was missing their turns.

Both changes apply to sessions in the app. `spectro run` and scheduled fires
write their session files as before.

## Answer line

The line under each answer has two readings. Normal, the default, shows input
tokens, output tokens and the duration. Extended shows what 0.12.0 showed: cache
read and cache write where the provider reported them, the speed, the start and
end clock times and the model. The model name is shortened and the full name
appears on hover. Where cache was reported, extended also shows the whole
context size, labelled context. Only the Anthropic provider reports cache
numbers today.

The choice is kept per browser, in the three-dot menu at the left of the chat
bar.

---

## Permission window

The window shows the tool, its input, which agent asked and how many requests
are waiting, as the Lab's window did in 0.12.0. New in it: the command as a
block of its own, the working directory, and the last six allow or deny
decisions of this session, newest first. For a child agent it also names the
agent that started it and the task it was given. Gates of a fleet node you have
entered wait in the same window, after the session's own. The choices to
remember an approval for the session or save it to the project are unchanged.

The Lab stopped asking. Scrubbing back through a live run could draw a window
for a call that had already been allowed, and an answer sent from it reached
nothing, while a new request stayed out of sight. The Lab draws no window now.
While the Lab is on screen, a waiting request shows as the `gate open` chip on
the chat tab. Every other view opens the window, except a recorded session open
for replay. While you watch a replay, a request from the live run shows neither
the window nor the chip, and the run waits until you go back to it.

In the desktop app, the browser page in the dock hides while the window is
open, so it cannot draw over it.

## Context window

The ring in the header divides by the window whenever the run states one, and
names which window it is: loaded window for the size a local server reports for
its loaded model, model window for the size the model publishes, set window for
a size you set yourself. The compaction point is a mark on the ring and a line
under the headline, such as `compacts at 175k`. Where no window is known, or
where you set `compactionThreshold` yourself, the headline reads as it did in
0.12.0. The Lab's context panel divides by the same number.

**You can set the window for one session.** In a live session the ring's
popover has a field for it. Type a whole number of tokens from 8,000 to
10,000,000, digits only, and press Set. The ring moves at once, the run compacts
at 70% of that window from its next turn, and child agents use the same window.
It takes precedence over the detected window and over a `compactionThreshold` in
your settings. The session file records it, so it survives a restart of the
app. Clear hands the decision back to detection. A recorded session opened for
replay shows no field.

**A model Ollama serves from the cloud reports its window.** spectroscope
recognises such a model by the remote host Ollama lists for it, asks Ollama's
`/api/show` for its context length once, and compacts at 70% of that. These
models have no loaded instance to ask and no row in the built-in table of
published windows, so until now they compacted at the 100,000-token fallback. A
local model is asked the way it was before.

## Prompt history

The up arrow in the message field brings back the prompts you sent in this
session, newest first. The down arrow walks forward again to the draft you were
writing, which comes back as you left it. While you walk, a line above the
field reads `History 2/5`, and the field grows to fit the prompt.

The arrows walk the list only from the first line of the field (up) or the last
line (down), so a draft of several lines still moves line by line. With a
modifier key held, the arrows behave as before. A message waiting in the queue
is part of the list, and recalling it takes it out of the queue: if you then
walk away from it without sending, it is not sent. A steering message joins the
list once the run has answered for it. The history holds text only, and only
live sessions have one.

## Skill search

Typing a skill's full name after `/` now puts that skill on the first row,
above skills whose names only start with or contain what you typed. Before, the
first row could hold another pack's skill of a similar name, and Enter inserted
it. Every row from a pack carries the pack's name as a small tag. A bare name
still finds a skill inside a pack. There is no pattern search.

## Skills view

Skills sits in the upper group of the sidebar now, after New chat, Scenarios
and Starters. The session list stays in the sidebar while the skills view is
open, and a click on a session opens it and closes the view. Before, Skills
replaced the session list, and you had to press Sessions before you could reach
a session again.

The catalogue in the skills view is grouped by pack: humanizer, matt-pocock,
superpowers and ui-ux-pro-max. Every pack starts collapsed. Its header shows how
many of its skills are installed, for example `2 of 35 installed`, and has two
buttons. Install copies every skill of the pack that is not installed yet, in
one step, and its label says how many (`install 33`). Remove takes the pack's
skills out of your own skills folder, `~/.spectro/skills`. If the server
refuses one skill of the set, it changes nothing, and the pack lists each
refused skill with its reason.

Open a pack to install or remove single skills with the switch on each row. A
skill that the project carries in its own `.spectro/skills` shows as on, and its
switch is disabled. Remove and a row's switch act on the first click.
Removing a skill also removes any edits you made to it. The list of installed
skills at the top of the view is unchanged.

## rtk

rtk is a command-line tool, developed outside this project, that shortens the
output of common developer commands. If it is installed, the last section of
the three-dot menu, Shell through rtk, routes the agent's shell lines through
it. The switch ships off.

When it is on, spectroscope asks `rtk rewrite` what each shell line would
become and runs that line instead. The permission gate decides on the line that
will actually run, and the request carries the model's original line next to
it. The transcript keeps the model's line as the model wrote it. Four rtk
commands are never used, wherever they appear in a line: `gradlew`, `find`,
`test` and `err`. In our measurements they reported success for commands that
had failed, or dropped output. A line rtk has no rewrite for runs unchanged.
Every rtk process spectroscope starts gets `RTK_TELEMETRY_DISABLED=1`.

If rtk is not found where the agent's shell looks, the switch is disabled and
says so, and every line runs as the model wrote it. The version found is shown
beside the switch; our measurements used rtk 0.45.0. The setting is `rtkFilter`,
`on` or `off`. A change takes effect at once, and only for the main agent of a
session in the app.

## Host guard

spectroscope now reads each shell command from the agent before it runs, and
refuses it if it would stop the app itself. That covers this server (by
process number, name or port), the window or terminal that started it, and its
helper processes. The check reads `kill` with a process number, `pkill` and
`killall` by name or pattern, and `pgrep` or `lsof` piped into `kill`, also
inside `sh -c`, `eval`, `sudo`, `env`, `timeout` and similar wrappers. It
applies in every permission mode, auto mode included. A refused command does
not run. The agent gets an error that starts `ERROR: refused`, names the
pattern and the process it matched, and tells it to ask the person who runs the
app if the app needs a restart. A kill aimed at other processes runs as before,
as long as it does not also match the app: `killall java` is refused, because
the server is a Java process.

The check comes after the permission gate. In ask mode you can be asked about a
command that is then refused, and the gate's record of it still says allowed.

A server that the desktop app started now ends when the app ends, even when
the app was killed and could not stop it. Before, such a server stayed on its
port with no window.

## Settings page

The settings page has one search field above its rooms. It searches the section
headings and settings keys of all six rooms, and the name, value and
explanation of each entry in the list of numbers that govern a run. A click on
a result opens its room and scrolls to it. A field's own label is not searched:
`timeout` finds the shell time limit, "Time per shell command" does not.

Each row of that list that governs something has a Copy prompt button. It
copies a sentence, in the language of the interface, that names the constant,
its value and its unit, and words the request by the kind of number. For a key
that is already settable it asks for a new value. For a number fixed in the
code it asks for a change that makes it settable, and points to the
configuration reference in the repository, which has a row for every settings
key.

Every number field on the settings page has a floor, the smallest value it
accepts: 260 for the widest dock, 0 where a 0 means off or none, such as
questions per run, and 1 for the others. An emptied field or a number below the
floor is not saved. A note under the field says so, and the saved value comes
back when you leave the field. When spectroscope reads a settings file, it
skips a value below its floor, whether you wrote it by hand or an older version
saved it, and the rest of the file still applies. The settings page then names
it beside the field,
for example `0 from user settings is below the floor of 1 and was skipped`,
with a reset button when the value is in your own settings file.
`spectro doctor` and the command line do not report a skipped value.

## Chat layout

The icons under the message field sit in 24 px boxes instead of 44 px ones and
stand closer together, and the row takes less height. Each icon's
click area reaches 4 px above and below its box, so a target is 24 by 32 px,
down from 44 by 44. On a touch screen that is a smaller target than before.

The space above the message field is 8 px shorter, and so is the status bar at
the bottom of the window.

An open thinking block can grow to half the height of the chat pane before it
scrolls. On a short pane it still gets 240 px, the fixed height it had before.
The limit follows the window when you resize it.

Sending a message no longer opens the right dock. It used to open on Files,
with Agents beside it, once the agent's working folder was known. It now stays
as you left it, and the Files icon in the header opens it. The dock still
opens on Browser when the agent starts a browser.

A fresh install's welcome screen offers three answers instead of two: "Walk me
through it", "Open everything, keep the tutorial" and "Open everything, no
tutorial". The third one used to need a trip to the settings, where all three

## Test builds

A desktop app you build yourself with `scripts/build-desktop-runkit.sh`, from a
commit that is not a release tag, says so. About shows Test build and a label
with the next version, the branch, the commit and the build time, for example
`0.14.0-beta (main, 1a2b3c4, 24.09. 14:05)`, and the window title carries the

## Recordings

Two new kinds of line can appear in a session file. `steering_message` records a
sentence sent into a running turn and whether the run took it.
`window_override` records a window set or cleared from the ring. The
`thresholdSource` field of `context_info` gained the value `window_override`,
and a cloud model served by Ollama now reports `model` where it used to report
`fallback`.

spectroscope reads both new kinds. A reader of your own may fail on a kind it
does not know instead of skipping it. Push one line of each through it before
you rely on it.

A session file written while the app was behind can hold fewer, longer
`thinking_delta` and `text_delta` lines: the pieces one agent had waiting are
joined into one line with the same text. When several agents write at once,
pieces of different agents can be written in a different order than they
arrived. Each agent's own pieces keep their order. A run that was still going
when the server quit ends with a `run_end` whose stop reason is `aborted`.

## Library API

No public member of the 0.12.0 API was removed.

`ChildBudget.FLOOR_MS` is deprecated. The floor of a child's budget is the
setting `subagentBudgetSeconds` now, and `floorMs()` on a budget gives the floor
it runs on. `FLOOR_MS` holds the shipped default floor, 7,200,000 ms, which is
`SpectroConfig.DEFAULT_SUBAGENT_BUDGET_SECONDS` (7,200) in milliseconds. In
0.12.0 it was 300,000.

Three more constants changed value: `Agent.DEFAULT_MAX_TURNS` and
`SpectroConfig.DEFAULT_MAX_TURNS` from 150 to 1,000, and
`SpectroConfig.DEFAULT_COMMAND_TIMEOUT_SECONDS` from 10 to 900. All four are
`public static final`, which `javac` copies into whatever compiles against
them, so a class compiled against 0.12.0 keeps the old numbers, 300,000 for
`FLOOR_MS` included, until it is recompiled. Recompile against 0.13.0 instead of
dropping the new jar under an old build.

`SubagentConfig` carries 15 components now. Its 13-argument constructor from
0.12.0 is still there, beside constructors for 15, 14, 10 and 9 arguments and
the builder. That constructor passes no floor setting, so the children it
configures run on the shipped floor of 7,200 seconds where 0.12.0 gave them
300, unless the budget you pass is a fixed one.

One enum and one sealed interface gained members. `CompactionThreshold.Source`
gained `WINDOW_OVERRIDE`, declared last, so the existing ordinals hold.
`RunEvent` gained `SteeringMessage` and `WindowOverride`. An exhaustive `switch`
over either stops compiling until the new cases are handled.

The rest is additive. `LlmProvider` gained `publishedWindow()` with a default of
0, so a provider of your own needs no change. `AgentOptions` and `SpectroConfig`
gained components and kept constructors with their exact 0.12.0 shapes.
`SpectroConfig.Resolved` gained `belowFloor()`, the values a settings file held
below their floor, and `SettingFloors` lists the floors. `StandardTools.all(long)`
is public. `spectro-orchestrator` has no change to its public API.

## Fixed

Most of these have a section above.

- **The shell time limit reached no run.** 0.12.0 listed this as a known limit.
  The app's sessions, child agents, `spectro run` and the terminal face read the
  setting now.
- **A subagent cut by its budget lost everything it had written.**
- **Clearing a number field on the settings page saved 0.** A 0 left in the
  settings file could, for example, end every run before its first turn.
- **Stop could show minutes late on a fast model**, and a quit in that time
  lost the events still queued.
- **The chat cut up the thinking of child agents running at the same time**
  into many short blocks. Each child's thinking now stays in one block until
  that child does something else, such as calling a tool.
- **A shell command from the agent could stop the app it runs in**, and the
  server could stay behind on its port.
- **The Lab could ask again about a permission request that was already
  decided**, and hide a new one while you were scrubbed back.
- **Typing a skill's full name could insert a different skill.**
- **The Skills heading in the slash picker was half covered** by the first row
  under it. It now sits fully above the list.
- **Opening Skills hid the session list.**
- **Sending the first message opened the right dock.**
- **A cloud model served by Ollama compacted at 100,000 tokens**, whatever its
  window.
- **The message field did not resize when a slash command was picked.** It
  resizes on every change to its text now, a recalled prompt included.

## Known limits

- **The host guard reads only the command line.** A command that hides its
  target still runs, for example `kill $(cat app.pid)`, a process number kept in
  a variable, or a script that stops the app. A line the guard cannot read runs
  unchecked. The fleet hub's port, when you turn the hub on, is not protected.
- **A command cut by its time limit hands back none of its output.** The model
  receives `command timed out after N s` and nothing the command had printed, so
  it cannot see how far the command got. With a 15-minute limit, that can be a
  quarter of an hour of build log.
- **Processes a cut command started can keep running.** A time limit or Stop
  ends the shell that ran the command. A process it started with `&&`, `;` or a
  pipe can survive, and nothing in the app shows it.
- **Compaction does not survive a restart.** A session resumed after the app
  restarts rebuilds its whole conversation, including what had been compacted,
  and sends all of it on the first turn, because a run cannot compact before its
  second turn. With cloud models on Ollama now compacting later, that first
  request can be very large.
- **In auto mode the permission window can flash.** Each gated tool call can
  open the window for a moment and close it again, and the working line at the
  bottom of the chat jumps with it. The call is already approved and nothing
  waits for you.
- **The thinking view can stop following.** During a very fast thinking stream,
  the thinking panel can stop scrolling with its newest line. Scroll it to the
  bottom to make it follow again.
- **Narrow windows lose controls.** In a narrow window, tabs can disappear off
  the tab strip with no way to scroll to them, and the right dock can squeeze
  the chat. At a phone width, the sidebar opens on top of the welcome screen
  and covers its three buttons; close the sidebar with its own toggle, then
  choose. Also at a phone width, the right dock opened on Files can be too
  narrow to use, and the skills view runs past the right edge of the screen.
- **On Anthropic, a tool loop is not cached past the fixed prefix.** The system
  prompt and the tool list are cached. On the request that follows a tool call,
  the conversation after them goes out uncached, so a long tool loop pays full
  input price for its growing history. The extended answer line shows it as a
  request with no cache write.
- **Two writes can tear a session line.** Rarely, two events written at the same
  moment merge into one broken line in the session file. The reader skips the
  broken line without saying so, and a resumed session or its archive view can
  then show an earlier turn's numbers. Seen under a scripted load, not yet in
  ordinary use.
- **rtk, steering and the session window reach the app's sessions only.** Child
  agents do not use rtk. `spectro run`, scheduled fires, fleet nodes and the
  terminal face have no rtk, no steering and no way to set the window.
- **A subagent cut by its budget hands back its last turn only**, not the text
  of its earlier turns.
- **The context popover's headline is in English** in both languages. The
  window field under it is translated.
- **The desktop kits are built per platform.** The disk image is Apple silicon
  only and the Linux kit x86_64 only. A kit built without a Developer ID and the
  notary profile is signed ad hoc, and macOS then asks once: right-click, Open.

## Getting it

The channels are the ones 0.5.0 shipped. Nothing new this cut.

**Homebrew, on macOS.** `brew install --cask spectroscope/tap/spectroscope`
installs the signed and notarized desktop kit.

**The macOS disk image.** `spectroscope-0.13.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**apt, on Debian and Ubuntu.** The signed repository at
`https://apt.spectroscope.dev` serves the deb once this version enters the pool.
Check `apt policy spectroscope` before assuming `apt upgrade` carries you here.
x86_64 only.

If nobody is at the keyboard, use
`sudo DEBIAN_FRONTEND=noninteractive apt install -y spectroscope` instead of the
documented line. The plain line waits for you twice, and in a container neither
question is answered: apt asks you to confirm the download, and on an image
where `tzdata` has never been configured a package further down the chain asks
which timezone you live in. Neither one times out.

**The Linux kit.** `spectroscope-0.13.0-x86_64.AppImage` and
`spectroscope_0.13.0_amd64.deb` on the release page, built and smoke-tested on
Linux by this project's own CI. Both bundle their own Java runtime and
`llama-server`. x86_64 only, not signed.

**The jar and the CLI.** `spectro-server-0.13.0.jar` and `spectro-0.13.0.zip`
run on any machine with Java 21. They are the smallest way in, and the only way
onto a platform that has no kit.

**In your own code.**

```
dev.spectroscope:spectro-core:0.13.0
dev.spectroscope:spectro-orchestrator:0.13.0
```

Read Library API above before you upgrade a build that compiles against 0.12.0.
Maven Central is append-only, and 0.9.0's libraries were never published there,
so the gap where 0.9.0 would sit stays visible. If the coordinates above
answer 404 for you, the publish has not propagated yet.
