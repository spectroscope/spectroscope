# spectroscope 0.15.3

This release moves the start of a playbook into the chat. In developer mode you
pick a playbook for the session in the header and type `/run-with-playbook`
with your task. You confirm the run in the chat, and every step works on that
task. The picked playbook also gives the session its skills, commands and
agents, read from the playbook folder without installing anything. The web chat
and the terminal now take their commands from one list. The session list gets a
third density, and you can change the model of a stored session before you
send. Stop now ends a run at once when the backend does not answer.

***

## Playbooks in the chat

**Pick a playbook for the session.** In developer mode the header has a
playbook dropdown and a play button beside the folder chip. The dropdown lists
the registered playbook folders and "No playbook". The playbook pinned for the
working folder shows as a suggestion, and the session stores it only when you
pick it or start a run. A picked playbook whose folder is gone shows "not
found", and no run starts with it.

**Start a run with /run-with-playbook.** `/run-with-playbook <task>` runs the
session's playbook on the task you type, in that session. `/playbook run
<task>` does the same. Without a task, or without a picked or suggested
playbook, the chat refuses the command and says why. The play button only
writes `/run-with-playbook ` into the message box. The slash picker offers the
playbook commands in developer mode only.

**Confirm in the chat.** Before the run starts, the confirmation opens in the
chat of the session. It shows the task, the drawing of the playbook, each step
with its provider and model, every command a check may run, what the playbook
contains and the hash. Start begins the run in this session. When a run may not
start, for example because a run is already active, the playbook has findings
or the folder changed, the reason shows in that chat.

**Every step knows the task.** The task is part of every step prompt and of
every question the run asks you. The run records it at its start, so a replay
shows what the run was asked. The chat shows a line when the run starts, one
for each step with its model, and one when the run ends. A prompt that a step
sends carries a "Playbook" header and a coloured rule, so you can tell it apart
from your own messages.

**Workflows by name.** `/playbook workflow <name> <input>` runs a workflow of
the session's playbook at once, without a confirmation. `/run-workflow` is a
shorter form of the same command.

**More playbook commands.** `/playbook` names the playbook the session uses and
where that choice came from. `/playbook list` lists the playbooks you can use,
`/playbook show [name]` sums up the steps, gates, models and contents of one,
and `/playbook use <name>` picks one for this session.

**The Playbook view is for configuring.** The view starts no runs and no
workflows any more: "Build by this", its start sheet and the Run buttons of the
workflow list are gone. Its first tab is now called Steps. Install and Remove
for a playbook's contents are gone too, and the app copies nothing into your
folders. The contents list in the confirmation marks each skill, command, hook
and agent as "in the playbook". Copies that Install put into
`~/.spectro/skills` in an earlier version, and hooks it wrote into your
settings, stay where they are. Such a copy counts as one of your own skills,
and such a hook still runs. Delete them by hand if you no longer want them.

**The run works in the session's folder.** A file a step writes lands in the
working folder of the session. The agent's file tools refuse to write under a
registered playbook folder in every permission mode. When the playbook folder
is itself the session's working folder, the agent may write there.

## Skills, commands and agents of a session

**The picked playbook brings its skills, commands and agents.** As soon as you
pick a playbook, also in a plain chat without a run, the session reads the
playbook's skills, commands and agents from its folder. They show in the slash
picker and on the Skills and Commands page, and the model starts the playbook's
agents with the tool `spawn_named_agent`. Picking another playbook or "No
playbook" takes them out at the next turn. The pick of one session does not
change other sessions. A run also reads the skills and agent files of its steps
from the playbook folder, and a file changed after the confirmation stops the
start.

**The session reads its own working folder.** A session now takes its skills,
commands and agents from the `.claude` and `.spectro` folders of its own
working folder, and no longer from the folder the app was started from. When
both folders have an item of the same name, the `.spectro` one is used. The
model starts these agents with `spawn_named_agent` as well. An agent file
without a type, as Claude Code writes them, runs as a worker, or as an explorer
when its tools line names no tool that writes files or runs commands. The app
ignores a model named in the file.

**Doubled names keep their source.** A session has three sources: the working
folder, the picked playbook and your own skills in `~/.spectro/skills`. When
two of them have a skill, command or agent of the same name, every copy stays.
Each one is then named after its source: the playbook's id, `workspace:` or
`user:`, for example `spectro:brainstorming`. A name that exists only once
keeps its plain form. This also applies without a playbook, so a skill that is
in both the working folder and your own folder now shows twice. A skill or
command named like a command of the web chat, such as `help` or `clear`, always
carries its source, for example `user:clear`. When a skill and a command of one
source share a name, the skill keeps the name and the command carries its
source.

## Commands

**One command list.** The web chat and the terminal REPL take their commands
from one list; the web chat gets it from the server. The slash picker, `/help`
in the web chat and in the terminal, and the Skills and Commands page are made
from it.
`/commands` is another name for `/help`. In the terminal, `/help` also lists
the commands of the web chat, marked "web only". While the list loads, the
picker says so, and a message that starts with a slash waits instead of going
to the model as text.

**Skills and Commands.** The rail row Skills is now called Skills and Commands.
It lists the chat commands, and under "This session" the skills, commands and
agents the session in view reads at its next turn, each with its source.

**/clear in the terminal keeps the session.** `/clear` in the terminal REPL now
works like the one in the web chat. The session keeps its id, its file, its
folder and its goal, a running loop goes on, and only the history goes.

## Sessions

**A minimal density.** The List options of the session list offer minimal,
normal and extended. Minimal shows the name of each session, its state dot and
the badge that says it waits for you. Normal still shows the name, the folder
and the state. The rows under "Other sessions on this machine" follow the same
density.

**Change the model of a stored session.** A stored session that you can
continue now shows the provider and model picker in the composer before you
send, set to the pair it last ran on. When you pick a model there, the session
becomes live again without sending a message, and its next run uses the picked
model. The pick also becomes the default for new chats, as a pick in a live
session does. Imported sessions, scenarios and a session open in another window
keep the read only chip. Opening the picker asks the recorded backend for its
models, within the connect limit below.

## Unreachable backends

**Stop ends a waiting run at once.** Stop now ends a run that waits for a
backend that does not answer, for example a server behind a VPN that is down.
This holds while the app connects, while a server that accepted the connection
sends nothing, and in the pause between two attempts. It covers OpenAI
compatible servers such as LM Studio and llama.cpp, Ollama, Anthropic and
Copilot. No new attempt starts after Stop, the chat shows the run as stopped,
and the session takes your next prompt at once. In our tests against a local
socket that never answers, the run ended at most 26 ms after Stop.

**A connect limit of 10 seconds.** The OpenAI compatible, Ollama and Anthropic
providers now give up connecting to a backend after 10 seconds. Before, each
attempt waited until macOS gave up, which took 75 seconds in our measurement,
and a run makes up to three attempts. Without Stop, a run against an address
that drops packets now ends after about 31 seconds (measured on a Mac). A
connected stream may still take as long as the model needs.

## Known limits

- The agent's file tools refuse to write under a playbook folder, but a shell
  command run with `run_command` can still write there.
- The hooks of a picked playbook do not run in the session.
- Refusals from the server, such as the reason a run may not start, show in
  English in the German interface.
- The context tab still lists the skills of the folder the app was started
  from, not the skills of the session.
