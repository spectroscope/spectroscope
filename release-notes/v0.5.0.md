# spectroscope 0.5.0

Released 2026-07-31. This release is about what you can run from inside
spectroscope: a node that waits for events instead of finishing once, a real
terminal in the Files tab, reasoning controls that match the model in front of
you, and an export dialog with a preview. It is also the first release with a
Linux desktop kit.

## Nodes that wait for something to happen

`spectro node -p "..." --context <fleet> --hub <host:port>` takes three trigger
flags: `--watch <dir>`, `--listen <port>` and `--every <n>ms|s|m|h`. With one of
them the node stays up, and each firing runs the prompt again with the event
appended as context. Without them nothing about `spectro node` changed.

- A triggered node is a fleet node. It needs a context and a hub, and says so
  instead of running on its own.
- `--listen` binds `127.0.0.1` and takes a bare port; a host cannot be chosen.
  It mints a bearer token at start and prints it once to stderr. Callers send it
  back as `Authorization: Bearer`, and nothing else carries it: it is written
  into no event, no fleet roster and no session file. Only `POST /trigger`
  exists. A body over 64 KiB is refused whole rather than truncated.
- An HTTP payload arrives in the prompt inside a fence that labels it untrusted
  input data, not instructions.
- `--every` is at least one second and does not fire at start, because the
  prompt is written against an event.
- `--watch` covers one directory, not its subdirectories. When the operating
  system drops changes, the prompt says the list overflowed instead of
  presenting it as complete.
- One run at a time, and one fire waiting behind it. While a fire is already
  waiting, further file changes merge into it, a timer tick is skipped, and an
  HTTP call gets 429 so the caller stays the retry authority.
- `run_start` and the fleet roster carry the trigger that started a run. The
  field is only there when there is one, so older sessions and older nodes stay
  byte for byte what they were.

## A terminal in the Files tab

The Files tab can open a shell in the directory the agent works in. It starts
your own `$SHELL` interactively, so your prompt, your aliases and your history
are the ones you know. Ctrl-C and job control work. Up to eight terminals in a
session and thirty-two on a server.

The pane is shut until you open it, and it reopens itself only for a stored
value it can read as a clear yes.

- The terminal is yours, not the agent's. The permission gate does not apply to
  what you type into it.
- The keys the server's own process carries are stripped before the shell
  starts, so a browser-driven terminal is not handed them. Your startup files
  still run, as they do in any terminal, so a key you export from `.zshrc` is
  there the same way it always was.
- The connection is accepted only from a page on this machine, and otherwise
  refused as though the endpoint did not exist.
- `SPECTRO_SHELL=off`, or `-Dspectro.shell=off`, removes the endpoint entirely.
- It needs the `spectro-pty` helper, which the desktop kits carry. With the
  server jar or the CLI on their own, the pane says there is no terminal
  available. The helper is POSIX only, so there is no Windows path.

## Reasoning, per model

The reasoning control moved out of the header into the provider picker and
settings, where it can be about the model you actually chose. It shows a switch
where the model has one, effort levels where it has them, and nothing at all for
a model with no reasoning channel. The header's Thinking switch is gone: it
offered the same thing to models that cannot do it.

- Where a model has no way of being told to stop reasoning, off sends nothing
  rather than a field the provider ignores.
- The bundled local engine is switched through its chat template, not through
  the documented reasoning field. That was measured against the bundled
  `llama-server`, which ignores the documented one.
- Anthropic, Ollama and OpenRouter are asked what a model supports. The others
  answer from a table shipped in the release, so those rows are as fresh as the
  file.
- Effort names are the provider's own vocabulary and are not translated. An
  effort a model does not list falls back to the plain switch instead of being
  sent.
- `GET /api/models/capabilities` returns the record the UI draws from.

## Export is a dialog now

Export opens a sheet with a preview instead of a two-item menu, from the chat
and from the text feed. You pick which views go into the file and which one
leads, the theme, whether reasoning and tool calls are folded, and whether both
languages travel in one file with a switcher. The preview is produced by the
same code that writes the file.

- Print, or save as PDF, from the same sheet. Everything is opened first,
  because a folded section does not print.
- JSONL exports in three shapes: spectroscope, a Claude Code transcript, or a
  VS Code agent export. Before you choose, the dialog counts what that format
  cannot carry in this session: tool outputs, permission decisions, subagent
  lanes, token counts, generated images. A count of zero is not shown.
- A generated image is named in the file rather than embedded, so an exported
  HTML file stays a file that opens without a network. Nothing is clipped.
- The preview stops at two megabytes and says so. The saved file is whole.
- The exported HTML contains no script.
- The four export themes match the four app designs, and a test reads the app's
  own stylesheets to keep them honest.

## A fourth design, and a new default

`spectro graphite` is a plain dark grey: ground `#262624`, white text, and the
same blue accent `spectro white` uses. It declares its ground and its accent and
inherits the rest, so the spectral colours stay one set across all four designs.
Measured contrast on it: 15.2:1 for text, 8.5:1 for dimmed text, 4.7:1 for the
faintest.

A new install now defaults to `spectro white`, with particles off. A design you
have already chosen is left alone.

## Reading a tool call

A tool call renders as the thing it is wherever it appears: in the chat, the
trace, the permission dialog, the fleet gate bar and the lab. A command sits
behind a `$`, an edit shows its before and after, a question shows the options
with the chosen one marked, a file body is syntax-coloured.

- New shapes: a question, a workflow, and task creation, updates and lists.
  These come from imported Claude Code and VS Code sessions rather than from
  spectroscope's own tools.
- A long multi-line string inside a tool input is lifted out of the JSON into
  its own labelled, highlighted block, with a reference left behind so the shape
  of the call stays readable.
- Syntax colouring covers twenty languages, up from five: c, cpp, csharp, css,
  go, html, java, javascript, json, kotlin, php, python, ruby, rust, shell, sql,
  swift, toml, typescript and yaml.
- A markdown file body opens rendered. The extension decides and the content is
  never sniffed, the bytes stay one click away in the same card, and a body this
  renderer would not reproduce faithfully stays bytes and says why.
- The permission dialog shows the payload it is asking about, instead of one
  escaped JSON line. Nothing there is ever shortened, because the answer is
  final.
- One switch above the trace sets the view for every row. A row you set by hand
  keeps yours until you use that switch again. The lab's tool panel has the same
  views, with the switch above the map.
- A folded tool row shows the fields that identify the call, with a large body
  named by its line count instead of quoted.

## A second reading of the chat, off by default

The chat has two readings. `v1 · as recorded` is the transcript in stream order
with subagent turns nested inline, and it stays the default. `v2 · work panel`
puts the main agent's line of thought on the left and concurrent work in a panel
on the right. Both sit in the three-dot disclosure menu, and v2 is labelled a
prototype.

The panel covers subagent lanes, background tasks from imported Claude Code
transcripts, and triggered node runs. Where a background task reports work that
never entered this stream, the panel quotes the claim and draws no rows beneath
it, because it shows no number it cannot take you to.

## Also new

- Each session in the sidebar carries a glyph built from what it recorded: how
  many agents ran, whether a gate was asked, how it ended. Beside it are
  relative time, turns, tokens and, when the sidebar is wide enough, the model.
  Rows that look alike fold into a pile you can open. Sessions recorded before
  0.4.0 have no model and leave that column blank.
- The trace keeps every row of a finished session, so an import, an archive or a
  replay reads from its first frame. A live session is still windowed to the
  last five thousand rows.
- `durationMs` on a tool result is now execution time alone. The wait at the
  permission gate travels beside it as `gateWaitMs`, in the session file and in
  the OTLP export, where a parked gate no longer stretches the tool span in your
  observability backend. Nothing in the app displays it yet. Sessions recorded
  before this release still count the wait inside the duration.
- Switching the built-in model is a handover: the new one starts and answers
  before the old one is stopped, and a switch that fails names both models and
  leaves the running one serving. A session created before a switch cannot reach
  the port that was released; its next turn fails and names both models.
- The workspace settings panel shows each key's effective value, where that
  value came from, which scope it overrides, and the values it accepts. A
  refusal names the key it refused.
- A malformed `update_plan` from a model is answered with the keys it actually
  sent, at most four of them, key names only and never values.
- An About panel, from the right of the usage footer and from the desktop menu,
  with the version the server reports and both licences: what each one covers,
  the conditions it carries, and a link to its full text. Every term there is a
  verbatim fragment of the licence files rather than a paraphrase, and the
  attribution line has a copy button. A test reads `LICENSE`,
  `LICENSE-ASSETS.md` and `NOTICE.md` and fails if the panel drifts from them.
- Links in the desktop app open in your browser instead of a window with no
  address bar.

## For developers

- `samples/` holds eight numbered examples: six standalone Gradle projects that
  resolve spectroscope from Maven Central rather than from this repository, plus
  two README-only endpoint variants. The six are the five lines, a fleet,
  recording a run for `spectro web`, a fleet across processes, OTLP export and a
  LangChain4j provider; the two are Langfuse and Phoenix, which are the same
  exporter pointed somewhere else and so carry no code of their own.
  `samples/verify.sh` builds the six and runs the three that work offline.
- `docs/api-collections/` has all 47 server endpoints in 16 folders, as a
  Postman collection and a Bruno folder, with import notes for Insomnia and
  Hoppscotch. Host and port are variables. Each description says how the
  endpoint answers a caller that has no browser origin, measured with curl
  rather than assumed.
- `docs/INTEROP.md` describes the seams that exist in the released artifacts,
  what each one covers, and what is deliberately not integrated.
- Both suites run in GitHub Actions on every push to main and every pull
  request, and the README carries the badge. The gate reads the real test count
  out of each run and fails when it is zero, because this build reports green in
  half a second when it runs nothing.
- `SECURITY.md` describes private reporting and what is in scope. `AGENTS.md`
  states the repository's rules and gates for anyone, human or agent, sending a
  change.

## How you get it

**Homebrew, macOS on Apple silicon.**
`brew install --cask spectroscope/tap/spectroscope` installs the signed and
notarized desktop kit. Uninstalling removes the app and leaves `~/.spectro`
alone, which is where your sessions live and which the CLI and the server jar
share.

**The macOS disk image.** `spectroscope-0.5.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**The Linux kit.** `spectroscope-0.5.0-x86_64.AppImage` and
`spectroscope_0.5.0_amd64.deb`, built and smoke-tested on Linux by this
project's own CI. Both bundle their own Java runtime and `llama-server`. Nothing
in them is signed, because Linux has no equivalent gate to pass. The deb
installs as `spectroscope` and puts that on your PATH. x86_64 only.

**The jar and the CLI.** `spectro-server-0.5.0.jar` and `spectro-0.5.0.zip` run
on any machine with Java 21. They are the smallest way in, and the only way onto
a platform that has no kit.

**In your own code.**

```
dev.spectroscope:spectro-core:0.5.0
dev.spectroscope:spectro-orchestrator:0.5.0
```

Both are on Maven Central, which is append-only: 0.5.0 stands beside 0.4.1
rather than replacing it.

## Fixed

- A session id is now checked at the store instead of at each caller, and has to
  resolve to a file directly inside the session directory. Before this, the
  `resume` parameter on the WebSocket could name a file outside it, and a
  resumed session would have appended there. The server accepts connections only
  from your own machine, which is the audience this was open to. Nothing in your
  store changed by itself, and the fix needs no cleanup.
- The built-in model's catalogue and status reads now require a local origin,
  like the other local endpoints. They report how much memory and disk this
  machine has and which models are on it.
- Two development-only dependencies in the desktop lockfile were updated:
  `brace-expansion`, at the six paths that carry it, and `fast-uri`.
- A fleet client could quietly lose a frame that arrived while nothing was
  listening on its topic, and carry a wrong resume position from then on. It now
  refuses to move past the gap until the frame is delivered.
- The image gallery no longer opens itself when you open an archived session
  that happens to contain an image. It opens when an image arrives.
- After a provider switch mid-session, the agent was still described to the
  model with the previous provider's tool support. It follows the provider that
  is actually running.
- The lab's expanded view was laid out with compact spacing in places, which
  produced fourteen measured card overlaps. They are now zero, and compact is
  unchanged.

## The gate

Measured on 2026-07-31 on the release tree, with the build cache and the
up-to-date checks disabled: 1166 Java tests and 1841 web tests across 130 files,
no failures. One Java test is skipped when no live API key is present. Both
suites run the same way in CI.

## Not in this release

- No arm64 Linux build. The Linux kit is x86_64 only.
- No Windows desktop kit, and no Windows path for the terminal, which needs a
  POSIX pty.
- The apt repository at `https://spectroscope.github.io/apt` serves a signed
  index and the public key, but not the packages themselves yet, so `apt install
  spectroscope` does not complete against it. Install the deb from the release
  page.
- Translation is unchanged from 0.4.1.

## Requirements

Java 21 or newer. The macOS desktop kit is arm64, signed and notarized, and
includes its own Java runtime. The Linux kit is x86_64, includes its own Java
runtime, and is not signed. The server jar and the CLI need a `llama-server` on
the PATH (`brew install llama.cpp`) to run a local model; both desktop kits
bundle one. The terminal in the Files tab needs the `spectro-pty` helper, which
only the desktop kits carry.
