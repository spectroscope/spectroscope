# spectroscope 0.15.4

This release stops shortening old tool results by default. A local model keeps
its prompt cache, and one checkbox under Local mode turns the shortening on
again for cloud models. A playbook or workflow run now shows as a plan beside
the chat that updates itself step by step. The context ring, the Plan panel
and the System context panel say which agent they show, and one picker
switches all three to a helper. The start sheet of a
playbook says why a step's model does not answer and lets you pick another
one. `/graph` builds, shows and asks the code graph from the chat, and the
slash picker shows the subcommands and the form of each command. Stop ends a
Copilot run at once, and a wrong fleet hub port no longer keeps the app from
starting.

***

## Tool results

**Old tool results stay whole.** Until this release the app replaced a tool
result that was older than four turns and longer than 2,000 characters with a
one-line stub in every request, for every provider. Each such change makes a
local backend process the prompt again from that point. In a session we
measured on a local llama.cpp model, the requests right after a shortening
carried more than ten times as many uncached prompt tokens as the others, and
all 16 repeated reads of a file came while its earlier result was shortened.
The shortening is now off by default, and every request carries each tool
result in full.

**One checkbox.** In the composer's gear, the Local mode section has a checkbox
"Optimize tool results cache (use with cloud models only)". On, the app
shortens old, large tool results in every request again, for every provider,
the main agent and every helper. Off, it never does. Turn it on only when you
work with a cloud model, where it saves tokens. A change reaches the next
session.

**Set in your user settings only.** The checkbox writes `toolResultElision` to
your user settings, `~/.spectro/settings.json`. A settings file in a project
folder may no longer set it: the app drops the key there and says so. If you
set `toolResultElision` to `on` in a project folder in an earlier version, set
it again with the checkbox.

## Playbook runs

**A run shows beside the chat.** When a playbook run or a workflow run starts,
the Plan panel opens beside the chat and shows the run. It opens once per run:
if you close it, it stays closed. A strip under the run's name has one mark per
step, and a decision is drawn as a diamond. Below it, each step has a card with
its state, its duration, who works on it (the chat, or a helper with its role),
its model, the documents it reads and the documents it wrote. The card of the
running step shows the last line its agent wrote. A decision shows its outcome
and round, for example "Review, round 2 of 5: changes needed". A step that
waits for your answer shows as waiting, and steps the run never reached show as
skipped when it ends. A session with several runs has a picker for them. A run
that has no end in the record, because you quit the app during it, says "no end
recorded" and does not show as running.

**A wide view.** The "wide" button gives the run the whole chat tab. The chat
and the panels step aside, and "small" brings them back. The run's graph sits
at the top, and one step shows in full below it: the step that runs now, else
the last one. The step shows its input with the documents it reads, its output
with the documents it wrote, the files its agents changed, how many shell
commands it ran and the helpers of a fan-out. A click on a node of the graph
selects its step. After a reload the run starts in the compact panel again.

**Jump to the chat, open a document.** A click on a card brings the chat back
and scrolls it to the prompt the step sent, or opens the thread of the helper
that did the step. A click on a document or a file opens it in the Files panel.
A file under a folder such as `.superpowers/` opens only when the run named it
as a document it wrote, and only while the session works in the folder the run
worked in. The app never opens these this way, in any letter case: `.env` files,
including `.env.*` and `.env-*`, `.envrc`, `.netrc`, `.npmrc`, files ending in
`.pem`, `.key`, `.p12` or `.pfx`, and anything under `.git`, `.aws` or `.ssh`.

**Workflow runs too.** A workflow run started with `/playbook workflow` shows
in the same panel. Its wide view draws the steps as a chain, because a
workflow has no graph. The chat gets a start line and an end line for a
workflow run. The start line of a playbook run and of a workflow run has a
link, "open the run", that shows the run in the Plan panel.

**The Playbook view is for configuring.** The run view has left the Playbook
view. When the session has a run, the Playbook view shows a link, "Runs of this
session: open", that opens the runs in the wide view. The run panel works in
learn, light and developer mode. Sessions recorded before this release show the
plan list as before.

## Playbook start sheet

**See why a model does not answer.** Before a playbook run starts, the app asks
every provider for its model list. Each step and each review check in the start
sheet shows whether its model answers. When it does not, the row says why: the
provider rejected the key (with the HTTP status and whether the key came from
the environment of the app or was saved in the app), the provider does not
answer, the provider does not list the model, or a private step names a cloud
model. The key itself never shows.

**Pick another model per step.** Each row has a model picker. It starts on the
playbook's model and offers the models of every provider that answered. A
private step offers local models only, and an Ollama model tagged `cloud` counts
as a cloud model there. Your picks hold for this run only. The playbook folder
is not changed.

**Start waits for a model that answers.** Start stays disabled while a step or
check has no model that answers, and a line above the button names them. The
server checks your picks again when the run starts. If it refuses one, the sheet
stays open and shows why. Stop during that check cancels the start.

**The question in a run names the address.** When a step's model does not
answer during a run, the question now names the address it used, or "the
default address" of the provider, instead of "no address".

**The plan step accepts the skill's header.** The bundled planning skill writes
the head of a plan as bold fields such as `**Goal:**`. The plan check of the
bundled playbook counted only headings, so such a plan failed three times and
the run ended as cancelled. A section check now counts a heading or a bold
field at the start of a line, and its message names both forms.

## Agent views

**The agent views name their agent.** The context ring with its popover, the
Plan panel and the System context panel say which agent they show, for example
"Showing: explore-1". One picker lists the main agent and every helper of the
session, and marks the helpers that have ended. A pick in one of these views
changes all three, and so does a click on an agent in the Agents tab, which
also opens the System context panel. After a reload the views show the main
agent.

**A helper's context.** With a helper picked, the ring shows the helper's fill.
The popover shows its model and the parts of its context with their sizes.
Helpers record the sizes of their parts, not the texts, so a session file
grows only a little. The Plan panel says that a helper keeps no plan, because
the main agent keeps it.

**Plans of the run and of the model.** While a session has a run, the Plan
panel shows the run first and the main agent's own plan below it, under "Plan
of the model". A playbook run no longer replaces the main agent's plan.

## Commands

**/graph.** `/graph` works with the code graph of the session's folder.
`/graph build` builds it, `/graph update` brings it up to date with the code
that changed, and `/graph show` opens it in the browser panel, as the folder
chip menu does. The chat says what happened, for example that the graph is
current, or that graphify is not installed and how to install it.
`/graph ask <question>` sends your question to the model with the request to
answer it through the code graph. Without a graph it refuses and offers
`/graph build`. `/graph` alone and `/graph help` list the subcommands.
`/codegraph` and `/graphify` are other names for `/graph`. The command works in
the web chat, not in the terminal.

**A skill for the code graph.** Every session whose folder has a code graph
gets the bundled skill `code-graph`. It tells the model what the graph answers
and when to ask it before reading files. The setting `codeGraphBackend` names
the program that builds the graph. graphify is the only one so far.

**A skill named graph.** A skill of your own or of the working folder named
`graph` now carries its source, `user:graph` or `workspace:graph`, as a skill
named `help` or `clear` did before. `/graph` runs the code graph command.

**The slash picker shows the form of a command.** When you type a command that
has subcommands, such as `/playbook` or `/graph`, the picker lists them, each
with its help line. Picking one writes it into the box. A command that takes
words shows its form under the highlighted row, for example
`/graph ask <question>` or `/loop [interval] <prompt>`, and picking it puts the
cursor where the first word goes. Help lines and forms come in English and
German. Once you type the words after a command, Enter sends the message and
does not pick a row of the picker.

## Stop

**Stop ends a Copilot run at once.** When the local Copilot runtime ignores the
abort, Stop now ends the run after about 200 ms instead of 5 seconds. When the
runtime does not answer its ping, Stop takes about 25 ms instead of 2 seconds.
We measured both against a stand-in runtime that ignores the abort or the ping.
The runtime settles in the background, and your next prompt starts at once.

**A dead Copilot runtime is replaced.** When the Copilot runtime dies, the next
prompt of every chat starts a new runtime. Before, every chat on that model
failed with "Client closed" until the app restarted.

## Fleet hub

**Two settings.** `SPECTRO_HUB_ENABLED` switches the fleet hub on or off, and
`SPECTRO_HUB_PORT` sets its port, 7700 by default. The fleet settings have a
switch and a port field. When the app saves `~/.spectro/.env`, it adds the
defaults as commented lines, so you can see and change them. A file that sets
only `SPECTRO_HUB_PORT`, the way to switch the hub on until now, still works.

**The hub never stops the app.** The hub never binds a port under 1024, which
only an administrator may use, a port from 8080 to 8100, or the server's own
port. The settings refuse such a port. A value like `SPECTRO_HUB_PORT=1` in the
file now starts the hub on 7700, or on the next free port, and the app says so.
A port that another program holds leaves the hub off with the reason, and the
app starts normally. Doctor, in the app and in the terminal, shows both
settings and the port in use.

**The desktop app says why the server did not start.** When the server stops
during start, the desktop app now shows the server's own error at once. Before,
it waited 30 seconds and said only that the server did not become healthy.

## Sessions

**Send again in a woken session.** After a refused command, the chat no longer
offers Send again for an older prompt, also after a stored session wakes up,
after you switch sessions, in the Lab tab and in a translated view. A failed
prompt still offers Send again.

**Chat lines survive a wake.** Lines that a command such as `/playbook use`
writes into a stored chat stay visible when the command wakes the session.

**The session row follows a playbook run.** The session list shows working from
the start of a playbook or workflow run, also while the run asks its first
question, and idle again when the run ends. Before, the row said working until
you reloaded the page.

**Provider switches use the settings.** Switching the provider of a live session
now takes the provider's address from your settings, read the same way as when
the session started. A settings file in the session's working folder can set
the address, as it can at the start. A change in the settings also reaches a
new chat that has not run yet, without a reload.

## Helpers

**A message to a new helper waits for it.** When the model starts helpers and
sends one of them a message in the same turn, the message now waits in the
helper's queue and the helper reads it in its first turn. Before, it was
refused with "waiting for a free slot" although no slot limit applied. A helper
that has ended is refused as ended.

**An unread message comes back.** When a helper ends before it reads a message,
because it was stopped, failed to start or failed before its first turn, the
message goes back to its sender. The sender reads that the message was not
delivered, with the helper, the reason and the start of the message, and the
chat shows the same line. The line is kept in the session file, so a stored
session and an export show it too.

## Library API

One change in `spectro-core` breaks code compiled against 0.15.3, and one
default changes.

`CommandList.Help` is gone. `CommandList.Text` takes its place and carries
`en` and `de`. `CommandList.Command` gained `usage` as its eleventh component,
a `Text` or null, and has no constructor with the ten components of 0.15.3. A
record pattern that takes `Command` apart must name eleven components now.

`SpectroConfig.DEFAULT_TOOL_RESULT_ELISION` is now `"off"`. A null
`toolResultElision` in `SpectroConfig`, `AgentOptions` or `SubagentConfig` now
means off, so an agent you build yourself shortens old tool results only when
you set the value to `"on"`. The checkbox does not reach the embedded
`Spectro.agent()` facade or a lane of a fleet panel (`Spectro.panel()`). Both
stay off unless your program sets `AgentOptions.toolResultElision`.

These changes keep the 0.15.3 constructors:

- `SpectroConfig` gained `codeGraphBackend` as its last component.
- `AgentOptions` gained `peerReadOnSend` and `introspectionTexts` as its last
  two components, each with a builder method of the same name.
- `AgentAddress.Result` gained `nameUnknown` as its third component.
- `MessagingSeat` gained `endedChild(String)`, a default method that returns
  null.

A record pattern that takes one of these records apart must name the new
component, and two records that differ only in it are no longer equal.

`AgentOptions.introspectionTexts` set to false leaves the texts of the three
context parts off every `context_info` the agent emits and keeps their
character counts. Null or true sends the texts. The helpers the app starts set
it to false. The main agent and the CLI keep the texts.

`RunEvent.RunStep` is a new event, `run_step` on the wire, with the phases
`run_start`, `step_start`, `step_end` and `run_end`. Its `run_start` line
carries `workspaceFingerprint`, a hash of the run's folder, never the path. The
nested records `RunNode` and `RunDoc` are new as well. The existing events
`playbook_progress` and `plan` are unchanged.

`RunEvent.AgentMessage` can carry the state `returned` on a line between
agents: a helper ended with the message unread.

New types in `spectro-core`: `CodeGraphAsk`, `CodeGraphBackend`,
`CodeGraphSetting` and `CodeGraphSkill` in `dev.spectroscope.core.codegraph`,
`CodeGraphTool.Availability`, and `ModelPicks` in
`dev.spectroscope.core.playbook.run`. `SpectroConfig` gained the constants
`DEFAULT_CODE_GRAPH_BACKEND` and `KNOWN_CODE_GRAPH_BACKENDS` and helpers for
`~/.spectro/.env`. New in `spectro-orchestrator`: `HubSettings`, which reads
`SPECTRO_HUB_ENABLED` and `SPECTRO_HUB_PORT`.

## Fixes

- The local model runtime could pick a port that another program already used
  on macOS and fail to start. It now checks the port at the address it uses.
- Two saves of `~/.spectro/.env` at the same moment could lose an API key. The
  app now writes the file under one lock, in one step, readable by you only.

## Known limits

- The deprecated settings file in the folder the app was started from can
  still set `toolResultElision`.
- A settings file changed by hand outside the app reaches an empty chat only
  after a reload.
- The agent's file tools refuse to write under a playbook folder, but a shell
  command run with `run_command` can still write there.
- The hooks of a picked playbook do not run in the session.
- Refusals from the server, such as the reason a run may not start, show in
  English in the German interface.
- The context tab still lists the skills of the folder the app was started
  from, not the skills of the session.
- The run panel lists the files that the agent's file tools wrote. It does not
  list files written by shell commands, MCP tools or git. It counts the shell
  commands of a step.
