# spectroscope 0.14.0

This release makes the window lighter and long sessions quicker to open. A
switch in the header turns on light mode: the chat, the workspace, the sessions
and the skills stay, and every other view stops its work in the background. A
long recorded session reaches its chat sooner, because its trace is built later,
and shows a loading sign while it opens. A question the agent asks now reaches
you in auto and readonly mode. Every session row has a menu for rename, pin and
delete, and a new session gets a short title from its model. A subagent has a
token budget, and a shell command cut by its time limit hands back the end of
its output and ends the processes it started.

---

## First run

**Light mode is new, and learn stays the default.** The header has a switch with
two choices, learn and light. Learn shows everything, as 0.13.0 did. Light keeps
the chat, the workspace dock, the session list and the skills view, and removes
the spectrum, trace, graph, text and lab tabs, the fleets and the state graph.
The views it removes also stop their work in the background. The server records
every session in full in both modes.

**A long session opens sooner, and says that it is opening.** A recorded session
no longer builds its trace before the chat shows. The trace is built when you
open its tab, or once the window is idle. After a short delay, a slow open shows
a sign with the session's title and a count of the events read so far. The
window keeps drawing while it does. Numbers are under Opening sessions.

**Questions reach you in auto and readonly mode.** In 0.13.0 the agent's
questions went unanswered at once whenever the session ran in auto or readonly
mode. In a session in the app a question waits in the answer bar until you
answer, in every permission mode. Tool calls in auto mode still run without
asking. If you leave an auto run open in the browser, it can now stop at a
question and wait there until you come back.

**Session rows have a menu, and new sessions get a title.** A three-dot button
at the right end of each stored session row opens Pin, Rename, Suggest a title
and Delete. When a new session starts its first run, the server asks the
session's own model for a title of three to five words in the language of the
first prompt. The row shows that title and keeps the first prompt in its
tooltip.

**The skills view reads like the settings page.** It is a column as wide as the
settings page, starting at the left. Installed skills are grouped by pack and
start collapsed. Each row has its switch before the name.

**The thinking view keeps up with a fast model.** It follows its newest line
until you scroll it yourself, including the last lines of a block. One scroll
back toward the end makes it follow again.

**A subagent stops at ten million tokens.** The new setting
`subagentBudgetTokens` caps what one child agent may spend. It ships at
10,000,000 tokens, counted as input plus output.

**A cut shell command hands back its output and ends what it started.** A
command that reaches its time limit returns the end of what it printed. A time
limit or Stop ends the command's shell and the processes below it.

**Auto mode no longer flashes the permission window.** A tool call that the mode
or a saved rule already allows opens nothing, and the working line at the bottom
of the chat stays put.

**The working folder sits above the input on a new chat.** The folder choice
moved from the middle of the empty screen to a row directly above the message
field, with a named entry for no folder. The row leaves once the first run
starts.

**To keep 0.13.0's behaviour while you upgrade**, there is little to set. Learn
is the default, so the window looks as it did until you switch. If a child agent
of yours needs more than ten million tokens, raise `subagentBudgetTokens` in
`~/.spectro/settings.json` before the first run. Questions in auto mode, the
session titles and the new folder row have no switch. A title request sends the
first prompt to the session's model a second time, and a paid backend bills it.

## Light mode

The switch, labelled Mode, sits in the header beside the language toggle. Each
choice has a tooltip that says what it shows. Tab reaches the switch, the arrow
keys move, and Enter or Space chooses.

Light keeps the chat, the workspace dock (files, terminal and browser), the
session list and the skills view. It removes these:

- the spectrum, trace, graph, text and lab tabs
- the fleets and the fleet parts of the sidebar
- the state graph
- the level pill and the level panel
- the live trace switch in the chat menu
- the fleet section of the settings page, which the settings search then does
  not find either

The tab row goes too, and the chat takes its place. While the tutorial is on,
that is with leveling set to ladder or checklist, the row stays with the chat
tab and the level pill. The back and forward buttons and the translate toggle
live in that row and leave with it. Cmd+Left and Cmd+Right still step back and
forward, and the translation sheet in the chat menu still leads back to the
original.

A switch takes effect at once, without a reload or a server request. If the view
on screen is one that light removes, the window moves to the chat of the same
session and the address follows. An address that points into a removed view,
such as `#/lab` or a session's trace, opens the chat instead. A scenario opens
in the chat, not in the Lab, and a fleet scenario does not open. In the desktop
app, the menu entries for the fleets and the state graph do nothing in light.

Light stops the work behind the removed views. It builds no trace rows, does not
prepare the trace view in the background, feeds neither the Lab nor the fleet
view, does not ask the server for the fleet list at start, and does not ask for
a session's llm wire index when the session opens or resumes. The removed views
load from files of their own, and light never downloads them. Learn downloads
them once the window is idle after its first render, so the first click on a tab
does not wait.

Back in learn, the trace is rebuilt from the events of the session, keeping the
newest 5,000 rows as a live session always has, and the Lab and the fleet list
are filled again. With the live trace switch off, no trace rows are built.

The mode is kept per browser, and other windows of the same browser follow a
switch at once. The desktop app and a browser tab each keep their own mode.

We measured learn and light on a recorded session of 91,956 events in Chrome at
1440 by 900, three alternating pairs, medians:

| | learn | light |
| --- | --- | --- |
| Script loaded before the first click | about 1.8 MB in 23 files | about 1.2 MB in 1 file |
| Click on the session to the chat drawn | 1.40 s | 1.52 s |
| Script memory after the open, after garbage collection | 112.5 MB | 91.1 MB |
| Resume the session until it reads resumed | 4.11 s | 1.55 s |
| Memory of the server process after the open | 704 MB | 708 MB |

The open takes about the same time in both modes, because learn no longer builds
the trace before the chat shows either. Light changes nothing on the server.
Going back to learn on that resumed session took one task of 200 ms. The desktop
app was not measured.

Light offers no download link for the llm wire record, because it never asks for
the index. If a separately loaded view cannot be downloaded, its place reads
"This view did not load. Reload the window to fetch it again." with a button
that reloads the window. The rest of the window keeps working.

## Opening sessions

Opening a session from the list, resuming one, following a link to one and
importing a transcript show a sign over the current view. It holds a spinner,
the session's title, the line `Opening session` and a count such as `40,000 of
91,956 events`. The sign fades in after 150 ms, so a quick open shows nothing.
With reduced motion set in the system, the spinner stands still and the text
carries the state. If the open fails, the sign goes and the previous view stays
as it was. A click on another session during the open stops the first one, and
only the second appears.

The window keeps drawing while a session opens. The events are read in small
slices with a pause for the browser between them. In our tests on a recorded
session of 91,956 events, the longest gap between two frames while the events
were read went from 2.2 s in 0.13.0 to between 26 and 34 ms. The slices alone
do not make the open faster.

Building the trace later is what makes the open faster. A recorded session opens
without its trace rows. They are built the first time you open the trace tab, or
once the browser is idle after the chat shows, under a sign that reads `Building
the trace`. The trace keeps every row. The session's llm wire index is fetched
after the chat shows, and the count on the trace tab appears when it arrives,
about a second later, in a place held for it from the start. On the same
session, click to chat went from 4.1 s to 1.0 s, median of three alternating
pairs against the build before this change. Opening the trace tab right after
the chat now takes 0.5 s instead of 0.1 s, because it waits for the index.
Opened a few seconds later, it is as fast as before.

The server answers the index faster too. It reads the llm wire record as a
stream and skips the message bodies. The answer is the same byte for byte. On a
record of 251 MB, one index request went from 596 ms to 154 ms, and the server
process peaked at 0.4 GB during the request instead of 2.0 GB, median of five
alternating requests against 0.13.0. A line with a byte that is not valid UTF-8
now costs only that line. Before, it cost the whole index.

## Questions

In a session in the app, `ask_user_question` now waits for your answer in every
permission mode. In 0.10.0 to 0.13.0, auto and readonly mode answered it as
unanswered on the spot, without showing it. The question shows in the answer bar
and the run waits until you answer. There is no time limit. Closing the tab
cancels the run and releases the question. Tool calls that need permission are
unchanged: auto mode allows them and readonly mode denies the risky ones,
without asking.

The progress guard asks through the same bar. When it stops a run that is going
nowhere and asks whether to carry on, change course or end it, a run in auto or
readonly mode now pauses until you answer. In 0.13.0 it warned and the run went
on.

The hint for auto mode in the composer's mode menu reads "Allows every tool call
automatically, without a permission request (demo mode). The agent's own
questions still reach you."

Once a question is answered, its folded row in the chat shows the answer, for
example `answer: SQLite`, where it used to show the raw input. The whole answer
is in the row's tooltip. Several answers are joined with ` · ` in question
order.

`spectro run`, scheduled fires and fleet nodes are unchanged. They have no
question tool, and their system prompt tells the model not to ask.

## Session list

Every stored session row has a three-dot button at its right end. It shows when
you hover the row or reach it with the keyboard, and always in a window narrower
than 768 px. The live row, scenarios and fleets have none. The menu holds:

- Pin, or Unpin on a pinned row
- Rename
- Suggest a title, on a row that has no title yet
- Delete, set apart and in the danger colour

The menu works from the keyboard. Enter, Space or the down arrow opens it on the
first item, the arrows move and wrap, Home and End jump, and Escape closes it
and returns to the button.

Rename turns the title into a text field with the title selected. Enter or
leaving the field saves, and Escape cancels. An empty field brings back the
suggested title, or the first prompt when there is none.

Pin moves the session into a group named Pinned at the top of the list, above
the live row, and the other sessions then sit under Recent. With nothing pinned,
the list has no headings, as before. Both groups are sorted by date, newest
first.

Delete asks once, in a small dialog that names the session and says that the
recording and its files are removed from this machine. While the session is live
in a window, Delete is disabled, and its tooltip asks you to stop or close the
session first. If the session you delete is on screen, the view goes back to the
live chat.

Titles and pins live on the server in `~/.spectro/session-meta.json`, so the
desktop app and every browser see the same list. They survive a reload and a
restart, and a delete removes them with the session. The session file itself has
no new field.

When a new session starts its first run, the server asks the session's own
provider and model, in the background, for a title of three to five words in the
language of the first prompt. It sends the first prompt only, cut at 1,200
characters, with no tools and with thinking off, caps the answer at 256 tokens
and gives up after 30 seconds. The run never waits for it. The answer is cleaned
to one line of at most 80 characters. If the request fails, the row keeps the
first prompt, and the server log names the session and the reason. The prompt
stays out of the log. A title you set by hand is never replaced by a suggestion.
The title request is not written to the session file or to its llm wire record.

Sessions from before this release keep their first prompt as title. Suggest a
title asks for one, one session at a time. Nothing asks for titles for the whole
list.

The server has two new routes for this, behind the same local checks as delete:
`PATCH /api/sessions/{id}` with `title` and `pinned`, and `POST
/api/sessions/{id}/title/suggest`. `GET /api/sessions` carries `title`,
`titleSource` and `pinned` for a session that has them.

## Skills view

The skills view is one column, as wide as the content of the settings page (646
px), and starts at the left edge of the view. Before, it ran the full width of
the window, and on a wide screen a short description sat far from its button.

The installed list is grouped like the catalogue. Skills without a pack come
first, then one group per pack, sorted by name. Each group starts collapsed and
its header says how many of its skills are installed.

Every row, installed or in the catalogue, has its switch at the left, before the
name. A remove button follows the row's text instead of the window's right edge.
Hovering or focusing anywhere in a row highlights the whole row. The pack
headers keep their install and remove buttons at the right.

A screen reader hears which skill a control belongs to. A switch in the
installed list reads `enable <name>`, one in the catalogue `install <name>`, and
the remove button `delete <name>`. The rows of MCP servers on the settings page
share the row style and get the same padding, highlight and button placement.

## Thinking view

The thinking panel follows its newest line during a fast stream. In 0.13.0 it
could stop following on its own: when the page was slow to render, the panel's
own scroll arrived late and read as yours. The panel tells its own scrolling
apart from yours. A wheel, a touch, the scrollbar or a scrolling key inside the
panel stops the follow. New text never moves a panel you have scrolled away.

Two more things changed. The lines that arrive together with the end of a block
are shown too. Before, a finished block often ended a few lines short of its
bottom. And when you scroll back toward the end, to where you left, the panel
follows again. A single wheel notch is enough. A drag of the scrollbar thumb
still has to reach the bottom.

In our tests, three-second streams at 83 and 142 lines a second ended with the
newest line in view 24 of 24 times, against 9 of 24 on 0.13.0 (an earlier run of
the same test read 4 of 24), in both designs at 390 and 1440 px. The Spectrum
lanes use the same panel and get the same change. They were not measured.

## Token budget

`subagentBudgetTokens` is a new setting under Settings, Permissions, next to the
other limits on one run, labelled Tokens per subagent. It ships at 10,000,000,
and its floor is 1.

It counts the input and output tokens a child agent's backend reports. Tokens a
prompt cache reads or writes are not counted. When a child starts a new turn
after its spend has passed the budget, it is cut, and its run ends with the stop
reason `child_token_budget_exhausted`. The parent receives an error line that
names the spend, the budget and the setting, for example:

```
ERROR: [<child>] out of tokens: <spent> spent (<in> in / <out> out), past its budget of <budget> (subagentBudgetTokens). Raise subagentBudgetTokens in the settings, or cut the subtask smaller.
```

Below that line comes the text of the turn that passed the budget, if it wrote
any, under the same unfinished marker a child cut by its time budget gets.

The cut comes when the child starts its next turn. The model request of that
turn has already gone out, and it is cancelled at once. It is not in the count,
and a paid backend may still bill its input.

Each child has its own budget. Four children started in one call can together
spend forty million tokens. The turn ceiling `maxTurns` stays shared by parent
and children, as in 0.13.0.

## Cut commands

A shell command cut by its time limit now hands back what it printed. The tool
result starts with the error line, which also names the setting to raise:

```
ERROR: command timed out after 900 s. Raise commandTimeoutSeconds if the command needs longer.
--- what the command printed before its time limit cut it, unfinished ---
```

The output follows the marker line. It is the end of what the command printed,
up to 10,000 characters, because a build prints its failure last. For scripts
such as Chinese or Japanese the kept end is shorter, about 3,300 characters. A
command that printed nothing gets the error line alone. The result is still an
error, and the tool card stays red. A goal check cut by its time limit now gives
the end of its output as its reason.

A cut also ends the processes the command started. On a time limit or a Stop,
spectroscope collects the processes below the command's shell, ends the shell,
then ends each of them. After a time limit or a Stop it waits up to two seconds
for them to be gone. In 0.13.0 a command such as `make && make test`, `a; b` or
`a | b` could leave processes running that nothing in the app showed. Hooks and
goal checks get the same. A command that ends on its own within its limit keeps
anything it started in the background with `&`.

## Permission window

A tool call whose answer is known before anyone is asked opens nothing. That is
a call that auto or readonly mode decides, or one a saved allowlist rule allows.
In 0.13.0 the permission window opened and closed again on every such call, and
the working line at the bottom of the chat jumped with it. The working line
counts on without a gap. A request that waits for you opens the window as
before.

The chat also stays at its bottom without a jump. It used to scroll to new rows
after the browser had drawn them, so the working line dropped by one row for a
frame and came back. It scrolls before the frame is drawn, and a new turn no
longer glides into view.

## Working folder

On a new chat, the working folder is a row directly above the message field,
centred, with 24 px of space above and below it. It used to sit in the middle of
the empty screen. The row reads Working folder and offers three choices:

- No folder: a run then gets a temporary folder of its own
- Default: the default working folder from the settings, or a fallback folder
  when none is set
- Choose folder…: pick a specific folder

The row names the folder in use and shows its full path on hover. A temporary
folder is marked as such. When a resumed session's folder is gone, the row says
so, for example `ForgeDemo is no longer there`. The row leaves when the first
run starts and does not come back in that chat. A prompt the server refused,
before any run started, leaves the row in place, so you can pick another folder.
A resumed or recorded session never shows it.

**A reopened session names its folder.** The Files panel of a stored session
opened from the list names the folder it ran in, with the note "This chat worked
in this folder. The path comes from the chat's own record; nothing on disk is
read." It used to say that no working folder existed yet. Sessions recorded by
0.10.0 or older, runs started by a fleet trigger and runs started without a
working folder have no folder on record and keep the old sentence.

**The status line joins the input area.** The line between the input area and
the status line under it is gone, and the status line has no background of its
own. The change applies under every view. The line above the input area, between
the history and the composer, stays.

## Tool cards

With rtk on, a tool card now shows the command that actually ran. The command
region prints the rewritten line after `$`, with `rewritten by rtk` beside its
label. A second region, As the model wrote it, prints the model's own line in
plain text. This holds in every permission mode, auto included, where 0.13.0
showed only the model's line. A command rtk did not rewrite shows one line, as
before. An exported chat shows both lines too. The rtk version beside the switch
in the three-dot menu no longer wraps at a phone width.

A folded tool card carries its one-line summary as a tooltip, so a summary cut
off in a narrow chat can be read on hover. On an answered question the tooltip
holds the whole answer.

## Import message

The bar after an import says what was opened in plain words:

```
Opened notes.jsonl: 14 prompts, 293 answers. The session is shown here only and not saved.
```

In German it reads "notes.jsonl geöffnet: 14 Eingaben, 293 Antworten. Die
Sitzung wird nur angezeigt und nicht gespeichert." A subagent transcript says
"The transcript is shown here only and not saved." Prompts count what the chat
shows on the person's side, steering messages included.

The file's own numbers sit behind a Details control on the bar: lines in the
file, frames, and lines not matched. The bar no longer warns about lines not
matched. On a Claude Code transcript that number is almost never zero, because
such files hold titles, reminders and other records that belong to no
conversation, and the importer skips them on purpose. Numbers are grouped for
the language of the interface.

A file name that contains `$&` or a similar pattern no longer garbles the
sentence. The same fix reaches the exported chat and the voice setup notes.

## Settings search

The settings search finds a field by the name the page shows beside it, in
English and German. In 0.13.0 only the settings key and the section heading
found a field, so "Time per subagent" found nothing. A result row reads the
name, then the key, for example `Tokens per subagent · subagentBudgetTokens`.

## Session links

A link to a session, `#/session/<id>`, opens that session again when the app
loads with it. In 0.13.0 such a load ended on the start page and opened nothing.
A link with an event, `#/session/<id>@<n>`, opens the trace at that event, and a
link opened on a server that has not built its session index yet works too.
After a link, the back and forward buttons count the page it opened.

## Answer line

The line under an answer keeps its own numbers. In 0.13.0, when the next model
turn only called a tool, its usage replaced the tokens and duration of the
answer above it. That turn's tokens count toward the run total only and draw no
line of their own.

## Prompt caching

On Anthropic, a tool loop now caches its conversation. The cache breakpoint for
the conversation sits on the last message before the current turn. Inside a tool
loop that message ends in a tool call, and a tool call could not carry the
breakpoint. So every round after a tool call sent its whole history at full
input price. A tool call now carries it. A request places up to three
breakpoints: the system prompt, the tool list and the last stable message. We
checked where the breakpoints sit in the requests the provider builds. We did
not measure the bill against the live API.

## Recordings

`permission_request` has a new optional field, `decidedBy`. It reads
`mode:auto`, `mode:readonly` or `allowlist` when the answer was known before the
request was written, and it is absent when a person decides. Sessions in the app
write it. `spectro run` and the terminal face write requests without it. A
session recorded before this release has no such field, so its replay still
opens the permission window for a moment on each gated call.

A child agent's `run_end` can carry the new stop reason
`child_token_budget_exhausted`. The `tool_result` of a `run_command` cut by its
limit carries the output after the marker line shown under Cut commands.

A reader of your own that fails on an unknown field or stop reason needs the new
values. Push one line of each through it before you rely on it.

Two writers can no longer tear a line of a session file. The run's events and
the llm wire exchanges could be written to the same file at the same moment, and
one line could end up inside another. Every write to a session file in one
server process waits for the one before it. A line spectroscope cannot read is
skipped, and the rest of the file is read. The server log,
`~/.spectro/logs/spectroscope.log`, names the session and the line number and
leaves out the line's content. Before, a tear inside a multi-byte character, an
umlaut for example, made the whole session unreadable: it vanished from the list
and could not be resumed. A file torn before this release is not repaired.

## Library API

No public member of the 0.13.0 API was removed, and no constant changed its
value. Code compiled against 0.13.0 still runs. `spectro-orchestrator` has no
change to its public API.

`RunEvent.PermissionRequest` gained `decidedBy` as its fifth component, before
`ts`. Its five-argument constructor from 0.13.0 is still there. A record pattern
that takes `PermissionRequest` apart must name six components now.
`stamped(String)` returns a copy with the mark set.

`PermissionBroker` gained `decidedBy(PermissionRequest)`, a default method that
returns null. A broker of your own needs no change, and its requests go out
unmarked, as in 0.13.0.

`SpectroConfig` gained `subagentBudgetTokens` as its last component, and
`SpectroConfig.DEFAULT_SUBAGENT_BUDGET_TOKENS` is 10,000,000. `SubagentConfig`
gained the same component, 16 in all, and a builder method for it. Both keep
their constructors with the exact 0.13.0 shapes. A `SubagentConfig` built with a
budget of zero or less throws an `IllegalArgumentException` that names the key.
A `SubagentConfig` built through its 0.13.0 constructor, or through a builder
that never sets the value, runs its child under the 10,000,000 token cap, and a
child past it is cut at its next turn with the stop reason
`child_token_budget_exhausted`.

New constants: `ChildBudget.STOP_TOKEN_BUDGET_EXHAUSTED`,
`StandardTools.CUT_OUTPUT_MARKER` and `ShellCommand.REAP_GRACE_MS`, which is
2,000 ms.

## Known limits

- **The host guard reads only the command line.** A command that hides its
  target still runs, for example `kill $(cat app.pid)`, a process number kept in
  a variable, or a script that stops the app. A line the guard cannot read runs
  unchecked. The fleet hub's port, when you turn the hub on, is not protected.
- **A cut can miss a process.** The processes below a cut command are collected
  once, at the cut. A process that detached itself before, for example with
  `setsid`, is not reached. A process that forks a new one between the
  collection and its own end leaves that one running. In a probe that forked
  every 3 ms, 3 of 20 cuts left one process behind.
- **The token budget counts after the fact.** The request of the turn a child is
  cut in reaches the backend before it is cancelled, and a paid backend may bill
  its input. Each child has its own budget, so several children can spend
  several budgets.
- **Compaction does not survive a restart.** A session resumed after the app
  restarts rebuilds its whole conversation, including what had been compacted,
  and sends all of it on the first turn, because a run cannot compact before its
  second turn.
- **A question has no time limit.** A run in any mode waits at a question until
  you answer or close the tab.
- **Light leaves a few links to the trace in place.** Rows in the dock that open
  a row of the trace, in the work panel and the Lab dock, stay visible in light
  and do nothing there. Back in learn, the rows for messages this window sent
  while in light, and for a resumed session's marker and its llm wire exchanges,
  are not rebuilt.
- **The first trace open waits for the index.** Opening the trace tab of a
  recorded session right after the chat takes about half a second. If the server
  never answers the index request, the sign stays over the trace tab.
- **A title request shares the backend with the run.** A local server that
  answers one request at a time can hold one of the two behind the other for a
  second or so.
- **Narrow windows lose controls.** In a narrow window, tabs can disappear off
  the tab strip with no way to scroll to them, and the right dock can squeeze
  the chat. At a phone width, the sidebar opens on top of the welcome screen and
  covers its three buttons; close the sidebar with its own toggle, then choose.
  Also at a phone width, the right dock opened on Files can be too narrow to
  use, and the skills view runs past the right edge of the screen.
- **rtk shows its rewrite on the tool card only.** The trace's tool section and
  the Lab's shell station still show the model's line.
- **rtk, steering and the session window reach the app's sessions only.** Child
  agents do not use rtk. `spectro run`, scheduled fires, fleet nodes and the
  terminal face have no rtk, no steering and no way to set the window.
- **A subagent cut by its time or token budget hands back its last turn only**,
  not the text of its earlier turns.
- **The context popover's headline is in English** in both languages. The window
  field under it is translated.
- **The desktop kits are built per platform.** The disk image is Apple silicon
  only and the Linux kit x86_64 only. A kit built without a Developer ID and the
  notary profile is signed ad hoc, and macOS then asks once: right-click, Open.

## Getting it

The channels are the ones 0.5.0 shipped. Nothing new this cut.

**Homebrew, on macOS.** `brew install --cask spectroscope/tap/spectroscope`
installs the signed and notarized desktop kit.

**The macOS disk image.** `spectroscope-0.14.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**apt, on Debian and Ubuntu.** The signed repository at
`https://apt.spectroscope.dev` serves the deb once this version enters the pool.
Check `apt policy spectroscope` before assuming `apt upgrade` carries you here.
x86_64 only.

If nobody is at the keyboard, use `sudo DEBIAN_FRONTEND=noninteractive apt
install -y spectroscope` instead of the documented line. The plain line waits
for you twice, and in a container neither question is answered: apt asks you to
confirm the download, and on an image where `tzdata` has never been configured a
package further down the chain asks which timezone you live in. Neither one
times out.

**The Linux kit.** `spectroscope-0.14.0-x86_64.AppImage` and
`spectroscope_0.14.0_amd64.deb` on the release page, built and smoke-tested on
Linux by this project's own CI. Both bundle their own Java runtime and
`llama-server`. x86_64 only, not signed.

**The jar and the CLI.** `spectro-server-0.14.0.jar` and `spectro-0.14.0.zip`
run on any machine with Java 21. They are the smallest way in, and the only way
onto a platform that has no kit.

**In your own code.**

```
dev.spectroscope:spectro-core:0.14.0
dev.spectroscope:spectro-orchestrator:0.14.0
```

Read Library API above before you upgrade a build that compiles against 0.13.0.
Maven Central is append-only, and 0.9.0's libraries were never published there,
so the gap where 0.9.0 would sit stays visible. If the coordinates above answer
404 for you, the publish has not propagated yet.
