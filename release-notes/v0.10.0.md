# spectroscope 0.10.0

Released 2026-08-19, 21 merges after 0.9.0. Two lines of work run through it.
A child agent can now finish its work and reach what its parent reaches, and
what it said comes back into the transcript instead of being lifted out of it.
And a run reports on itself honestly: an agent can stop and put a decision to
you rather than guessing, and a run that walks away from its own plan half way
says so instead of reading as done. The rest is 0.9.0's workspace under five
days of real use — the app opens on its greeting again, and the transcript
stays where you put it while a run streams.

## Subagents can finish, and reach what their parent reaches

An agent can hand part of its work to a child agent: a second run with its own
context and a role that decides what tools it gets, whose answer comes back to
the parent. Whether a child gets spawned at all is the model's decision. This
release makes the offer affordable and able; it does not make it automatic.

A child used to be killed after two minutes, counted from the moment it was
spawned rather than from the moment it started answering. Against a local model
that is not a budget: over one measured session the median turn took 92
seconds, and 7 of 15 measured exchanges ran longer than a child's entire
allowance. On that backend a child would have been cut off mid-thought about
half the time, with the tokens already paid for — which is part of why, across
324 consecutive sessions, no run spawned one at all.

The limit is derived now, from the parent session's own measured turns: three
times the running median, with a floor of five minutes and a ceiling of thirty
minutes. It runs on two clocks. The work budget starts at the child's first
token, so a child queued behind a busy backend does not spend its allowance
waiting, and a separate queue grace, counted from the spawn, only asks whether
the backend ever began. A child that does run out says which clock it hit, and
the result handed back to the parent names the clock and the derivation.
Before, it said only that a timeout had happened, with no clock and no
derivation — and for a short budget it could print `timeout after 0 s`. From a
run against a slow local model: the first token arrived 128 seconds after the
spawn, which the old limit would not have survived, and the child then worked
another 232 seconds and ended on its own.

The tool belt is assembled once and handed to parent and children alike, so a
tool you add cannot silently miss the children. In the app a worker child
reaches the browser tools, the launch tools, image generation, the three web
tools and every MCP server you configured. On the command line it reaches image
generation, the three web tools and your MCP servers — the same belt its parent
has there. What a role gives up is declared in the role instead of in the
wiring. `update_plan`, `ask_user_question` and the spawn verbs stay with the
main agent: a child cannot spawn children, and a child cannot park you behind a
question you never approved. Four children still run at once.

**What the wider belt means for you.** A worker child now leaves the machine.
`web_search`, `web_fetch` and `browse_page` ride into every worker child, where
before only the research role reached the web. A child also reads the browser
page you have attached, searches it, reads its console, lists your launch
configurations and reads their logs, and asks you nothing for any of the five.
That is on purpose: a child holds the parent's own tool instances, so gating
those reads for children would have started prompting you on every page read of
your own. Every other newly reachable tool asks per call, under the child's own
name, so you can see which child wants what. Four workers can be asking at
once, so a busy fan-out produces noticeably more prompts than a single agent
does.

## A child's words come back

Since before 0.9.0 the transcript has had two readings, chosen in the
three-dots menu and still marked *prototype* there. `v1 · as recorded` nests a
child's turns inline in stream order. `v2 · work panel`, the default, keeps the
main agent's line of thought on the left and puts each child's metrics — name,
state, tokens, tool calls — in a panel on the right.

In the default reading a child's turns were lifted out and a small marker, a
chip, was drawn where they had been. The panel that chip led to has no field
for text. So a child's answer, its reasoning and its tool output were on screen
in neither place. On one three-child session, 66 of 72 turns and 7,248
characters of the children's prose reached no screen at all.

Nothing was ever lost on disk, so it comes back the moment you click. The chip
opens in place and shows that child's turns, drawn by the same renderer `v1`
uses. Closed is the default, and a saved run opens and closes exactly like a
live one. The chip is two controls now: the body opens the child, and a small
button at its trailing edge still jumps to the panel. One control doing both
jobs silently is how the confusion started.

Opening a chip also collects a child that the older reading scatters. In that
same session `v1` broke one worker into 25 separate blocks for 27 turns; the
opened chip gives each child one section. Opening it does not fight your
scroll: at the live edge you stay pinned, and if you have scrolled up, the chip
you clicked stays exactly where it sat.

## The run can ask you

An agent that reached a decision it could not make used to guess, and you found
out afterwards. It can stop and ask now: one question, up to four choices, and
a text field when none of them fit. The run waits until you answer and then
carries on with what you picked.

Waiting is not counted as work. Measured live: an answer given after three
minutes left the tool's own duration at zero, and a second question drew
`0.0 s` of work beside `waited 51 s for you`. A slow human never lands in a
readout about a slow model.

Nothing on any path invents an answer. Escape does not answer. Skip releases
the question without one, and so does closing the tab, aborting the run, or a
permission mode that runs unattended. The model is told nobody answered, which
is not an error and does not invite a retry.

The tool is registered only where a person is actually there: a session in the
app, and the interactive command line, which prints the numbered options and
reads your choice. Headless runs, scheduled runs, fleet nodes, runs driven from
your own code and child agents never see it in their tool list, so a model in
those places cannot plan around a question nobody would hear. One run may ask
three questions; the fourth is refused.

The fleet monitor shows a waiting question without you opening the node: the
run's row marks it in the colour the app already uses for waiting, and a folded
fleet card raises a member's question to the top. The answer bar says where
your answer goes — into this session's transcript. It is not a place for a key
or a password. Questions inside an imported transcript stay what they are, a
record of an answer someone else already gave, with no live controls.

## A run that stops mid-plan says so

A run that stopped mid-plan looked exactly like one that finished, on every
surface. A model that wrote a six-step plan, did two of them and then answered
in prose ended the run with `end_turn`, and the footer said `ready`.

The run is graded against the plan it kept now, and the verdict is one of
three: finished, unfinished, or unknown when no plan was ever written. Three
places state it. The footer under the chat reads `stopped · 2 of 3 steps open`.
The interactive command line's run-end line reads `◆ unfinished · 2 of 3 steps
open`. The exported HTML reads `ended: unfinished · 1 of 2 steps open`. All
three are drawn from one rule, so they carry the same verdict and the same
count and an archive read months later does not disagree with the app it came
from.

Unknown is an answer of its own wherever the verdict is drawn. On a small local
model no plan is usually written at all, and the footer says `ready · no plan
on record` rather than claiming a clean end it cannot see. A run that stopped
with steps open no longer earns the first-run step on the progress ladder that
unlocks features as you use the app.

## The harness holds the run instead of handing it back

A run that stops with plan steps still open no longer only says so. On a
voluntary stop the harness starts another turn by itself, with a message it
writes: the steps that are still open, in their own words, and which
continuation this is out of how many. It needs nothing from the model, no tool
call and no cooperation, which is the whole point — the local backends this was
built against report that they are not trained for tool use, so a mechanic the
model has to ask for is missing exactly where it is needed. The budget is three
continuations per run, `continuationBudget` in the settings file, and zero
switches it off.

It refuses to spin. A stop carrying the same plan as the last continuation,
with no tool call that came back clean in between, is not continued again. On a
small local model told to touch nothing after writing its plan: one
continuation, then the refusal. Spending the budget is an ending of its own,
distinct from a clean finish and from a plain unfinished — the run says it was
continued and still ended with steps open. Only the voluntary exit is ever
re-entered; a run that hit the turn cap, ran out of tokens, was aborted or
errored already says something else ended it, and re-entering would spend the
same context against the same wall. The command line prints a line for each of
the three outcomes: `◈ continued  continued: 3 of 4 steps open, continuation 1
of 3`.

The turn cap stops being invisible with it. It was 15 and stays 15, but it was
a private constant and is a setting now, because a continuation raises the
effective ceiling, and a ceiling that is the product of two numbers, one of them
unreadable, is not one anybody can reason about.

**You can also say what a run is for.** A goal is an outcome in your own words
plus a shell command whose exit code is the verdict. On the command line `/goal`
has four forms — show, set, check, clear — and without a check it tells you the
run would be reported untested. There is no tool for stating one: a
model-written goal is a run defining its own success. It is a file, one per
session under `~/.spectro/goals`, in the shape `AGENTS.md` is already read in,
and the loop re-reads it every turn, so an edit in a text editor takes effect
without reconnecting.

It reaches the model on every turn, verbatim, riding the system prompt, which is
the one part summarizing a long history never rewrites — so it holds whatever
threshold the next section derives. It ends by telling the model not to report
the goal as met: say what you did and what you observed, the check decides. The
section costs 77 prompt tokens a turn for a 326-character goal, measured on the
local model this house tests against.

The check runs once, at the exit that would otherwise end the run, through the
same permission gate every tool blocks on, and it asks you once per run per
command. Exit 0 and the run is done and names the command that said so.
Non-zero and the run carries on with the check's own failing output as the
guidance, paid out of the same continuation budget, so the bound stays one
number rather than two. Not runnable, timed out, or denied at the gate and the
run ends untested, never met. The timeout is ten minutes, and a timeout is
untested rather than failed, because a check that hung is a statement about the
check. A run that hits the turn cap keeps that name and gets a verdict too;
that one was found by a live run rather than by reading the change. Three runs
on the small local model: a check that could never pass ended unmet, a green
suite came back met at exit 0 while the model claimed nothing at all, and
against a red suite the harness handed the model the failing output, which it
read, ran, edited and re-ran until the second check exited 0.

**And a run that is going nowhere gets stopped.** What started this: a local
model wrote a test its own implementation could not satisfy, saw it fail, and
instead of repairing either side copied the file under a new number and wrote
the same failing test again. Thirty-one files, one distinct content, 283 bytes
each, at roughly 90 seconds a turn for about an hour, with the harness watching
and saying nothing. It broke out of it by itself in the end, so the loop was
escapable; it just took 31 copies.

The harness notices at three now. Identical bytes written to a new path three
times, or the same command failing three times on byte-equal input, stops the
run and asks you: carry on, change course, or end it. The question names which
of the two fired, the count and what it saw. Carrying on stands that detector
down for the rest of the run; changing course only clears its memory, so a
model that walks back into the same loop has to earn a full three again. With
nobody to ask, the run carries on and the net stays up. A third detector, a
plan whose steps have not advanced across a number of turns, is built and ships
off: a weak local model often keeps no plan at all, so it is the third net and
never the first. The three numbers are `progressGuardWrites`,
`progressGuardFailures` and `progressGuardPlanTurns`. There is a floor of 64
characters under the first, so a scaffold writing empty files is not a loop.

The three sit at different points of one loop, and the order is settled rather
than raced. The guard runs inside a turn and speaks first: a run it ends is
ended, and is not graded afterwards, because ending it was your answer. The
leash and the check both sit at the exit, and where a goal is stated the check
takes that exit instead of the plan ledger — the only way two graders never
disagree is if exactly one of them grades. A call the guard blocked never ran,
so it is not progress for the leash either, and the stop that follows it is not
continued.

All three ship only where a person is there: a session in the app, and the
interactive command line. Headless runs, scheduled runs, fleet nodes, triggered
nodes and child agents get none of them. On the two attended faces this is a
live behaviour change when you upgrade — a run that used to hand control back at
its first stop now continues up to three times by itself.

## The window you loaded is the window you get

A session summarized itself away at 100,000 tokens however much the model could
hold, and the ring said so: `43.0k of 100k before compaction`, on a backend that
was holding two and a half times that. The harness asks now — how large is the
window of the model the server actually has loaded — and compacts at three
quarters of it. Measured against that backend the following day: 204,288 loaded,
so 153,216 before anything is summarized. Against ollama with a small model up:
32,768 loaded, so 24,576. A model loaded with 8,192 gives 6,144, which is
earlier than the old constant, and deliberately so.

Three quarters, because the very next call after the threshold trips is the
summarizer, which re-sends essentially the same history and asks for a
completion on top. 131,072 is the smallest window in common use here — three of
the sixteen models installed on the machine this was measured against report
exactly that ceiling — and a quarter of it is 32,768, just over the 32,000 a
completion may ask for by default. A tenth would leave 13,107, and the request
the threshold exists to prevent would be the one that bursts. The summarizer's
own request is sized to the same reserve, so on an 8k model it asks for 2,048
instead of four times the whole window.

It is the loaded window and never the model's ceiling. The same listing that
reported 204,288 loaded also reported that the model can hold 1,048,576, and
compacting against that would push the trip past the window the server is
actually holding, which is the one direction worse than a constant. Where
nothing can be learned it stays at 100,000: a model installed but not loaded, an
endpoint with no such route, a host that does not answer.

Your own `compactionThreshold` still wins, and it reaches child agents now,
which used to derive their own — a parent pinned to 5,000 spawned children
running to 153,216. The derivation also reaches the models the app bundles:
every entry in that catalogue is loaded with 8,192 tokens or fewer, so they
compact where they should rather than effectively never. And the question is
only asked when you have not set a threshold yourself. It used to be asked
either way and the answer thrown away: 363 ms against an endpoint with no such
route, 2,001 ms against a host that black-holes the connection, spent before the
run had started.

## While the agent works, the screen says so

After you send a prompt, an animated line stands under the transcript with an
elapsed timer, `working … 0:07`, and leaves the moment the answer starts.
Before, the caret and the thinking dot both hung off an already-open assistant
turn, so the stretch from run start to the first token, and every tool run,
showed a dead transcript. Against a local model the line held through a
five-minute prompt-processing stretch, `working … 0:13` through `4:59`, and
disappeared when the answer streamed. It yields to the thinking dot and the
caret where those apply, and it yields while a permission question is open,
because that wait belongs to you. Replays show no line, and reduced motion
stills it.

An answer that carries usage and timing now states its generation speed beside
the token counts it already had: `2411 in · 186 out · 236 tok/s · 0.8 s` on a
replay, and `5105 in · 364 out · 4.7 tok/s · 1 m 17 s` on a live local run. It
is computed at render time from events already recorded, so a saved run gains
the figure when you replay it and nothing new is written to disk. Where the
usage or the timing is missing, the figure is simply absent.

## The live trace has an off switch

A checkbox in the three-dots menu stops the browser retaining trace rows for a
live run. The recording on disk and the OTLP export are untouched: the session
file kept carrying `run_start`, `turn_start` and `context_info` throughout a
run checked four minutes in, and the trace tab says plainly that the live trace
is off instead of showing an empty table. Flipping it off frees what is already
held; flipping it on starts retaining again from that moment, and the rows it
skipped do not come back. Replayed archives and the fleet mount keep their full
trace. The default is on, which is what 0.9.0 did.

## The transcript belongs to the reader

While a run streamed, scrolling up threw you back down. One wheel notch moves
100px, and the zone that counted as "still at the bottom" was 120px, so the
view was back at the bottom 42ms later and the follow never disarmed at all.

That zone is down to two pixels of rounding slack. The follow comes off on your
gesture itself, before the browser has scrolled anything: a wheel notch, a
touch drag, the Page, Arrow or Home keys, or a press on the scrollbar. It stays
off until you return to the bottom, press jump-to-end, or send a message, which
is as deliberate as pressing jump-to-end. Nothing the app scrolls can re-arm
it. The same notch now holds at zero drift while 441px of content arrives below
it.

The scrollbar was the worst of it, because a thumb drag reports its two ends
and nothing in between. Under a stream re-commanding a follow twenty times a
second it took 35 scroll events and 2,228ms of being pulled back before a 24px
drag finally held. The press alone stops the follow now: it holds at the eighth
scroll event, 6px up, with no fight. Opening a saved run also opens at its top
instead of inheriting the position of whatever you were reading before.

## The view keeps being fed

Two things could stop the live view updating while the file on disk stayed
complete.

The view was updated only on animation frames, and a window that is minimised,
occluded or in a background tab draws none — so nothing arrived on screen until
you looked again, in the trace, the spectrum and the chat alike. There is a
250ms fallback timer now. A visible window never reaches it, because a frame at
16ms always gets there first, so the batching you see while watching is
unchanged. The desktop shell made this worse than a browser tab, since Chromium
clamps a hidden window's timers to a second, and to roughly a minute once it
has been hidden five minutes. That throttling is off.

The second was a half-open socket. Reconnecting happened only when the socket
reported itself closed, so a connection lost to a sleep, a network change or a
hop that quietly went away delivered nothing, never retried, and the chip kept
reading "connected". The client asks now. After 15 seconds of silence it sends
a probe, each probe has 10 seconds to be answered, and two unanswered probes
retire the socket: 35 seconds of total silence, including two direct questions,
before anything is condemned. A socket error also triggers a reconnect, not
only a close. The instant the socket is retired the chip says the connection is
lost and it is retrying, so nothing reads "connected" past the window.

It is a probe rather than a silence timer because losing the socket aborts your
run, closes the session's browser and kills what it launched. A run waiting on
a slow first token or a five-minute tool call is silent in exactly the way a
dead socket is. Silence cannot tell them apart; an unanswered question can.

A reconnect returns to the session the server minted. Before, a page that had
opened a fresh session and lost its socket could reconnect as a different
session and feed a second run's frames into the first run's view while the
first run's file kept growing on disk. And if your client is newer than the
server it talks to, the older server answers the probe with an error that would
otherwise land in your chat and in your session file every fifteen idle
seconds; the client recognises that refusal and stops probing that peer.

## The app opens on a greeting, and the composer stops spilling

An install from before 0.9.0 opened the right-hand panel with its files and
terminal cards on the new-session home; a layout written by 0.9.0 added the
browser card on top. Measured on a 1310x840 window with all three, chat opened
at 442px, and at a 1150px window it fell to 356px, under its own 360px reserve,
with the toggle strip wrapped to two lines. The home opens at full width with
the panel closed now, whatever the stored layout says. A layout you left open
still comes back when you enter that session: what was stored is now a
preference about which cards live in the panel, not an instruction to open it
at launch. The panel has a hard chat floor, so dragging it to its maximum
leaves chat exactly 360px.

At narrow chat widths the composer's small controls used to escape the rounded
box: at a 1150px window the row wanted 388px in a 324px column and the gear sat
63px outside it. German labels are longer and broke it worst — the archive bar
pushed its return control 80px outside the box and 31px under the panel. The
action row measures its own column now, so it collapses whether the window is
small or the panel is dragged wide. Below a 500px column the controls move into
the three-dots menu as a session-tools section, the draft box and send seat
never shrink for them, and the row wraps as a last resort so nothing clips.
Export and translation went further: the menu is their only home now, at every
width.

## The agent's browser drives the panel, not your tab

In 0.9.0, asking an agent to open a browser flipped the session tab to a
full-window browser, closed the panel cards you had open, and grabbed the tab
back from you on every browser action the agent took. Worse, the desktop shell
painted a native browser pane at a stale rectangle on every one of those
actions and nothing hid it again, so a reload left the old page painting over
the fresh app with your clicks landing in the web page, and only restarting the
program healed it.

A browser action makes the page real and paints nothing now. Only the app's own
report of where the panel sits puts a pane on screen, and navigating the app
window hides every pane. The panel reveals itself at most once per run, so if
you close it mid-run you are not asked again. The session tab stays what it
was: the by-hand state and replay view. Separately, a stored panel layout the
app cannot read resets to the default and says so once rather than wedging, and
your sessions are untouched by that reset.

## Several files at once, rendered or as source

The files panel holds tabs. Opening a second file no longer replaces the first:
tabs are keyed by path, so re-opening a file focuses its tab, each tab keeps
its own state while inactive (a scrolled iframe and a collapsed region survive
a switch), and closing a tab releases its content. Tabs cap at eight, the
oldest inactive one making room, and there is a close-all until only one tab is
left.

Both readings are offered for every file except binary images. The source view
has line numbers, syntax highlighting in the app's own palette, and
indentation-based folds that show how many lines they hide: a Python function
folded from 14 rows to 8 with a `⋯ 6` badge, and the numbering jumps honestly
across the fold rather than pretending to be continuous. The choice is per tab.

## A slash carries the skill's instructions

A skill you invoke with `/` stays in the message as a coloured `/name` token,
several per message, anywhere in the text, while the prompt sent to the model
carries that skill's actual instructions. The picker completes mid-text at the
caret, so "and/or" and `/tmp/x` stay typable, and it splices a token instead of
the old prose sentence.

What you see is what is recorded. The session file keeps the words you typed;
only the request to the model carries the skill's instructions attached to
them. A token naming no skill goes through as plain text, and a repeated token
expands once.

The focused row now shows its whole description in a popover beside the list,
where before only a truncated line and its tooltip were available. Arrow keys
and the mouse move it together, it takes whichever side has room, and in a
window with none it falls back to the row's tooltip.

## The file tools say what they did

`write_file` answered `Wrote` whether it had created the file, changed it, or
written bytes identical to the ones already there. It ends its result with the
difference it made now: `— created`, `— changed (+15 bytes)`, `— changed (same
size, different bytes)`, or the one that matters, `— unchanged (the file
already contained exactly these bytes)`. `edit_file` says the same when a
replacement puts the string back unchanged, and that stays a different answer
from `old_string not found`. Finding nothing to replace and replacing something
with itself are different news.

In one session on a local model, 107 of 128 tool calls over 103 minutes were
writes. One test file was written eleven times with five distinct contents, and
the same bytes went out seven of those times, five of them consecutively. The
model worked that out by spending an extra turn on a read. It is told in the
same breath now. A second case from the same week: 31 writes across 31 files,
with one distinct content between them.

The transcript's tool card shows the same word beside the write, in English and
German, and so does the trace's detail view, so you read what the model read.
An unchanged write still writes: the bytes are identical, so nothing on disk
moves except the timestamp.

## A screenshot no longer wedges a text-only model

Pasting a screenshot into a session on a text-only model wedged it for good.
The request came back as an HTTP 400, the picture stayed in the history, and
every prompt after it was refused for the same reason.

Where the backend can answer the question — ollama does — the model is asked
whether it can see before the request is built. Where it cannot, the first
image still fails once and every prompt after it works. Either way the picture
is kept out of the request from then on, the model gets a marker where the
image would have gone so it does not answer about a screenshot it never
received, and the chat says it once per run: "Image not sent: this model cannot
see images. It stays in the record." The picture stays in your bubble and in
the session file. The same rule applies when a long history is summarized,
which is the other door the old failure came back through.

## The desktop agent finds the toolchain you installed

An agent in the Finder-launched desktop app concluded there was no `node` on
the machine — its shells got `node: command not found` — while your own
terminal ran Node fine. A macOS app started from the Finder inherits launchd's
minimal PATH, and on the running app that was `/usr/bin:/bin:/usr/sbin:/sbin`
in both the shell and the server, with Node installed at
`/opt/homebrew/bin/node` and therefore invisible.

The policy lives in the JVM now, one implementation for the Finder-launched and
the terminal-launched app. The inherited PATH is kept verbatim, and toolchain
directories that exist on disk but are missing from it get prepended:
`/opt/homebrew/bin`, `/opt/homebrew/sbin`, `/usr/local/bin`, `/usr/local/sbin`,
`~/.local/bin`. From a terminal that already exports them, the result is the
inherited string unchanged. `spectro doctor` prints the entry count, what the
policy added and the effective PATH verbatim, so the next such mystery is a
lookup rather than an investigation: in a scrubbed environment it reads
`7 entries · 3 added by policy`.

## Smaller, and worth having

- Settings was one modal that scrolled through fifteen sections. It has six
  tabs now: general, models, tools, MCP, permissions, system. The tab row and
  the title stay put while the page scrolls, the row holds one line down to a
  400px window, and nothing inside changed. Deep links select the room they
  land in, and following the same link twice now lands in the same place.
- The plus menu's Skills panel scrolls. With the 36 skills one real machine
  produces, 2,277px of rows were drawn into a 444px box: 8 rows visible and 30
  of 38 out of reach, including the Manage and Browse rows at the bottom, which
  made "Browse catalogue" unclickable on exactly the machines that have a
  catalogue. The entries scroll in their own area now, with the line above them
  and both footer rows staying put: nothing out of reach. The MCP servers list
  beside it scrolls the same way.
- A translation sheet opened from the composer's menu stays open. A press
  inside it used to count as a click outside the menu and took the sheet down
  with it.

## Getting it

The channels are the ones 0.5.0 shipped. Nothing new this cut, and nothing
dropped.

**Homebrew, on macOS.** `brew install --cask spectroscope/tap/spectroscope`
installs the signed and notarized desktop kit.

**The macOS disk image.** `spectroscope-0.10.0-arm64.dmg` on the release page.
Signed, notarized, and carrying its own Java runtime and `llama-server`. Apple
silicon only.

**apt, on Debian and Ubuntu.** The signed repository at
`https://apt.spectroscope.dev` serves the deb; if you added it for an earlier
release, `apt upgrade` carries you here. x86_64 only.

**The Linux kit.** `spectroscope-0.10.0-x86_64.AppImage` and
`spectroscope_0.10.0_amd64.deb` on the release page, built and smoke-tested on
Linux by this project's own CI. Both bundle their own Java runtime and
`llama-server`. x86_64 only, not signed.

**The jar and the CLI.** `spectro-server-0.10.0.jar` and `spectro-0.10.0.zip`
run on any machine with Java 21. They are the smallest way in, and the only way
onto a platform that has no kit.

## Known limits

- Whether a child agent is spawned is the model's call. On a small local model
  that is not trained for tool use it usually is not, and there is no control
  yet that forces or forbids the offer.
- Five of a child's reads ask you nothing: the browser page you have attached,
  a search of it, its console, your launch configurations and their logs.
  Gating them for children would have gated them for you.
- Spawning itself is not permission-gated. One un-gated parent call now sets
  more in motion than it did in 0.9.0.
- The two child clocks run in sequence, so a child that speaks just before its
  queue grace expires and then wedges can cost both ceilings: 75 minutes, not
  30.
- There is no setting for a child's budget. It is derived from the session's
  own measured turns; a program embedding the library can pin a number, the app
  cannot.
- There is no screen yet that shows what a role keeps from its children. It is
  computed and served on the API, and the System context view drops it.
- A reconnect does not go back for what it missed. The socket's own down
  window, up to 35 seconds of watchdog plus up to 15 seconds of backoff, is
  missing from the live view afterwards. Nothing is doubled, and the session
  file on disk carries every event, but the view does not fetch the gap.
  Closing that needs a cursor on the history endpoint and a rule for which
  events line up. It is not in this release.
- The minimised-window case is covered by tests and by reasoning. Nobody has
  yet watched a real minimised window through a network drop, so treat that
  combination as unproven.
- The scroll rule was measured on a bench that drives the shipped module
  through a real browser, not in the app against a live model, so the look in
  all four designs is still open, and a touch drag was never performed on a
  real device. On a display whose resting scroll residue exceeds two pixels the
  follow could only be re-armed by jump-to-end or by sending; fractional
  device-pixel ratios and browser zoom were not measured.
- A socket that dies silently can raise the "session busy" notice on its own,
  when the automatic reconnect asks for a session the server still holds a
  claim on. The notice is sticky and dismissed by hand, and you did not ask for
  that reconnect.
- Where a platform draws overlay scrollbars, macOS by default, the bar has no
  width for a press to land on, and a thumb drag falls back to the old
  scroll-event behaviour during a stream.
- An opened child is remembered per view and not across a reload, so a reload
  returns every chip to closed. `v1 · as recorded` is unchanged.
- Against an OpenAI-compatible endpoint the image capability is not probed
  before the first send: `/v1/models` lists ids and not what they accept, and
  the one endpoint that does answer — LM Studio's own `/api/v1/models`, which
  reports vision per model — is not read yet. So the first image at a model
  that cannot see still fails once, now with a sentence that says why, and the
  refusal is remembered for the rest of the session. With ollama the answer is
  known before the first send.
- A question waits forever. In an attended session nothing times out and
  nothing auto-answers, and a run may ask three.
- The plan verdict displaces only `end_turn`. A run that hit the turn cap still
  counts as a completed run on the ladder, even with plan steps open. `spectro
  run` has no `update_plan` on its belt, so a headless run cannot write a plan
  and its verdict is always unknown. The session list's row cannot tell a run
  that wrote no plan from a finished one, because the row carries no plan; the
  footer, the command line's run-end line and the export can.
- Nothing about the progress guard has been run against a live model. No real
  session file carries its line, and nobody has watched the app draw its
  question. What says it will work is a reading of the code, not a measurement.
- The guard, the continuation and the goal run only where a person is there: a
  session in the app and the interactive command line. A headless run, a
  scheduled run, a fleet node, a triggered node and a child agent get none of
  them, and no warning line either.
- The three end differently when their bound is reached, and nobody has decided
  whether that is right. The guard stops and asks you. The continuation budget
  runs out and the run ends. A check that cannot be run ends untested. One
  answer should cover all three; today each does its own thing.
- Only the guard can be overruled while a run is going. Its "carry on" stands
  that detector down; the continuation and the check have no equivalent, and
  their only exits are the budget or the refusal to continue a run that has not
  moved.
- None of the four numbers behind them has a row in the settings panel.
  `progressGuardWrites`, `progressGuardFailures`, `progressGuardPlanTurns` and
  `continuationBudget` travel the whole settings chain and stand in the printed
  config reference, and the only way to change one or switch it off is to edit
  the settings file by hand.
- The app draws almost none of it. The guard's question reaches the answer bar
  the app already has, but the guard's line, the continuation lines and the
  goal's verdict are printed on the command line and nowhere in the app, and
  there is no goal screen at all: the server sends a run's goal and accepts a
  new one, and nothing renders either half.
- The guard's question is English only. The event carries the detector, the
  count and what it saw separately, so a surface can word it itself, but the bar
  shows English.
- The stalled-plan detector ships off. A plan that stops advancing is not
  watched unless you turn it on.
- With nobody to ask, the guard leaves the net up and only clears its memory, so
  an unattended run that really does repeat itself writes a line every three
  events instead of one line and then silence.
- The goal's check cannot be held to the no-progress refusal in practice. The
  refusal compares the check's output verbatim, so a suite that prints a
  timestamp or an elapsed time never repeats and the refusal never fires for it,
  leaving only the budget. Normalising it would mean guessing which digits of
  somebody else's test runner are noise. It is the weakest thing in this cut.
- A line of your own prose in the goal file that begins with `## ` ends the goal
  section.
- The goal's check does not pass the pre-tool hooks. Those are policy about what
  the model may do; this command is your own, and it is shown to you at the
  gate.
- A model judge for the goal exists in the library and is wired to no face. On
  the same evidence it disagreed with the command check once in four checks, and
  the disagreement was the judge calling a green suite not met because the
  transcript did not show the model running it.
- No goals across sessions, no goal per child agent, and no face refuses to
  start a run without one. There are no scheduled or self-paced wake-ups between
  runs either.
- The continuation was proven on a small local model in a run whose every file
  write was denied at the gate, so it shows the hold and never the repair. The
  same run against a stronger local model, to show the continuation firing less
  often, was not made.
- The guard watches for repetition, not for damage. A command that deletes the
  working tree still passes the gate without a question.
- A session on a small local model that used to run uncompacted forever now
  summarizes itself. That is the point of deriving the threshold in both
  directions, and it is a loss for whoever liked it the other way.
  `compactionThreshold` is the lever.
- The gauge shows the derived threshold and captions it "before compaction", but
  it does not say which fact the number came from, and with nothing configured
  the settings row reports "not set" and no number at all.
- Only an answer or a flat refusal is remembered. A server error, a timeout or
  an empty listing is asked again at every run start, forever, and a host that
  black-holes the connection costs the connect deadline, about two seconds, each
  time. Setting a threshold yourself costs nothing, because then nothing is
  asked. The Anthropic provider is never asked what window it has.
- Four of the six settings rooms are taller than one screen at 1280x900, and
  two of them, tools and permissions, run about two and a half. The tallest
  single section is taller than the window on its own.
- A browser action by the agent still fronts the whole app window, even though
  it no longer takes your tab.
- The live-trace switch is a relief valve you choose. Nothing here measures how
  much memory it saves.
- A hand-typed skill token that omits the pack prefix goes through as plain
  text. The token has to carry the agent's exact skill name, which is what the
  picker inserts.
- Version-manager shims (nvm, pyenv, asdf) are deliberately not guessed for the
  agent's PATH: picking one behind your back would hand the agent a different
  toolchain than your terminal has.
- No arm64 Linux build, no Windows desktop kit, and no arm64 package in the apt
  repository. Unchanged from 0.5.0.
- Translation is unchanged from 0.4.1. Only where you reach it moved.

## Requirements

Java 21 or newer. The macOS desktop kit is arm64, signed and notarized, and
includes its own Java runtime. The Linux kit is x86_64, includes its own Java
runtime, and is not signed. The server jar and the CLI need a `llama-server` on
the PATH (`brew install llama.cpp`) to run a local model; both desktop kits
bundle one. The terminal panel needs the `spectro-pty` helper, which only the
desktop kits carry.
