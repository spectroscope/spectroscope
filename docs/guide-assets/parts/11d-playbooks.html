Chapter 15dPlaybooks: a way of working, drawn

A playbook is a folder that says how a team builds: which steps come in which order, where the work branches, which skill and which model each step uses, and which handover document passes from one step to the next. The developer mode reads such a folder, checks it, draws it and lets you edit it. A session that picks the playbook gets the skills, commands and agents the folder brings, and a session can run by it: each step on the model it names, with the handover checked before the next step starts.

What a playbook is

The central file is playbook.json. It describes a graph of three kinds of node. A step is work: it names who does it (the chat or a child agent), which skills it uses, which model choice it runs on, whether it stays private or may use a cheaper hosted model, which documents it takes in and which it hands on, and whether it waits for your nod. A decision is a check with named outcomes, for example pass and fail, and every outcome has exactly one arrow leaving it. An end closes the path with a result. Arrows connect them, and an arrow that leads back to an earlier node is a loop.

Every loop has a ceiling. A decision that sits on a loop carries max_rounds, and when the rounds are used up the decision takes a further outcome called exhausted. A playbook whose loop has no such decision is refused when it is loaded, and the finding names the arrow.

The file chooses a model by name, never by address. The names are model choices, a small set that the playbook defines once, and each choice holds a provider and a model with an optional list of fallbacks. A step says strong or fast, and the choice resolves to whatever your own installation has. This is what lets a team share a playbook without sharing a machine.

The folder

The playbook that ships with the product shows the layout. These are the entries at the top of the folder:

EntryWhat it holds
playbook.jsonThe graph, the model choices, the document types and the checks. This is the only file the loader must find.
skills/The skills the steps name. The shipped folder holds the pack spectropowers, fourteen skills.
templates/One Markdown template per document type, so a handover document always has the same sections.
docs/A generated index.html: the graph as a picture, one section per step and one per document type.
LICENSEThe licence text of the material the playbook was built from.
PROVENANCE.mdWhere the material came from, as which version, and every file that was changed.

The format also has places for agents/, hooks/, commands/ and workflows/. The shipped playbook leaves the first three empty and ships two workflows (“Running a workflow” below), and version 1 only reads the paths the contents list of playbook.json names. The loader reads playbook.json and those files and nothing else, at most 1 MB per file and 200 files per folder, and only a folder you have registered. What a session does with those entries is described under “Playbook contents”.

The developer mode

developer is the third view mode, next to learn and light (chapter 6c). It opens everything learn opens, without the tutorial, and adds one segment to the sidebar: Playbook. The choice is offered in the first question of a new window, and the mode switch at the top right changes it later. In learn and light the segment does not exist and its code is never requested.

The segment has a row of tabs: Steps, Skills, Agents, Hooks, Commands, Workflows, Plugin, Files and New. The section “The bundle tabs” below describes the tabs from Skills to Files, and New is Spectrolyzr. The segment configures and edits playbooks and starts nothing: a run starts from the chat of a session (“Running a playbook”). The Steps tab has four parts.

  • Folders. The folders you have registered, kept in ~/.spectro/playbooks.json. A field adds a folder by its absolute path, and the button “Choose” beside it fills the field from the system's folder dialog. The same field is the target of “Copy the spectro playbook into a folder”. A pick changes nothing by itself: “Add” and the copy button act on the field, and a picked folder is checked exactly like a typed one. The playbook folder of Spectrolyzr has the same “Choose” button, and its project folder has one named “Pick”. A button next to each other folder, “Use for this workspace”, pins it to the working folder of the window.
  • The graph. Steps are cards that show the step name, the model choice and who performs it. Decisions are diamonds, ends are rounded boxes. Each arrow out of a decision carries its outcome as a label, and a loop is drawn as a loop with its round limit, for example “up to 5 rounds”. The colors follow the active design, light or dark.
  • The steps. One table row per step: who performs it, each skill with “in the playbook” or “missing in the playbook” (read from the skill folders of the playbook itself), the model choice with the provider it names and that provider's state on this machine, the privacy switch, the documents the step takes and hands on, and whether it waits for a nod.
  • Findings. The problems found in the file, one line each, naming the node or key. The list appears only when there is something to report. A file the reader refuses, for example one with an unknown field or a forbidden key, is not drawn at all. A file that reads but breaks a rule, such as a loop without a ceiling, is drawn with its findings above the graph.

For a session that holds a run the tab has one more line, “Runs of this session: open”. It goes back to the chat and shows the session's runs wide in the Plan panel (“Watching and stopping” below). With no folder pinned the segment shows the folder picker, the copy button and that line, and nothing else.

The spectro playbook

The product ships one playbook, spectro. It holds 10 steps, 8 decisions and 2 ends. A first decision classifies the work as a spike, a bounded change or an architectural change, and each class takes its own path.

  • The architectural path brainstorms with you, checks that the spec has its sections, waits for your nod, writes a plan, checks the plan, waits for your nod again, sets up a worktree and then enters the build loop: implement a task, review it, fix what the review found, for at most 5 rounds per task. A final review follows, and then the branch is finished.
  • The bounded path is a short design in the chat, an implementation test first, and the finish.
  • The spike path is a probe that ends in a recommendation.

The model choices are fast, standard, strong and judge. The document types are Ticket, Spec, Plan, Task report and Review report, and every step names the ones it takes in and hands on. The skills come from spectropowers, a copy of the superpowers skills with house rules worked into the text. LICENSE carries the MIT text of the source, and PROVENANCE.md names the source version and lists every edited file.

Copying it into a folder

Choose a folder you want to keep the playbook in, ideally one that is its own repository, type its absolute path into the field and press “Copy the spectro playbook into a folder”. The server writes the bundled files there and registers the folder. It never overwrites. If any target file already exists, nothing is written, the answer is a conflict, and the window lists the files that stand in the way. After a copy you can edit playbook.json in your own editor or in the segment's editor, which the next section describes. The segment reads the file each time it loads the folder, so the graph shows what the file says now.

Spectrolyzr

Spectrolyzr writes a new project and, if you ask for it, a playbook for it. It can also write a playbook alone. It is one page in the Playbook segment, behind the tab “New”, next to the tab that shows the playbook. Every choice stands on the page at once, so nothing hides behind a step. The project is small, builds, and ships one test that passes. The same choices always produce the same files, byte for byte. The files come from templates inside the app, so nothing is fetched from the network, and no generated project depends on a spectroscope package.

At the top of the page the switch “What to make” offers two options, “Project” and “Playbook”. The page below it changes with the option.

With “Project” the choices stand in one column and the files beside them. On a narrow window the files move under the choices.

  • Archetype, language and name. Pick an archetype and a language and type a name. The archetypes are Service, an HTTP server with one /health route; Library, one public function; and Command line tool, a command that greets a name and returns an exit code. The languages are TypeScript, Python and Java. A name starts with a lower case letter, holds lower case letters and digits, may join parts with single hyphens, and has at most 40 characters. A name that turns into a reserved word of Java or Python is refused, and the field says so.
  • Add-ons. Any of three, in any combination. Quality gate adds one command that runs the type or lint check and the tests, and fails when no test ran. CI adds a GitHub Actions workflow that runs that check on every push and pull request. spectro playbook writes the playbook of chapter 15d into a folder of its own. With this add-on on, a field “Playbook folder” appears under “Folders”.
  • Folders. The project folder and, when the playbook add-on is on, the playbook folder. Each field takes an absolute path. The button beside it, “Pick” at the project folder and “Choose” at the playbook folder, opens the system's folder dialog and puts the path into the field. A pick changes nothing on disk, and you can still type or paste into the field. Where the system has no folder dialog, the page says “No folder dialog here. Paste an absolute path into the field.” If a dialog is already open, it says “A folder dialog is already open.”
  • Files. Under the heading “Files” stands a file tree with the project and, when you chose it, the playbook as two roots. Select a file to read its content and, under “Why this file”, one sentence on why it is there. The summary names the number of files per folder and two commands: the test command, and the check command, which is the gate command when you chose the quality gate. The tree fills in as soon as an archetype, a language and a name are set.

“Generate” stands at the bottom and writes the files. It stays off until the project folder is set, and in the “Playbook” option until the playbook folder is set.

With “Playbook” the page asks for less. It shows the “Playbook folder” with its “Choose” button and the section “Models”, with one choice for each of the four model roles of the shipped playbook, fast, standard, strong and judge. A choice offers “Keep the spectro playbook's model” first and then every model the provider registry lists, provider by provider. A role you leave on the first option keeps the model of the shipped playbook. “Generate” writes a copy of the shipped spectro playbook into the folder, sets the model of each role you chose, and registers the folder. No project is written, and the playbook is pinned to no workspace. The folder then appears in the Steps tab. The contents row of the loaded folder counts its skills, commands, hooks, agents and workflows. A playbook made this way carries the two workflows of the shipped playbook, fanout-review.json and fanout-research.json, for every archetype, byte for byte as the pack ships them.

The playbook folder

The playbook does not go inside the project. The field starts as a sibling of the project folder, named after the project with -playbook at the end, and you can change it. It may not be the project folder, inside it, or around it. Generate writes the spectro playbook there, sets its test variable to the check command of your project, registers the folder, and pins it to the new project folder. The pin shows in the Playbook segment once the project folder is the working folder of the window. Spectrolyzr does not change the working folder for you.

What Generate refuses

Generate never overwrites. It looks at both folders first. If any target file already exists, nothing is written, and the window lists the files that stand in the way, per folder. A choice the server does not know, or a name it refuses, comes back as a message that marks the field. After a successful run the window names both folders, says the playbook is pinned to the project, and offers a button that copies the path.

A generated Java project has no Gradle wrapper yet, so the command gradle test needs Gradle on your machine, next to Java 21. The product's own CI builds every archetype in every language, once bare and once with all three add-ons, and runs its check command, so a template that stops building turns that job red.

Editing a playbook

The segment edits the file with the mouse. The “Edit” button in the header opens the editor for the folder you are looking at. It is offered when the file can be rewritten without losing anything. A file that carries fields the reader does not know stays read only, and the header says why. Nothing on disk changes until you press “Save”.

The editor puts a toolbar above the graph and a panel beside it, or below it on a narrow window. The graph is the picture of the read view, with one difference: the layout engine places every box again after each change, so no box can be dragged to a spot of your choosing. The left mouse button selects and draws arrows. The right and the middle button pan, the wheel zooms, and “Fit” brings the whole playbook back into view.

To add a box, select a step, a decision or an arrow and press “Add step”, “Add decision” or “Add end”. After a step or an arrow the new box is inserted into the arrow that leaves the step, or into the selected arrow, so the path stays whole. After a decision it takes the first outcome that has no arrow yet. A new box gets the next free id, such as decision_1, and a plain English name that you can change in the panel.

To connect two boxes, drag from a handle on the right edge of the first and let go anywhere on the second. A step has one handle and a decision has one per outcome, each named when you hover over it. An outcome has exactly one arrow, so dragging from a handle that already has an arrow points that arrow at the new target. Select an arrow and the panel shows its target and, for an arrow that leaves a decision, its outcome, both of which you can change there. “Delete” removes the selected box with its arrows, or the selected arrow. On the canvas, Backspace and Delete do the same.

The panel has three tabs. Selection edits the selected node: a step has an id, a name, a goal, who performs it, a role for a child agent, its skills (the skills of the playbook folder, each marked “in the playbook” or “missing in the playbook” as in the steps table), a model choice that shows the provider's state, privacy, permission, the documents it takes and hands on, and the human nod. A decision has an id, a name, a check, its outcomes and its maximum rounds, and an end has a result. Documents and Checks edit the document types and the checks. Model choices, vars and contents are read only in this version. A text field saves when you leave it or press Enter, Escape brings the old text back, and Backspace in a field never deletes the selected box.

“Undo” and “Redo” step through the last 50 changes. Ctrl or Cmd with Z does the same outside a text field, with Shift for redo. A box that an arrow names but nobody defined is drawn as a dashed box marked “missing”, and its arrow can still be selected, so the mistake stays visible and nothing disappears silently.

The list of findings under the panel is the check of the read view. The server runs it on your draft a moment after each change. “Save” is refused while a finding exists: the status reads “Not saved” with the number of findings, the list names each one, and the file on disk stays as it was. A file you wrote by hand in another layout is rewritten in the editor's fixed form on the first save, which may reformat the whole file. The editor announces that before you save, because the first diff is then larger than your change. After that a save writes structure only, with no coordinates and the keys in one fixed order, so a diff shows your change and nothing else.

If the file changed on disk after you opened it, for example in your own editor, the save is refused with the message that the file changed on disk, and your draft stays on screen. “Revert” drops your changes and reads the file again. “Stop editing” closes the editor. While there are unsaved changes it is disabled, and so is the folder list.

As an example, a review round after Implement task in the spectro playbook takes these steps. Select Implement task and press “Add decision”. Choose the check task_review and type 3 into the maximum rounds. Select the arrow from the new decision to Review task and set its outcome to pass. Drag the fail handle to Implement task and the exhausted handle to the end cancelled. Press “Save”. The file gains one node and three arrows, one existing arrow now points at the new decision, and no other line differs.

The bundle tabs

A playbook folder carries more than playbook.json, and the tabs from Skills to Files show and edit the rest. Skills, Agents, Hooks, Commands and Workflows each list the entries of their kind in the contents of playbook.json. An entry is marked “Listed”, only on disk, or “Listed but missing”. “List it” adds an entry that is only on disk, and “Remove” takes an entry out of contents and deletes its files after a confirmation. Beside the list each tab shows a file browser of its folder. Files shows the whole folder. The tabs from Skills to Workflows and the Plugin tab stay disabled until a playbook is loaded; Files needs only a folder. The Workflows tab edits the files, and a workflow runs from the chat of a session with /playbook workflow (“Running a workflow”).

Select a file in a browser to edit it on the right. “Save” checks that the file did not change on disk after you opened it and offers “Reload from disk” when it did. Markdown and JSON files show a preview beside the text, and playbook.json opens the graph editor described in “Editing a playbook” above. While a file has unsaved changes, the other tabs are blocked. The editor opens UTF-8 text only. playbook.json, LICENSE and PROVENANCE.md belong to every playbook and cannot be deleted. The app reads a folder to six levels and 200 files; the tree says when the folder holds more. The app follows no symbolic link inside a playbook.

The Skills tab imports skills. “Import” lists the skills installed on this machine and the skills of the catalogue, with a checkbox each. An imported skill keeps its licence, and PROVENANCE.md gets a line that names its source. Agents and Commands have “New” with a name field: a name holds letters, digits, - and _ and starts with a letter or a digit, and an agent's type is explore, worker or research.

The Hooks tab has “Import hooks”. It copies the hooks of your user settings into hooks/hooks.json, together with the scripts in your home folder that a command names, and replaces a hooks.json the playbook already has after it says so. A path in your workspace is written as {project}, and the contents list shows the working folder there. A hook that names a hidden file or folder in your home folder, such as ~/.ssh, or a path that leaves the workspace with .., is left out, and the list marks it before you import. Other paths in your home folder are written with ~ where they start a word of the command. An import changes nothing in your settings, and nothing copies a playbook's hooks into them.

The Plugin tab lists the Claude Code plugins of your home folder, from the plugin cache and from the marketplaces, with the count of skills, agents, commands and hooks each one carries. “Import” copies the kinds you tick: the skills as one pack, the agents, the commands, and the hooks that run before or after a tool call. Agent fields and hook events the playbook format does not know are left out, and the report after the import lists them with the reason. MCP server definitions are never copied. A plugin without a LICENSE is not imported at all.

“Export” saves the folder as <id>.playbook.zip, and the same folder always gives the same file. “Import ZIP” reads a bundle in the browser, shows its files and contents, and writes them into an empty folder you choose, which it then registers. The server checks every path and the playbook before anything lands, so a refusal leaves the folder empty. A bundle has exactly one top folder with a playbook.json in it. It is refused when it holds more than 200 files or more than 24 MB, an entry deeper than six levels, two entries for the same file, or a binary file outside docs/ or larger than 2 MB. Export and Import ZIP also refuse a hooks file in which a value matches one of the key patterns the recordings already redact, and name the line and the pattern. The check knows only these patterns: it does not find a password after a command option, for example.

After Generate on the New tab with “Playbook” chosen, and after an import on the Plugin tab, the pane opens the Skills tab of the folder. After Import ZIP it opens the Steps tab of the imported folder.

Playbook contents

A playbook can carry five kinds of content. The Playbook segment shows a Contents row with the count of each kind, and the tabs from Skills to Workflows list the items. Nothing copies a playbook's contents anywhere: the window has no Install or Remove button, and the server has no route for either. A session that picks the playbook reads its skills, commands and agents in place, from the playbook folder.

KindIn the folderWhat a session gets
Skillsskills/, one pack folder holding one folder per skillEach skill under the name of its folder, in every session that picked the playbook. The pack folder is not part of the name; when two skills of the playbook have one name, both take pack:skill.
Commandscommands/, one Markdown file per commandEach command under the name of its file, invoked in the message box as /name, with the rest of the message as arguments.
Hookshooks/, a hooks.json and the scripts beside itListed with the command each hook would run and the full text of every script. A playbook's hooks do not run: nothing adds them to your settings.
Agentsagents/, one Markdown file per agent with a name, a description, a type and a preambleNothing is copied and nothing needs installing: the agent file is read from the playbook folder in place. A child step may name it as the role agent:name, and the run starts that child on the type and preamble of the agent file; its bytes are part of the hash the confirmation shows, so a file edited after the confirmation stops the start. The run does not start when the file is missing or is not a plain file in the folder (“agent not found”). In the chat, a session that picked the playbook starts its agents with the tool spawn_named_agent. The agent file cannot set a model, a permission or a tool list.
Workflowsworkflows/, one JSON step list per fileListed with their hash and never copied. A file that reads as a step list is “runnable” and runs in a session with /playbook workflow and its name (“Running a workflow”). Any other file is listed and is not run.

When your workspace or your own folders bring a skill or command with the same name, each of them takes a prefix that names where it comes from, and the playbook's item is invoked as /<playbook id>:<name>. A name that a command of the web chat uses, such as clear, always takes the prefix.

Every skill and command of the picked playbook adds one line to the system prompt of the session, a number of characters that the contents list adds up. The cost weighs more on a local model with a short context window.

Running a playbook

A run follows the drawing. The playbook becomes one graph on the product's own state graph engine: a step is a node that does the work, a decision is a node that runs its check and returns an outcome, and an arrow is followed only by the outcome it is labelled with. The next step starts after the handover of the previous one has passed its checks.

The confirmation

In developer mode the header carries a playbook chip beside the folder chip: a dropdown of the registered playbook folders and a play button. With nothing picked, the dropdown shows the playbook pinned to the working folder, marked “suggested for this folder”; it is stored for the session only when you pick it or start a run with it. “No playbook” is a pick of its own: the pinned playbook then does not stand in, and a start is refused. The pick belongs to the session and comes back when the session is opened again. The Playbook view only configures and edits: its first tab, “Steps”, shows the playbook and its latest run and starts nothing.

A run starts in the chat of the session. Type /run-with-playbook or /playbook run and the task in the message box, for example /run-with-playbook add a CSV export, and send it. The play button only writes the command into the message box. Without a task the command is refused with its usage line. The task reaches every step, every question the run asks you names it, and it is recorded with the run. Nothing starts yet. The server answers with a sheet, “Start this run?”, that names the task and shows the drawing and these parts:

  • One row per step, and one per decision whose check is a review: who performs it, the provider and the model its model choice resolves to on this machine, the state of that provider, the privacy switch, the permission and whether the step waits for your nod. Before the sheet opens, the server asks every provider for its model list. When the playbook's model does not serve, the row says why in plain words: the key was rejected (with the HTTP status, and whether the key comes from the environment of the app or is saved in the app, never the key itself), the provider does not answer, it answers but does not list the model, or a private step names a cloud model.
  • A model picker in every row. It starts on the playbook's model, labelled as the playbook's default, and offers the models of every provider whose list answered. A private step is offered local providers only, without Ollama's cloud models (a tag cloud or one ending in -cloud). A pick shows at once that its provider lists the model. It holds for this run only: the playbook file is not written.
  • “Skills”, each with its source: “in the playbook” or “missing in the playbook”.
  • “Commands this run may execute”, every command of a command check word for word, so a command written in a shared folder is read before it can run.
  • “What this playbook brings”: the skills, commands, hooks, agents and workflows of the folder, for reading only, each with its source and hash. A skill, command, hook or agent is marked “in the playbook”, and a workflow “runnable” or “not run”. Nothing is installed, so the list names no install state and no item changed since an install. The full contents hash follows the list. The contents are shown here and are not part of the run hash.
  • “Hash”: a sha256 over playbook.json, every template, every file under the skill folders and every agent file a step names. The sheet shows the first characters.

“Start” stays disabled while the sheet lists reasons under “The run does not start because”. The reasons are a finding in the file, a skill that is missing, a step that asks for the permission extended, a human check with more than four outcomes, which is more than a question can offer, and a nod or a human check when nobody can be asked. Start also stays disabled while a row has no model this run can use, and a line above the button names those steps and checks. A private step whose model sits on a cloud provider is such a row, and a local pick lifts it. Pressing Start sends the hash and the picks to the server, which loads the folder again and compares. If any file changed since the sheet opened, the run does not start and the answer is “The playbook changed since the confirmation. Open it again.” The server then asks each picked provider for its model list once more and refuses a pick that no longer serves. The sheet stays open until the run starts, and a refusal of this start shows in it as well as in the chat. Stop while the picks are checked again stops the start before the run begins. The run keeps the copy it pinned, so an edit while it runs applies to the next run. No tool of the chat agent can start a run. A playbook that the chat agent wrote reaches a run only through this sheet and your click.

What a step does

A chat step runs as a turn of the main agent. If the step's model differs from the chat's current model, the chat is switched to it first and the conversation travels along. The prompt is a short text that the session keeps and a long text that the model receives: the goal, the documents the step reads and writes with their required sections, the full text of each named skill and the template of each document it hands on. When the run ends the chat returns to the model it had before.

A child step runs as a child agent in the role the step names (worker when it names none), on the provider of its own model choice, whatever the chat uses. A role agent:name runs on the type and preamble of that agent file, as pinned at the start. It draws one slot from the chat's pool like any other helper.

After a step the runner looks for the files that changed under the location of each document the step produces. If the step carries a nod, you are asked whether to approve the handover, and anything but approval ends the run.

The checks

A decision runs one check and takes the outcome it returns. Five kinds exist.

KindWhat it doesOutcomes
sectionsEvery listed document exists, every required section has text, and no forbidden string appears. A section is a heading with its name. If there is no such heading, a line that starts with the name as a bold field, such as **Goal:** or **Goal**:, counts as the section. Its text runs up to the next bold field line or the next heading of level 1 or 2, so ### sub-headings belong to it. A bold field inside a fenced code block does not count.pass, fail
open_itemsNo line of the documents is an unchecked task, a list item that starts with [ ].pass, fail
commandRuns a command from vars in the working folder. It passes the same host guard and the same permission gate as a command the agent runs, and the gate sees it as playbook_check. Exit code 0 is pass.pass, fail
reviewA child agent on the model the check names reads the listed documents, cannot write, and answers with one outcome as the last line of its answer. A reviewer runs under the stricter privacy of the steps that produced the documents it reads.the labels of the check
humanAsks you the question of the check and waits. An answer outside the labels counts as no answer.the labels of the check

A decision that sits on a loop carries max_rounds. The number counts how often the decision may send the run back. At the limit it takes the outcome exhausted, which the playbook routes to an end. The engine's own step limit stays as a second guard.

Privacy and model choice

Every step has a privacy switch, and the confirmation shows it as private or cheap.

  • A private step uses only the primary model of its choice, or the model picked for it in the sheet. Its fallbacks are never tried, and a primary on a cloud provider or an Ollama cloud model is refused before the run. If the model does not answer when the step starts, the run stops and asks whether to retry or stop. The question names the provider, the model, the address that was tried and the reason.
  • A cheap step tries the primary model and then its fallbacks in order and takes the first that answers. The walk is recorded.
  • If a chat step would switch to a cloud model after a private step ran earlier in the same run, the run asks first. The history of the chat would reach that provider, so the question names it and offers to continue or stop. It is asked once per run and provider.

Permission

A step may name a permission. The mode that applies is the stricter of the session's current mode and the step's, from strictest to widest: read only, ask, auto, extended. A playbook cannot widen what the session allows, and the step's limit ends with the step.

Watching and stopping

You follow a run beside the chat, in the Plan panel (chapter 6). The panel opens by itself when the run starts. It names the run, its task and how long it has run, draws a strip with one mark per node of the forward path, and has one card per step and decision in the order they ran: who works on it and on which model, the documents it reads and writes, the files its agents changed, how many shell commands ran, and while it runs the last line its agent wrote. A decision shows its round and outcome, and a loop that ran out of rounds reads “limit of 2 rounds reached”. The button “wide” puts the run in the chat's place, with the run's graph on top, drawn from the graph file the runner writes and asked again every second while the run lasts, and one entry in full below it; a press on a node shows that node's latest entry. A press on a card, or “In the chat” in the wide view, goes back to the chat at that step. A press on a document opens it in the Files panel, also one under a dot folder such as .superpowers/ when this run wrote it (“What a run leaves behind” below). How the run ended comes from its stop reason alone: done, stopped or failed. The model's own plan from update_plan shows under the run as “Plan of the model”; the plan the runner writes, one line per node, is not shown there, because the run above draws the same nodes. The footer does not call a chat step unfinished because later steps are still open. Stop ends the run: the running step and the run close as stopped, and the graph file still ends cleanly.

The chat of the session follows the run too. It shows a line when the run starts, with the playbook and the task and the link “open the run”, which brings that run up in the Plan panel, a line when a step starts, with the model it runs on, and a line when the run ends, with the result and the stop reason. The prompt a chat step sends appears as a turn with the header “Playbook” and an accent rule, so it does not read as a message you wrote.

A run ends with one of these words, recorded as the stopReason and shown in plain language in the chat's end line.

WordMeaning
doneThe path reached one of its ends. The result names which one; in the spectro playbook it is cancelled when a loop ran out of rounds.

A window that is closed or a server that is stopped during a run leaves no end record. The Plan panel then says “no end recorded” for the run and for the step that was open.

What a run leaves behind

The session file holds the run as run_step lines (chapter 22): one when the run starts, with its forward path, one when each step or decision starts and one when it ends, and one when the run ends. They carry who worked on a step, the model, what it was given and what came out, cut at 4,000 characters, the documents it read and the documents it wrote, each with its path in the working folder. The Plan panel draws the run from these lines, so a stored session shows its runs after a restart. The documents a run wrote open through GET /api/run-document (chapter 26), dot folders included: only a path a step_end line of that run names, only inside the session's working folder, only while that folder is the one the run worked in, and never a secret such as a .env file, a key file or anything under .git, .aws or .ssh. Any other path opens the way the Files panel opens a file.

Two kinds of file live in ~/.spectro/playbook-runs/, outside the sessions folder so that the session list does not read them. Both are removed when the session is deleted.

  • <session>.<run>.graph.jsonl is the graph artifact of one run: the topology and one record each time a node starts or ends and each time an arrow is taken. The state graph view reads it.
  • <session>.playbook.jsonl is the sidecar of the session, one line per fact, several runs one after the other. The session file itself is not changed, so the sidecar is found by the session id. Its record types are playbook_start (playbook, folder, hash, the session's permission mode, the chat's model before the run and the models picked in the sheet, if any), step_start (step, model choice, whether its model was picked, provider, model, address, the probe with its state and reason, the walk over fallbacks, the effective permission), step_end (the child, whether the step succeeded, how long it took, the error), check (the check, its kind, the outcome, the loop count, a short detail), nod (the answer and how long it took), privacy (the provider asked about and the answer) and playbook_end (the stop reason, the result and the number of steps). A workflow run writes into the same sidecar: workflow_start (the workflow, its file, its hash and how many characters you typed after its name), workflow_step (the step, its kind, the round, the children it started, whether it succeeded and how long it took) and workflow_end (the stop reason, the result and the number of steps). The sidecar answers which model served which step. Every string passes the same redaction as the other recordings, and the file stops growing at 16 MiB with a line that says so.

Running a workflow

A workflow is a short list of steps in one JSON file under workflows/, listed in the contents of playbook.json. The shipped playbook carries two. In fanout-review.json the chat prints the diff of the working folder, three reviewers read it at the same time for correctness, security and readability, and a summariser joins their findings into one review. The note you type after the workflow's name goes to each reviewer and to the summariser. In fanout-research.json three explorers look for the answer to your question in the code, the documents and the tests, and a summariser answers from what they found. A file has a name, a description and steps, and a step is one of three kinds:

  • prompt is one chat turn. Its template is sent as a message of this session, and the answer of the turn is the step's answer.
  • fanout starts one to four helpers, each with a role and a task, and optionally a join with one more task for the summariser. The role is explore or worker.
  • end ends the run, with an optional result label.

A template may name {{input}} (the text you type after the workflow's name), {{previous}} (the answer of the step before), {{folder}} (the working folder) and, in a join task only, {{results}} (what the helpers returned). Any other name is refused when the file is read. A step can repeat until its answer contains the text in repeat_until, and then it must carry max_rounds, from 1 to 10; a file without it is refused with the line the step starts on. A run whose step used up its rounds without the text stops as exhausted. A whole run has two ceilings, counted when the file is read. It starts at most 20 helper runs, and every round of a fan-out counts its helpers and its summariser. It runs at most 20 step runs, and every round of a prompt or fan-out step counts. A file over either ceiling is refused, and the finding names the step where the count passes it. The format has a JSON schema, workflow.schema.json, and it also reads the scenario shape of the Lab, where a step is written as the one key that names its kind.

The Steps tab lists the workflows of the loaded playbook under “Workflows”, each with its name and the start of its hash, and starts none of them. A workflow starts in the chat of a session: /playbook workflow or /run-workflow, the workflow's name (its file name without .json) and the text for {{input}}, for example /playbook workflow fanout-review check the auth module. It runs at once in that session, from the session's playbook: the one picked in the header chip, else the one pinned to the working folder. An unknown name is refused with the names the playbook has. A workflow that starts a worker helper is listed and not run: a worker can write files, and a workflow starts without a confirmation sheet. The list marks such a file “Does not run: not a step list, or the workflow starts a worker helper, which can write files.” A run holds the session like a playbook run, so a message typed meanwhile is refused with the usual note. The run shows in the chat: a line when it starts, “Workflow fanout-review started on: check the auth module”, with the link “open the run”, and a line when it ends, with the stop reason in words. A loop whose rounds ran out before its condition held ends with exhausted, “the round limit was reached”. The Plan panel follows it like a playbook run, and its wide view draws the steps as a chain, because a workflow has no graph file. During a fanout step no model turn of the session is open: the run starts the helpers with spawn_agents in the background, waits for them and collects their results with wait_agents, then hands the joined results to one summariser helper. The summary is the last message of the run in the chat. While the helpers work, each status line they report appears in the chat, the session's status line in other sessions' list_agents shows the latest of them, and list_agents of this session lists the helpers. A helper can write to the run with send_message to parent, and its message appears in the chat. A helper cannot write to another helper: the summariser gets their results from the run. A message from another session that arrives during the fan-out waits for the next chat turn. A fan-out of three helpers and one summariser starts four helper runs on the provider. The run writes the sidecar records above and no file into the working folder; the helpers write only what their tasks name.

What a playbook file may not carry

A shared folder must not be able to route your material or widen your rights. A key named apiKey, key, baseUrl, endpoint, address, hooks, mcpServers or autoApprove, anywhere in playbook.json except inside the contents list, is refused with its path, for example nodes[1].baseUrl. The permission of a step can be inherit, readonly, ask or auto, and never extended. Node kinds for splitting and joining paths, a fallback chain on a step and a nested playbook are recognised and refused as not supported in version 1.

What version 1 does not do

  • A run does not resume after a restart. A quit or a server stop ends it, and starting again begins at the first node.
  • There is no headless entry. A run starts from the window, and a playbook with a human check or a nod is refused when nobody can be asked.
  • A shared folder cannot start a run. Only the confirmation sheet does, after you read the commands, the contents and the hash.
  • A command, hook or workflow of the folder that changes after the confirmation does not stop a run by itself. Every file under the skill folders, every template and every agent file a step names is part of the hash, and a change to one of them after the confirmation stops the start.
  • Between two steps the chat is idle and its composer is enabled. A message typed then is refused with the usual note that a run is active.
  • You cannot place a box by hand. The graph carries no coordinates, and the layout engine decides where each box goes.
  • A workflow file that is not a step list is listed and not run. A workflow has no split and join of its own beyond the fan-out step, and a run starts only from the chat of a session.
  • A playbook's hooks do not run in a session that picks it. The agent's file tools refuse to write under a registered playbook folder, but a shell command run with run_command is not fenced from it.
  • Paths that split into parallel branches and join again are not part of the format yet.
